## 0. TL;DR — the four load-bearing decisions

The product, platform, and tie-breaker memos most need to react to these:

1. **`settings-rewrite` is a fifth mutation kind, not a variant of
   `file-replace`.** v0.2's `MUTATION_KINDS` enum reserves four values
   (`dir-rmtree`, `file-unlink`, `file-replace`, `json-fragment-edit`); v0.3
   adds `settings-rewrite` as a separate, fully-defined kind. The reasoning is
   that "settings" is not a generic file: the apply protocol must validate the
   shape *before* snapshotting, must run an idempotency check that
   `file-replace` cannot specify, and must refuse JSONC files cleanly. We do
   NOT use `json-fragment-edit` because v0.3's three promotion detectors
   (`hook_path_dangling`, `mcp_command_missing`, `invalid_json`) need
   whole-document rewrites, not fragment patches. See §1.

2. **`composeHardenPlan(home, options)` is a peer to `composeCleanPlan`, not a
   superset.** It lives in its own module (`scripts/lib/harden-plan.mjs`) and
   reuses the 12-rule refusal classifier from `clean-plan.mjs` by exporting
   that classifier as a shared helper. Harden adds three new refusal reasons
   (`settings-jsonc-detected`, `patch-not-idempotent`,
   `patch-produces-invalid-json`) that compose with — not replace — the
   existing taxonomy. This keeps the no-mutation allowlist short: v0.3 adds
   exactly one new mutation surface to `test/no-mutation.test.mjs`. See §2.

3. **`clean --batch` is a parser-and-orchestrator change, not a new mutation
   kind.** A batch is N existing operations under one operation manifest, one
   snapshot tree, one lockfile acquisition, one aggregate budget check, and
   one rollback unit. The CleanPlan schema grows from a single
   `operations[0]` to `operations[0..N-1]` with `N <= 10`, and `executeCleanPlan`
   is refactored to drive the loop. No new MutationRegistry entries. See §3.

4. **Detector promotion is a flag on the detector's raw output, not a side
   table.** Each detector grows a `hardenable: boolean` (or `cleanable:
   boolean`) declaration in its `DetectorOutput`, mirroring how
   `forceStance` already works. The audit pipeline reads that flag and routes
   findings to `prepare` stance vs. `review` stance accordingly. This is Q4's
   answer (§5.4). It keeps the audit pipeline declarative and avoids a hidden
   "is this cleanable?" lookup table in `clean-plan.mjs` or `harden-plan.mjs`.
   See §4.

The rest of the memo backs these four with concrete schema, every detector
promotion mapped to a mutation kind, an idempotency proof, refusal extensions,
threat model deltas, and answers to all five Open Design Questions.

## 1. The `settings-rewrite` mutation kind

### 1.1 Why a new kind, not a variant

`scripts/lib/snapshot.mjs` already supports a generic file-write through the
`applyOperation(id, home, ops)` seam at line 535: the caller passes an `ops[i]`
whose `apply(originalPath)` callback can write any content. The temptation is
to say "harden is just `file-replace` with a pre-computed payload."

That is the wrong abstraction for three reasons that bite immediately:

1. **Pre-apply validation must run before the snapshot is taken.** If we
   produce a settings JSON that doesn't parse, the snapshot write has already
   happened and we leave behind a dead `op_<id>.json` manifest that the
   `housekeeper.interrupted_operation` detector will surface on the next
   `diagnose`. The user pays a noise tax for our validation gap. Cleaner: a
   `settings-rewrite` apply contract requires `validatePatch()` *before*
   `takeSnapshot()` is called.

2. **Idempotency is a settings-specific invariant.** A merge into
   `settings.json` that *appends* a hook entry will produce different output on
   a second apply (two appended entries). A merge that *replaces* a key with a
   normalised value is idempotent. The mutation registry needs a place to
   declare which kind of merge a given patch is, so `executeHardenPlan` can
   refuse non-idempotent patches at validation time rather than catching the
   failure post-snapshot.

3. **JSONC handling is settings-specific.** Other JSON files we touch (e.g.
   `installed_plugins.json`) are strict JSON. Claude Code's `settings.json`
   accepts JSONC. A generic `file-replace` has no place to declare its parser
   choice. `settings-rewrite` does.

So: a new mutation kind whose contract bakes in the validation, idempotency,
and JSONC posture decisions.

### 1.2 Apply protocol — read, transform, validate, write, hash

The full lifecycle for one `settings-rewrite` operation:

```
                          ┌─────────────────────────────────────┐
                          │ composeHardenPlan(home, opts)       │
                          │  - reads settings.json              │
                          │  - parses (strict JSON, per Q2)     │
                          │  - applies the proposed transform   │
                          │  - re-runs the transform on output  │
                          │  - asserts byte-equality (idempot.) │
                          │  - validates output parses as JSON  │
                          │  - emits CleanPlan or refused[]     │
                          └────────────────┬────────────────────┘
                                           │
                          ┌────────────────▼────────────────────┐
                          │ validateHardenPlan(plan, home)      │
                          │  - re-runs assembleReport           │
                          │  - re-hashes current settings.json  │
                          │  - asserts no drift since compose   │
                          │  - asserts protected-path policy    │
                          │  - throws PlanDriftError on mismatch│
                          └────────────────┬────────────────────┘
                                           │
                          ┌────────────────▼────────────────────┐
                          │ executeHardenPlan(plan, home)       │
                          │  - acquires housekeeper lockfile    │
                          │  - gcSnapshots (mirror clean)       │
                          │  - takeSnapshot on settings.json    │
                          │  - applyOperation w/ rewrite ops    │
                          │     - re-reads, re-transforms       │
                          │     - atomicWrite to settings.json  │
                          │     - records sha256After           │
                          │  - verify (sha matches sha256After) │
                          │  - releases lockfile                │
                          └─────────────────────────────────────┘
```

The contract is *symmetric* with `clean`: same snapshot writer, same lockfile,
same rollback path. That's the architectural lever — by making `harden` just
another consumer of the v0.2 pipeline, we get rollback for free.

### 1.3 The `MUTATION_REGISTRY` extension

In `scripts/lib/snapshot.mjs` the registry today (well — strictly in
`scripts/lib/clean-plan.mjs`, see §1.5) keys on mutation kind:

```js
// scripts/lib/clean-plan.mjs:115
export const MUTATION_REGISTRY = Object.freeze({
  "dir-rmtree":  (args) => ({ apply: ..., args }),
  "file-unlink": (args) => ({ apply: ..., args }),
  "file-replace":      (_args) => { throw new NotImplementedError("file-replace"); },
  "json-fragment-edit":(_args) => { throw new NotImplementedError("json-fragment-edit"); }
});
```

The v0.3 entry:

```js
"settings-rewrite": (args) => ({
  apply: async (originalPath) => {
    // args.transform — pure function: (parsedJson) => parsedJson
    // args.parserChoice — "strict" | "jsonc" per Q2 ruling
    // args.expectedSha256Before — drift guard against TOCTOU
    const raw = await readFile(originalPath, "utf8");
    const parsed = args.parserChoice === "strict"
      ? JSON.parse(raw)
      : parseJsonc(raw);
    const transformed = args.transform(parsed);
    const serialised = JSON.stringify(transformed, null, 2) + os.EOL;
    // idempotency double-check (cheap; transform is pure)
    const reTransformed = args.transform(JSON.parse(serialised));
    const reSerialised  = JSON.stringify(reTransformed, null, 2) + os.EOL;
    if (serialised !== reSerialised) {
      throw new NotIdempotentError(originalPath);
    }
    await atomicWrite(originalPath, serialised);
  },
  args
});
```

Three notes on the shape:

- `args.transform` is a pure function smuggled from
  `composeHardenPlan`. It is the same callable we used in compose to compute
  the expected output; reusing it in apply prevents drift between
  "what we planned" and "what we did."

- `args.expectedSha256Before` is redundant with `applyOperation`'s drift check
  at `snapshot.mjs:544-549`, but we keep it here as a defense-in-depth so a
  future refactor that bypasses the drift loop still catches a race.

- `args.parserChoice` is set once per plan, by `composeHardenPlan`, from the
  Q2 ruling. We do not let it vary per operation — that would invite a
  mixed-mode plan where some operations strip comments and others preserve
  them.

### 1.4 Pre-apply checks — why they belong in compose, not apply

The four pre-apply checks (from PLAN-v0.3 §3):

| # | Check | Where |
|---|---|---|
| 1 | Target parses as valid JSON | `composeHardenPlan` |
| 2 | Proposed patch produces syntactically valid output | `composeHardenPlan` |
| 3 | `sha256Before` matches the snapshot at apply time | `applyOperation` (existing) |
| 4 | Patch is idempotent | `composeHardenPlan` (primary), `apply()` (defense-in-depth) |

The reason 1, 2, and 4 belong in compose is the same reason
`composeCleanPlan` does its symlink and MCP-server checks before
`takeSnapshot`: a failure here yields a `refused[]` entry with `exitCode 2`,
not an interrupted operation manifest. The user gets a clean refusal with a
`nextStep` hint, instead of a half-written snapshot and a noise finding on
the next diagnose.

Check 3 (drift) is the one we cannot do in compose, because it has to be done
*atomically with the read that produces the new content*. `applyOperation`
already implements this; we don't duplicate it.

### 1.5 Module placement — `scripts/lib/snapshot.mjs` vs. `clean-plan.mjs`

A subtle point. The `MUTATION_REGISTRY` in v0.2 lives in `clean-plan.mjs`, not
`snapshot.mjs`. That's because the registry encodes *what cleaning does*,
which is `clean-plan`'s job; `snapshot.mjs` is the I/O layer. The v0.3
question: do we put `settings-rewrite` in `clean-plan.mjs`'s registry, or in
a new registry in `harden-plan.mjs`?

**Recommendation: split.** `clean-plan.mjs` keeps `dir-rmtree` and
`file-unlink` (and the reserved `file-replace` / `json-fragment-edit`
stubs). `harden-plan.mjs` owns `settings-rewrite`. Both modules import a
shared `executeMutation(opId, snapshotHome, ops)` helper from `snapshot.mjs`
so they don't duplicate the apply-and-verify loop.

This keeps `no-mutation.test.mjs` honest: it allowlists exactly two mutation
surfaces (`lib/clean-plan.mjs`, `lib/harden-plan.mjs`) instead of one giant
file. It also keeps each module under the 800-line size guideline.

### 1.6 The schema delta

`docs/schema-stability.md` documents the manifest at `schemaVersion: 0.2`.
v0.3 stays at 0.2 because the only schema change is *adding* a value to the
implicit `mutationKind` enum, which is forward-compatible: old readers that
don't recognise `settings-rewrite` will see a normal manifest with files[]
and either roll it back or surface it as interrupted.

The operation manifest's `command` field gains a new value:
`"command": "harden"`. v0.2 already documents `"clean" | "rollback"` and
reserves `"harden"`; we are turning the reservation into a live value.

## 2. The `harden` pipeline — compose, validate, snapshot, apply, verify

### 2.1 Pipeline diagram

Mirrors `clean` with one extra pre-snapshot check (the harden plan must
produce a valid output JSON before any file I/O):

```
                                          (user types `harden --confirm --yes`)
                                                         │
                          ┌──────────────────────────────┼──────────────────────────────┐
                          │                              ▼                              │
                          │     ┌─────────────────────────────────────────────────┐      │
                          │     │ 1. composeHardenPlan(home, {target, path})     │      │
                          │     │    - assembleReport (Q-USER-2 freshness)        │      │
                          │     │    - filter findings by target/path             │      │
                          │     │    - 12-rule classifier (clean-plan.mjs)        │      │
                          │     │    - +3 harden-specific refusals (see §2.3)     │      │
                          │     │    - validate output parses                     │      │
                          │     │    - validate idempotency                       │      │
                          │     │    - emit CleanPlan {operations, refused}       │      │
                          │     └────────────────────────┬────────────────────────┘      │
                          │                              │                              │
                          │     ┌────────────────────────▼────────────────────────┐      │
                          │     │ 2. validateHardenPlan(plan, home)              │      │
                          │     │    - re-assembleReport, hashReport == plan.hash │      │
                          │     │    - re-check protected-path policy             │      │
                          │     │    - re-check current settings.json sha256      │      │
                          │     │    - throw PlanDriftError on any mismatch       │      │
                          │     └────────────────────────┬────────────────────────┘      │
                          │                              │                              │
                          │     ┌────────────────────────▼────────────────────────┐      │
                          │     │ 3. executeHardenPlan(plan, home)               │      │
                          │     │    - acquireLock(home)                          │      │
                          │     │    - gcSnapshots(snapshotHome)                  │      │
                          │     │    - for op in plan.operations:                 │      │
                          │     │        takeSnapshot(targets=[settings.json])    │      │
                          │     │        applyOperation(opId, snapshotHome, ops)  │      │
                          │     │            (settings-rewrite atomicWrite)       │      │
                          │     │        verify(opId, snapshotHome)               │      │
                          │     │    - releaseLock                                │      │
                          │     │    - return finalManifest                       │      │
                          │     └─────────────────────────────────────────────────┘      │
                          └─────────────────────────────────────────────────────────────┘
```

### 2.2 What's identical to `clean`

By design, `harden` reuses every load-bearing piece of v0.2:

- `assembleReport` from `audit.mjs` (re-run at compose and validate)
- `loadConfig` + `pathMatchesProtection` from `policy.mjs`
- `classifyFinding` (the 12-rule classifier — extracted into a shared helper)
- `takeSnapshot`, `applyOperation`, `verify` from `snapshot.mjs`
- `gcSnapshots` for the 10-op retention budget
- `acquireLock` / `releaseLock` lockfile protocol
- Rollback path through `composeRollbackPlan` / `executeRollbackPlan`

That last point matters: **rollback for harden is the same code path as
rollback for clean.** A v0.3 harden operation produces an
`OperationManifest` whose `files[]` array points at `settings.json`'s
snapshot; `executeRollbackPlan` reads the manifest, restores the snapshot
copy with `copyFile`, and re-hashes. The `mutationKind: "settings-rewrite"`
in the operation field is informational metadata — the rollback registry
keys on `rollbackOp.kind = "file-restore-from-snapshot"`, which already
handles whole-file restore.

This is the v0.3 architecture's most important non-obvious property:
**`rollback-plan.mjs` requires no changes for `harden` to be rollbackable.**
We verified this by reading the rollback handler at
`rollback-plan.mjs:197-202`:

```js
const ROLLBACK_REGISTRY = Object.freeze({
  "file-restore-from-snapshot": async (args) => {
    await mkdir(dirname(args.targetPath), { recursive: true });
    await copyFile(args.sourcePath, args.targetPath);
  }
});
```

That's it. The rollback writes the snapshot bytes back to the original
path. For `settings.json` that means the pre-patch JSON re-appears
byte-for-byte. We do NOT need a new rollback kind, and we do NOT need to
teach rollback about JSONC, idempotency, or any settings-specific concern —
those are *forward* concerns, owned by harden's apply path.

### 2.3 What's new — three refusal extensions

The 12-rule classifier gains three new refusal reasons, applied only when
the target detector is `hardenable`:

| # | Reason | Triggers |
|---|---|---|
| 13 | `settings-jsonc-detected` | File contains `//` or `/* */` comments AND Q2 ruling says refuse JSONC |
| 14 | `patch-not-idempotent` | `transform(transform(settings)) !== transform(settings)` |
| 15 | `patch-produces-invalid-json` | `JSON.parse(JSON.stringify(transform(settings)))` throws |

All three fire at compose time. They produce `CleanPlanRefusal` entries with
`exitCode 2`, mirroring the existing taxonomy.

The `nextStep` hints (NEXT_STEP_BY_REASON in `clean-plan.mjs:327`) gain three
entries:

```js
"settings-jsonc-detected":
  "Harden refuses settings files with JSONC comments. Either strip comments manually or wait for v0.4 JSONC support.",
"patch-not-idempotent":
  "Applying this patch twice produces different output. Re-run `diagnose`; if the finding persists, file a bug.",
"patch-produces-invalid-json":
  "Patch would produce invalid JSON. Re-run `diagnose`; if the finding persists, file a bug."
```

Note that the last two end in "file a bug" — they should never fire in
practice for the v0.3 detector set. If they fire, our patch generators have
a bug. The refusal is there as defense-in-depth, not a routine flow.

### 2.4 Idempotency — the proof obligation

For each `settings-rewrite` patch we ship, we must prove (via a unit test)
that:

```
transform(transform(s)) == transform(s)   for all s in the detector's input domain
```

This is the **T-102 idempotency check** from the taskboard. The proof is:

- **`hook_path_dangling`**: transform removes the dangling hook entry. Run
  twice: the second run is a no-op because the entry is already gone. ✓
- **`mcp_command_missing`**: transform removes the `mcpServers[name]` entry.
  Run twice: no-op on the second run. ✓
- **`invalid_json`**: see Q1 ruling — if we go option (b) "move aside +
  write empty `{}`", then transform is the constant function `() => {}`,
  which is trivially idempotent. ✓

All three are idempotent by construction. The runtime check
(`apply()` re-runs transform on its own output and asserts equality) is a
runtime guard against a future patch generator that violates this property.

### 2.5 Interaction with v0.2 lock + budget

The harden pipeline acquires the **same** `<home>/.claude/housekeeper/lock`
that clean uses. This is intentional. The invariant we want is "at most one
housekeeper mutation in flight against this home." If clean and harden held
separate locks, a concurrent harden could mutate `settings.json` while a
clean was deleting a plugin cache version that `settings.json` references —
the worst possible TOCTOU.

The 30-minute staleness window applies identically. A stale harden lock
surfaces as `housekeeper.stale_lock` and the user can clean it with the
existing flow.

The budget (50 files, 10 MiB from `snapshot.mjs:26-29`) applies trivially:
each harden operation snapshots exactly one file (`settings.json`), which is
typically <100 KiB. We do not need to extend `MAX_OPERATION_FILES` or
`MAX_OPERATION_BYTES` for v0.3. Batch operations (§3) test this at the
aggregate level.

## 3. Batch flow — `clean --batch`

### 3.1 What "batch" means precisely

A batch is **N operations in one manifest, one snapshot tree, one lockfile,
one budget check, one rollback unit**. It is NOT:

- N separate manifests inside a loop (that would be N lockfile
  acquisitions, N rollback ids, N gcSnapshots calls; defeats the "one
  consent, one undo" UX the product memo wants)
- A reduction of N findings to one mutation (that would lose per-finding
  rollback granularity — but see §3.4 on the atomicity question)
- A way to chain `clean` and `harden` in one invocation (that's a v0.4
  request, called out in PLAN-v0.3 §1's "deferred" table)

The CLI shape (parser change, T-500):

```
$ claude-housekeeper clean --batch --confirm --yes \
    --target=plugin.cache_unreferenced --path=/path/to/v1 \
    --target=plugin.cache_unreferenced --path=/path/to/v2 \
    --target=registry.local_command_identical --path=/path/to/cmd.md
```

The parser yields an array `[{target, path}, ...]` of pairs. The
`--batch=N` form sets the aggregate cap (default 10, per PLAN-v0.3 §3).

### 3.2 Plan composition for batch

`composeCleanPlan` grows an alternative entry point — call it
`composeBatchCleanPlan(home, targets)` — that:

1. Runs `assembleReport` once at the top (Q-USER-2 freshness, but cheaper
   than running it per target).
2. For each `{target, path}` pair, runs the existing single-target compose
   path, collecting `operations` and `refused`.
3. Concatenates the `operations` arrays into one flat list.
4. **Re-checks the aggregate budget**:
   - `sum(operations[i].estimatedBytes) <= MAX_OPERATION_BYTES`
   - `sum(operations[i].expandedFiles.length) <= MAX_OPERATION_FILES`
5. If aggregate exceeds budget, refuses the entire batch with a new reason:
   `batch-budget-exceeded`.
6. Caps N at 10 per PLAN-v0.3 §3. If N > 10, refuses with `batch-cap-exceeded`.

The output is a single `CleanPlan` with `operations[0..N-1]` populated. The
existing `validateCleanPlan` re-checks each operation; the existing
`executeCleanPlan` drives the loop.

### 3.3 Snapshot for batch — one tree, many files

A batch takes **one** `takeSnapshot` call with N targets (or the union of
each operation's `expandedFiles`). The manifest's `files[]` array holds the
union. The snapshot directory holds one `files/` subdirectory with one entry
per snapshotted file.

The budget check inside `takeSnapshot` (`snapshot.mjs:275-293`) handles this
automatically — it sums byte sizes across all targets. The aggregate budget
in compose (§3.2 step 4) is a *pre-check* so we refuse cleanly with a
`CleanPlanRefusal` instead of a `SnapshotBudgetError` (which would be a
thrown error, not a structured refusal).

### 3.4 Atomicity — the Q3 question

If a 5-operation batch completes ops 1, 2, 3 and crashes on op 4, what
happens?

Three candidate models (from PLAN-v0.3 §4 Q3):

- **(a) Auto-rollback all 5.** Consistent state, no half-applied surface. But
  ops 1, 2, 3 succeeded — their work is undone.
- **(b) Leave partial state.** `housekeeper.interrupted_operation` surfaces
  the half-applied manifest; user runs `rollback <id>` manually.
- **(c) Resume on next invocation.** Re-run the partial batch from op 4.
  Complex; requires per-op resume tokens.

**Recommendation: (b)**, mirroring v0.2's `partialApply: true` semantics.
Rationale: this matches v0.2's existing model for the
`housekeeper.interrupted_operation` flow. A v0.3 user who runs
`rollback <id>` undoes the entire batch (snapshot tree still has the
pre-state of all 5 ops). A v0.3 user who runs `diagnose` sees the
interrupted operation and the `nextStep` routes them to rollback. This
keeps the v0.3 cognitive surface identical to v0.2 — no new mental model
for batch failures.

Option (a) is tempting (auto-rollback on partial) but PLAN-v0.2 ruled this
out for v0.2 ("Auto-rollback on partialApply: true — Tie-breaker Ruling 9:
deferred to v0.2.x"). We should not introduce auto-rollback in v0.3 either;
it changes the contract retroactively. v0.4 is the right place to revisit
once we have a quarter of real-world telemetry on partial-apply frequency.

See §5.3 for the full Q3 ruling.

### 3.5 Rollback of batch

A batch produces one manifest with N files in `files[]`. `executeRollbackPlan`
loops over `manifest.files`, restoring each via `copyFile`. No changes
needed.

The only ergonomic question: does the user want to roll back **all** of a
batch, or **just one** finding's worth? v0.3 ships **all-or-nothing**: the
operation id is the unit of rollback. Per-finding rollback inside a batch
would require splitting `files[]` into groups by finding, and we'd need a
new `rollback <opId> --only=<finding-target>` flag. That's a v0.4 feature
if telemetry shows demand; for v0.3 it stays out of scope.

### 3.6 Why batch is not a v0.4 problem

The product memo will rightly push back on "do we need batch at all in
v0.3?" Two reasons we should land it:

- **It's the natural test case for `harden`.** Once `harden` ships,
  users will want "fix all my dangling hooks in one go." Without batch,
  they invoke harden N times, taking N locks, accumulating N manifests.
  That's a quadratic UX cost for what is fundamentally one decision.

- **It validates the lockfile + manifest design under aggregation.**
  v0.2 ships a single-op flow. We have no evidence the design composes
  to N ops without surprises. Better to find out in v0.3 (low stakes —
  N <= 10) than in v0.4 (where the request will be N = "all").

The platform memo may have a counter-argument around Claude Code's
file-watcher behaviour for `settings.json` (does it re-read on every
write or debounce?). Defer to that memo's verdict; if Claude debounces
poorly, batch may need to serialise harden operations rather than
parallelise them. Either way, the schema and refusal taxonomy are the
same.

## 4. Detector promotion mechanics

### 4.1 The promotion question

Three detectors graduate in v0.3 (PLAN-v0.3 §3):

| Detector | Mutation kind | Promotion type |
|---|---|---|
| `settings.hook_path_dangling` | `settings-rewrite` | `hardenable` |
| `settings.mcp_command_missing` | `settings-rewrite` | `hardenable` |
| `settings.invalid_json` | `settings-rewrite` (per Q1.b) | `hardenable` |

None graduate to `cleanable` — they all need to *rewrite* a file, not
delete it. So v0.3 introduces a new graduation lane: the audit pipeline
must distinguish "this finding can be cleaned" from "this finding can be
hardened" from "review only."

### 4.2 The mechanism — `hardenable` / `cleanable` flags on DetectorOutput

Two new optional fields on the `DetectorOutput` shape (from
`audit.mjs:390`):

```js
// DetectorOutput = {
//   id, class, surfaceHints, surface?, evidence, missingKeys,
//   summary, targetPath, blockedActions?, nextAllowedStep?,
//   claimLevel?, forceStance?,
//   hardenable?, cleanable?    // ← new in v0.3
// }
```

A detector that supports harden sets `hardenable: true`. A detector that
supports clean sets `cleanable: true`. Neither flag is required; absence
means "review only." A detector MAY set both flags (e.g. a future
detector that could be either cleaned or hardened).

### 4.3 How the audit pipeline reads the flags

In `audit.mjs:buildFinding` (~line 191), after stance is decided, the
finding gains a `nextAllowedStep` derived from stance. For
`hardenable`/`cleanable` findings, the `nextAllowedStep` is upgraded:

```js
if (raw.hardenable && stance === "prepare") {
  finding.nextAllowedStep =
    `harden --confirm --yes --target=${raw.id} --path=${raw.targetPath}`;
}
if (raw.cleanable && stance === "prepare") {
  finding.nextAllowedStep =
    `clean --confirm --yes --target=${raw.id} --path=${raw.targetPath}`;
}
```

This means the `nextStep` field in diagnose output becomes a literal
command the user can paste. It's the same shape we already use for
v0.2's `plugin.cache_unreferenced` finding.

### 4.4 The promotion sequence per detector

For each of the three promotion detectors, the v0.3 PR sequence is:

1. **Acceptance card** in `docs/acceptance/` describing the user-facing
   contract (what the patch does, what the refusal cases are).
2. **Golden fixture** in `fixtures/synthetic-homes/<detector-name>/`
   reproducing the finding state.
3. **Transform function** in `harden-plan.mjs` that produces the patched
   settings.
4. **Idempotency test** asserting `transform(transform(s)) == transform(s)`.
5. **Audit annotation** — add `hardenable: true` to the detector output.
6. **Refusal test** for the three new refusal classes against the fixture.

Steps 1-5 are independent per detector; step 6 is shared. Estimate: ~2-3
days per detector, in parallel.

### 4.5 Why this beats a side table

The alternative is a lookup table in `harden-plan.mjs`:

```js
const HARDENABLE_DETECTORS_V03 = new Set([
  "settings.hook_path_dangling",
  "settings.mcp_command_missing",
  "settings.invalid_json"
]);
```

v0.2 already does this for clean (`CLEANABLE_DETECTORS_V02` in
`clean-plan.mjs:156`). Why not the same for harden?

Two reasons we should prefer the per-detector flag:

- **Detector ownership.** A detector knows whether it has a meaningful
  patch transform. Putting the flag on the detector keeps that knowledge
  co-located with the detector code. A side table forces a developer
  adding a new detector to remember to update *two* files.

- **Composability.** If v0.4 adds a fourth surface (say,
  `installed-plugins-rewrite`), we'd want to add a fourth flag without
  growing a fourth side table. The per-detector pattern scales; the
  side table doesn't.

**Pragmatic note:** v0.2's `CLEANABLE_DETECTORS_V02` stays as-is. We
don't refactor v0.2 to use per-detector flags retroactively — that
would be scope creep and would risk regressing the v0.2 release. v0.3
sets the precedent for new detectors; v0.4 can do the v0.2 cleanup if
the pattern proves out.

### 4.6 What about `review-only` detectors?

These need no change. A detector that emits findings with neither
`hardenable` nor `cleanable` flag set produces a finding whose
`nextAllowedStep` reflects the existing stance logic from
`stance.mjs`. v0.3 does not regress any v0.2 review-only flow.

## 5. Q1–Q5 answers

These are the architect's proposed defaults. The tie-breaker pass
(T-D04) will combine these with the product and platform memos'
proposals and produce a final ruling.

### 5.1 Q1 — `settings.invalid_json` recovery

**Question (PLAN-v0.3 §4 Q1):** Should harden act on a settings file
that doesn't parse as JSON?

**Proposed default: (a) Refuse.**

**Rationale:** We cannot infer the user's intent from a broken parse.
Option (b) ("move aside + write empty `{}`") destroys whatever the
user was trying to write; even with the `.broken-YYYYMMDD` rename, a
user who runs `harden` thinking they've authorised a hook removal will
suddenly find their entire settings file blanked. That's a worse UX
than "refuse and tell the user to fix it manually." Option (c) (JSON
repair heuristics) is silently-wrong territory and we've explicitly
ruled it out in v0.2 (see refusal taxonomy "no-mutation-mapping-in-v0.2").

The refusal class is the existing rule 12: `no-mutation-mapping-in-v0.2`,
extended to `no-mutation-mapping-in-v0.3` (or kept as-is with a
detector-specific message). The `nextStep` hint:

> `settings.json` is invalid JSON; harden cannot infer your intent. Open
> the file in your editor, fix the parse error, and re-run `diagnose`.

This makes `settings.invalid_json` **block-stance only** in v0.3. The
detector keeps emitting findings; harden refuses to mutate.

**One-line rationale:** Refuse — silent settings overwrite is a worse
failure mode than a forced manual fix.

### 5.2 Q2 — Settings JSONC support

**Question:** Claude Code accepts JSONC in `settings.json`. Should harden:
(a) refuse JSONC files, (b) strip+restore comments, (c) adopt a tolerant
parser?

**Proposed default: (a) Refuse JSONC files in v0.3, revisit in v0.4.**

**Rationale:** Comment preservation in JSON round-trips is a known hard
problem. The `jsonc-parser` library (option c) parses JSONC but does NOT
preserve comments on serialisation — you'd get a comment-free output.
Option (b) (strip+restore) requires a comment-position tracker; even
sophisticated implementations (e.g. `comment-json`) have edge cases
around comments inside merged objects.

The platform memo will likely confirm that Claude Code's own loader
accepts JSONC; that's a *read* path. Housekeeper's harden is a *write*
path, and the comment loss on round-trip would be a silent
information-destroying change.

Refusing JSONC in v0.3 is conservative but correct. The refusal class is
new (`settings-jsonc-detected`, see §2.3). The `nextStep` hint tells
the user to strip comments and re-run, or to wait for v0.4.

**Detection mechanism:** `composeHardenPlan` reads the raw settings
bytes and scans for `//` or `/*` outside string literals. A simple
regex catches the common cases; we accept that pathological strings
might false-positive (e.g. `"value": "http://example.com"` — actually
no, `//` inside a string is fine for the scanner because we lex
JSON strings first). The full algorithm:

```js
function detectJsonc(raw) {
  let inString = false;
  let escape   = false;
  for (let i = 0; i < raw.length; i++) {
    const c = raw[i];
    if (escape) { escape = false; continue; }
    if (inString) {
      if (c === "\\") { escape = true; continue; }
      if (c === '"') { inString = false; continue; }
      continue;
    }
    if (c === '"') { inString = true; continue; }
    if (c === "/" && raw[i+1] === "/") return true;
    if (c === "/" && raw[i+1] === "*") return true;
  }
  return false;
}
```

~20 lines of code, no dependency. Tested against the v0.2 fixture set.

**One-line rationale:** Refuse — comment round-trip is unsolved, silent
loss is unacceptable for a settings file.

### 5.3 Q3 — Batch atomicity model

**Question:** If a batch of 5 operations completes 3 then crashes:
(a) auto-rollback, (b) leave partial state for manual rollback, (c)
resume on next invocation?

**Proposed default: (b) Leave partial state.**

**Rationale:** See §3.4. This mirrors v0.2's `partialApply: true`
semantics. The user's recovery path is the same as v0.2's: `diagnose`
shows `housekeeper.interrupted_operation`, `nextStep` routes to
`rollback <id>`. We do not introduce a new model for batch failures.

The cost is that the user sees a "half-cleaned" home until they run
rollback. The benefit is that they don't lose successful work from a
batch where only one op failed — but only if they explicitly *don't*
roll back. If they DO roll back, they get the v0.2 contract: full
restore.

Option (a) is appealing for consistency but contradicts v0.2's deferred
decision. Option (c) is too complex for a v0.3 feature.

**One-line rationale:** Match v0.2's `partialApply` semantics — same
mental model, same recovery path, no contract drift.

### 5.4 Q4 — Per-detector harden eligibility

**Question:** Should each detector declare `hardenable: true/false` in
its raw output?

**Proposed default: Yes (the per-detector flag pattern from §4.2).**

**Rationale:** See §4.5. Detector co-location wins on ownership,
composability, and grep-ability. The alternative (a side table in
`harden-plan.mjs`) is the v0.2 pattern; we keep that for v0.2's
`CLEANABLE_DETECTORS_V02` but use the new pattern for v0.3's harden lane.

**One-line rationale:** Per-detector flags scale to v0.4+ surfaces;
side tables don't.

### 5.5 Q5 — Site / docs version-pinning automation

**Question:** v0.2 GA cut had to manually update `docs/index.html`'s
version pin. Should v0.3: (a) add a CI check, (b) replace the
hardcoded version with build-time substitution?

**Proposed default: (a) CI check.**

**Rationale:** Option (b) requires a build step for the docs site,
which we don't currently have — `docs/index.html` is a hand-edited
static file. Adding a build step is a much bigger change than the
problem warrants. A CI check (a simple grep that asserts
`docs/index.html` contains `package.json`'s `version`) catches the
exact failure mode we hit in v0.2 GA without introducing new tooling.

The check goes in `.github/workflows/ci.yml` as a one-line step:

```yaml
- name: Verify docs version pin
  run: |
    VERSION=$(node -p "require('./package.json').version")
    grep -q "v$VERSION" docs/index.html || \
      (echo "docs/index.html missing version $VERSION"; exit 1)
```

That's it. ~5 lines. No build pipeline.

**One-line rationale:** CI check is the smallest change that closes the
G4 gap — no new build step required.

### 5.6 Summary table for the tie-breaker

| Q | Architect proposal | Rationale (one line) |
|---|---|---|
| Q1 | Refuse `invalid_json` | Silent overwrite worse than forced manual fix |
| Q2 | Refuse JSONC in v0.3 | Comment round-trip unsolved; silent loss unacceptable |
| Q3 | Leave partial state | Match v0.2's `partialApply` — no new mental model |
| Q4 | Per-detector flag | Scales to v0.4+ surfaces; co-located with detector |

## 6. Risks not in the plan

The PLAN-v0.3 risk table is good but misses three things I caught while
reading the v0.2 code:

### 6.1 `applyOperation`'s drift loop reads ALL files before mutating ANY

`snapshot.mjs:544-550`:

```js
// Pre-apply drift check: verify all files before mutating any.
for (let i = 0; i < manifest.files.length; i++) {
  const entry = manifest.files[i];
  const currentHash = await hashFile(entry.originalPath);
  if (currentHash !== entry.sha256Before) {
    throw new SnapshotDriftError(...);
  }
}
```

For a batch of N operations, this means we hash all N files before
touching any. The per-file hash is cheap (sub-millisecond on settings,
maybe tens of ms on a plugin cache directory). But for the 10-op cap with
expanded files, this could be 50 files (the budget cap) × ~10 ms = 500 ms
of pre-apply hashing.

That's fine for interactive use. It's borderline for CI use. The G15
`--timeout` deadline (b4ad3bc) defaults to 30 seconds, which gives us
plenty of margin, but a future `--timeout=5` user could hit the pre-apply
hash loop and time out before any mutation runs.

**Mitigation:** add a `--timeout` interaction test that exercises a
near-budget batch and asserts we don't TLE on the pre-apply hash loop. If
we do, we lower `MAX_OPERATION_FILES` for batch (separate budget from
single-op).

### 6.2 `settings.json` is the most-watched file in `~/.claude`

Claude Code reads `settings.json` on every launch and may re-read on
SIGHUP or file-watcher events. v0.2's `dir-rmtree` against a plugin
cache directory never touches a Claude-watched file. v0.3's
`settings-rewrite` directly mutates one.

The atomic-write protocol (`atomicWrite` at `snapshot.mjs:215`) guarantees
Claude sees either the old or new content, never partial. **But** if
Claude re-reads on a file-watcher event, our atomic rename triggers that
event. Two failure modes to think about:

- **(a) Claude re-reads in the middle of our snapshot → apply window.**
  Claude reads the old content (snapshot already captured it). No
  problem.
- **(b) Claude re-reads immediately after our atomic rename.** Claude
  reads the new content. This is what we *want* — harden's whole point is
  to fix settings issues. The user should see the fix without restarting.

The risk is timing-sensitive failures we can't reproduce locally — e.g.
Claude is mid-init and reads a transient state. The platform memo will
research Claude's actual re-read semantics; this memo flags the surface
area.

**Mitigation:** harden's `nextStep` output (after a successful apply)
should suggest "consider reloading Claude Code in any active session"
just as clean's `RELOAD HINT` does today. The platform memo owns the
exact wording.

### 6.3 The 12-rule classifier's rule 4 is too strict for settings

`clean-plan.mjs:404`:

```js
// Rule 4: execution-class — surface executionClass !== "inert".
if (surface.executionClass && surface.executionClass !== "inert") {
  return { refuse: true, reason: "execution-class", ... };
}
```

`settings.json`'s surface, per `surface.mjs` (not read in detail, but
inferable from v0.2 behaviour), has `executionClass: "config-active"`
because settings *configure* runtime behaviour. That would route a
`settings-rewrite` finding straight into the `execution-class` refusal,
which is wrong — harden's whole job is to mutate config files.

**Mitigation:** the classifier needs a per-command-surface exception. The
simplest form:

```js
// Rule 4 (v0.3 amended):
if (command === "clean" && surface.executionClass !== "inert") return refuse;
if (command === "harden" && surface.executionClass !== "config-active" &&
                            surface.executionClass !== "inert") return refuse;
```

Or, more cleanly, the classifier takes an `allowedExecutionClasses` set
as input and the caller (clean vs. harden) supplies it. This is a small
refactor of the 12-rule classifier extraction (§2.1's "shared helper");
it must happen as part of T-200, not retrofitted later.

This is the most important risk in this section. If we don't address it
in compose, every harden invocation will refuse with `execution-class`
and v0.3 ships a no-op.

### 6.4 `gcSnapshots` may evict an in-flight v0.3 batch under contention

`snapshot.mjs:447-514` keeps the most recent 10 terminal manifests. A
v0.3 batch produces *one* manifest with N entries in `files[]`, so a
single batch still counts as one against the budget. But if a user runs
10 single-op cleans, then a harden, the harden's `gcSnapshots` call could
evict the 10 prior cleans' manifests. That's fine — they're terminal.

The risk: if any of those 10 prior manifests is NOT terminal (say, the
user ran a harden that hit a partial-apply and never rolled back), then
the manifest stays around indefinitely. Over many sessions, this
accumulates. v0.4 should consider a "stale interrupted operation"
cleanup (deferred).

**Mitigation:** this is a v0.4 concern. Document it in the v0.3
threat-model addendum (T-701) so we have a hook for v0.4 to grab.

### 6.5 The "ownership" rule 6 has a stale-lock exception that doesn't generalise

`clean-plan.mjs:426-435`:

```js
const housekeeperSelfCleanup =
  id === "housekeeper.stale_lock" && surface.ownerClass === "housekeeper-owned";
```

This is a single-detector special case. v0.3 doesn't add another
self-cleanup detector, so the exception doesn't need extension. But
v0.4 might (e.g. `housekeeper.snapshot_corrupted` could mutate the
snapshot tree). The pattern needs a clearer abstraction.

**Mitigation:** v0.3 stays with the single special case. We add a
comment in `clean-plan.mjs` noting that this is a known stop-gap, and
the v0.3 threat model addendum mentions "self-cleanup ownership
exceptions need a v0.4 abstraction."

## 11. Appendix — apply-order trace for one harden operation

For the synthesizer and reviewers, here's the literal call sequence for
a successful `harden --confirm --yes
--target=settings.hook_path_dangling --path=/Users/u/.claude/settings.json`:

```
A. CLI                                claude-housekeeper.mjs::runHarden(options)
B. compose                            harden-plan.mjs::composeHardenPlan(home, {target, path})
B1.   audit                             audit.mjs::assembleReport(home, {mode: "safe"})
B2.   policy                            policy.mjs::loadConfig(home)
B3.   classify                          clean-plan.mjs::classifyFinding(finding, ctx)
B4.   transform                         harden-plan.mjs::buildHookPathDanglingTransform(finding)
B5.   pre-validate                      JSON.parse(JSON.stringify(transform(currentSettings)))
B6.   pre-idempotency                   assert transform(transform(s)) === transform(s)
B7.   build CleanPlan                   { operations: [{mutationKind: "settings-rewrite", ...}], refused: [] }
C. validate                           harden-plan.mjs::validateHardenPlan(plan, home)
C1.   audit re-run                      audit.mjs::assembleReport(home, {mode: "safe"})
C2.   hash-equal                        hashReport(report) === plan.reportHash
C3.   policy re-check                   pathMatchesProtection for each op.targetPath
C4.   settings sha re-check             hashFile(plan.operations[0].targetPath) === plan.preApplySha
D. execute                            harden-plan.mjs::executeHardenPlan(plan, home)
D1.   acquire lock                      acquireLock(home) → <home>/housekeeper/lock created
D2.   gc                                snapshot.mjs::gcSnapshots(snapshotHome)
D3.   takeSnapshot                      snapshot.mjs::takeSnapshot(snapshotHome, {targets: [settings.json], command: "harden", mode: "confirm", consentSummary})
D3a.    budget check                      sum(stat.size) <= MAX_OPERATION_BYTES
D3b.    protected-path check              pathMatchesProtection per target
D3c.    hash + copy each target           atomicWrite snapshot files
D3d.    write meta.json                   atomicWrite
D3e.    write manifest                    atomicWrite operation manifest (status "snapshot_taken")
D4.   applyOperation                    snapshot.mjs::applyOperation(opId, snapshotHome, ops)
D4a.    drift check                       hashFile(settings.json) === sha256Before
D4b.    apply                             ops[0].apply(settings.json)
D4b.i     re-read                           readFile(settings.json)
D4b.ii    re-parse                          JSON.parse(raw)
D4b.iii   re-transform                      transform(parsed)
D4b.iv    re-validate                       JSON.stringify + JSON.parse round-trip
D4b.v     re-idempotency                    transform(parse(stringify(transform(parsed)))) === transform(parsed)
D4b.vi    atomicWrite                       write-temp + rename + fsync
D4c.    post-hash                         sha256After = hashFile(settings.json)
D4d.    set status                        status "applied", appliedAt = now
D5.   verify                            snapshot.mjs::verify(opId, snapshotHome)
D5a.    re-hash                           hashFile(settings.json) === sha256After
D5b.    set status                        status "verified", verifiedAt = now
D6.   release lock                      releaseLock(<home>/housekeeper/lock)
E. CLI render                         "DONE. Operation verified. Rollback id: op_<...>"
```

Every step from B to D6 is rollback-safe: if any step throws, the lock is
released (D6 is in a finally), and the manifest is left at the last
durable status. `housekeeper.interrupted_operation` will surface it on
the next diagnose, with `nextStep` routing to `rollback <opId>` or
`rollback <opId> --abort` depending on the status.

deferred (CLI wording, Claude-Code re-read semantics, the JSONC library
survey, the compatibility matrix). The architecture *itself* is
buildable from this memo plus the v0.2 code already in `main`.

The four load-bearing decisions are restated for the tie-breaker:

1. `settings-rewrite` is a fifth mutation kind, not a variant of
   `file-replace`.
2. `composeHardenPlan` is a peer to `composeCleanPlan` in its own
   module; both share the 12-rule classifier as a helper.
3. `clean --batch` is a parser-and-orchestrator change, not a new
   mutation kind.
4. Detector promotion is a per-detector `hardenable`/`cleanable` flag,
   not a side table.

All five Open Design Questions have proposed defaults (§5). Three risks
not in the plan are flagged (§6). The tie-breaker has authority to
reverse any of the above; the architect's role is to put the strongest
possible case on the table.
