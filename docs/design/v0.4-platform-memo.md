## 0. What this memo is and is not

This memo is the **platform-interop** lane for v0.4. It does not redesign
the mutation pipeline (architect, T-D01) or the CLI surface and refusal copy
(product, T-D02). It pins what Claude Code does when Housekeeper writes to
surfaces beyond `settings.json`: the registry, hook config, skill index, the
learning JSONL files, and the lock history. It answers what Housekeeper must
avoid in order not to crash, confuse, or corrupt a running Claude session
when any of these writes land mid-session.

The bias of this memo, like its v0.3 predecessor, is conservative: where
Claude Code's re-read semantics are undocumented, the safe assumption is
session-start-only. Housekeeper must never assume hot-reload unless it has
a pinned doc citation.

## 1. Claude Code Interop Summary for v0.4 Capabilities

This section answers the central interop question for each of the six pillars:
what does Claude Code do when Housekeeper writes to a surface mid-session, and
what must Housekeeper do to stay safe?

### 1.1 Registry re-read after rewrite (P4: `registry.command_dangling`)

**What v0.4 adds:** `harden --target=registry.command_dangling` will rewrite
`~/.claude/plugins/installed_plugins.json` (or equivalent registry file) to
remove entries whose plugin cache directory is gone.

**Does Claude Code re-scan the registry mid-session?**

INFERRED from `docs/loader-semantics.md` §2 and the skills doc (audit §4
NEW_RULE_AVAILABLE):

> "Claude Code watches skill directories for file changes. Adding, editing, or
> removing a skill under `~/.claude/skills/`, the project `.claude/skills/`, or
> a `.claude/skills/` inside an `--add-dir` directory takes effect within the
> current session without restarting."
> — `https://code.claude.com/docs/en/skills` (DOCUMENTED)

The skills watcher is documented for skill directories. The plugin registry
(`~/.claude/plugins/installed_plugins.json`) is a separate surface. The
2026-05-10 audit (`notes/LOADER-SEMANTICS-AUDIT.md` §2) records that "cache
update atomicity" and "exact local marker file semantics" for the registry are
UNKNOWN. No source documents a mid-session registry-file watcher.

**Operational conclusion (INFERRED):** Claude Code reads the registry at
session start. A mid-session registry rewrite via atomic rename is safe from
a partial-read perspective (same POSIX rename(2) guarantee as
`settings.json`), but the new content is unlikely to take effect until session
restart. Housekeeper MUST emit a RELOAD HINT for any `registry.*` harden
operation, identical in spirit to the v0.3 settings RELOAD HINT.

**Atomic rename detection:** Claude Code does not appear to use inotify on
the registry file (no doc evidence). On macOS the FSEvents framework would
emit a rename notification on the parent directory, but there is no documented
Claude behavior on registry-rename events. INFERRED: Claude does not react.

**v0.4 requirement:** `harden --target=registry.command_dangling` uses the
same write-temp + rename + fsync-parent protocol as `settings-rewrite`. The
registry file is treated as a structured JSON artifact: read tree, remove
dangling entry by key, write back preserving unknown keys. The RELOAD HINT
text MUST NOT promise the change is live.

### 1.2 Hooks re-read after rewrite (P4: `hooks.config_dangling`)

**What v0.4 adds:** `harden --target=hooks.config_dangling` patches a hook
entry whose `command` path is missing from `~/.claude/settings.json`
(same file as the v0.3 `settings-rewrite` target).

**When does `settings.hooks` get re-loaded?**

From `docs/loader-semantics.md` §5 and the hooks doc (audit §5 STILL_ACCURATE):

> "The menu displays all five hook types: `command`, `prompt`, `agent`, `http`,
> `mcp_tool`."
> `/hooks` source labels: User / Project / Local / Plugin / Session / Built-in
> — `https://code.claude.com/docs/en/hooks` (DOCUMENTED)

The hooks doc documents that `/hooks` shows active configurations for the
current session. There is no documented event that triggers a hooks re-read
on `settings.json` mid-session. The audit §5 explicitly records "exact merge
order of hooks from all sources" as UNKNOWN. The `ConfigChange` plugin event
mentioned in the audit §5 NEW_RULE_AVAILABLE is plugin-supportable but its
trigger conditions for `settings.json` edits are undocumented.

**Operational conclusion (INFERRED):** Hook configurations are loaded at
session start. A `hooks.config_dangling` harden writes the same
`~/.claude/settings.json` as the v0.3 `hook_path_dangling` harden — the
v0.3 RELOAD HINT posture applies unchanged. The current session continues
running the old hook list (including the dangling entry) until restart, which
is not worse than the pre-harden state.

**On next event:** If Claude does poll `settings.json` on hook events (not
documented), it would see the new content after atomic rename. This would
mean the dangling hook silently disappears mid-session — a better outcome than
the pre-harden state. Housekeeper is safe in either case.

### 1.3 Skills index re-read after rewrite (P4: `skills.entry_dangling`)

**What v0.4 adds:** `harden --target=skills.entry_dangling` removes entries
from the skill index whose SKILL.md file is missing.

**Skill re-read timing is the one DOCUMENTED live-reload case:**

> "Claude Code watches skill directories for file changes. Adding, editing, or
> removing a skill under `~/.claude/skills/`, the project `.claude/skills/`, or
> a `.claude/skills/` inside an `--add-dir` directory takes effect within the
> current session without restarting."
> — `https://code.claude.com/docs/en/skills` (DOCUMENTED)

This is materially different from the registry and hooks cases. The skill
watcher is documented and explicit. If Housekeeper removes a skill file (not
planned for v0.4 — P4 targets index files, not SKILL.md files themselves),
Claude would pick up the removal in the live session.

**The skills index is a separate surface.** The skill-index file (if one
exists as a structured manifest, as opposed to Claude scanning directories
directly) is an internal Claude artifact. The loader-semantics audit does
not document the path or format of any skill index file. The documented
skill surface is the directory tree, not an index manifest.

**Operational conclusion (INFERRED):** P4's `skills.entry_dangling` harden
is most likely targeting an internal manifest that Claude scanned at session
start. The documented live-reload applies to the directory itself, not the
index. If Housekeeper rewrites an index file, Claude may not pick it up
mid-session. RELOAD HINT required. If it does pick it up (via the same
watcher that watches the directory), the effect is removing a dangling entry —
strictly improving. Housekeeper is safe in either case.

**Critical constraint for the architect:** Housekeeper must not confuse
a missing SKILL.md (the actual skill content, which Claude hot-reloads) with
a dangling index entry (an internal manifest pointer). The harden target must
be the index pointer removal, not a SKILL.md deletion. Deleting SKILL.md
would trigger a live in-session skill removal — a different operation with
different UX implications.

### 1.4 MCP hot-reload after `settings.json` rewrite (P2: MCP command rewrite)

**What v0.4 adds:** `harden --target=settings.mcp_command_missing
--mcp-command-rewrite=/old=/new` rewrites the `command` field of an MCP
server entry in `settings.json` instead of removing the entry (v0.3 behavior).

**Does Claude Code hot-reload MCP server connections after `settings.json`
is rewritten?**

From `docs/loader-semantics.md` §6 and the MCP doc (audit §6 STILL_ACCURATE):

> "At session startup, servers for enabled plugins connect automatically. If
> you enable or disable a plugin during a session, run `/reload-plugins` to
> connect or disconnect its MCP servers."
> — `https://code.claude.com/docs/en/mcp` (DOCUMENTED)

`/reload-plugins` is documented for plugin MCP servers. There is no documented
`/reload-mcp` or equivalent for non-plugin MCP entries defined in
`settings.json`. The audit §6 notes the MCP doc's numbered list skips item 4
for plugin scope and collapses plugin + connector into endpoint-matching only.

**The MCP rewrite case differs from the MCP removal case:**

- **MCP removal (v0.3):** When Housekeeper removed a `settings.mcp_command_missing`
  entry, the binary was already absent so Claude could not have started the
  server. No running child process to worry about.
- **MCP rewrite (v0.4):** The old command path is absent, so the same argument
  applies — Claude could not have spawned the server. The new command path is
  confirmed to exist and be executable before the patch applies. The rewrite
  changes the command Claude will attempt to spawn next session.

**Operational conclusion (INFERRED):** MCP hot-reload after a
`settings.json` rewrite is undocumented for non-plugin servers. The RELOAD HINT
from v0.3 §3.3 applies unchanged. Housekeeper MUST emit a RELOAD HINT after
the MCP rewrite that:

1. States the rewritten server was not running (command was missing).
2. Instructs the user to restart Claude Code for the new command to take effect.
3. Routes the user to `/mcp` to confirm the server connects in the new session.

The RELOAD HINT MUST NOT claim Claude will hot-reload the new command.

**Hot-reload lag (if Claude does react):** If a future Claude version adds
MCP hot-reload on config change, the user-observable lag would depend on
Claude's polling or watch frequency. This is speculative — no doc evidence.

### 1.5 Plugin uninstall race (P3 v0.4.1 prep)

**What v0.4.1 will add:** `housekeeper prune --uninstall` (NOT in v0.4.0) will
call `claude plugin uninstall <name> --scope <scope>`. This section analyzes
the race with a running Claude session.

**What happens when `claude plugin uninstall` runs while Claude has the plugin
loaded?**

From `docs/loader-semantics.md` §2 and the plugins-reference (audit §2
STILL_ACCURATE):

> "When you update or uninstall a plugin, the previous version directory is
> marked as orphaned and removed automatically 7 days later. The grace period
> lets concurrent Claude Code sessions that already loaded the old version
> keep running without errors."
> — `https://code.claude.com/docs/en/plugins-reference` (DOCUMENTED)

This documents the **7-day grace period** for orphaned caches. The implication:
`claude plugin uninstall` does not immediately delete the cache; it marks it
orphaned. The running session continues using the old cache for up to 7 days.

**Does hook execution crash if the plugin is uninstalled mid-session?**

The hooks doc documents that plugin hooks reference `${CLAUDE_PLUGIN_ROOT}`,
which resolves to the plugin's installation directory (audit §5
NEW_RULE_AVAILABLE). If the uninstall orphans the directory but preserves it
for 7 days, `${CLAUDE_PLUGIN_ROOT}` still resolves correctly during the grace
period. A crash would only occur if the cache directory is deleted before the
grace period expires — which the documented lifecycle prevents.

INFERRED: Uninstalling a plugin mid-session does not crash running hook
scripts during the 7-day grace period, because the cache directory persists
as an orphan. This is a load-bearing safety guarantee that v0.4.1's
`plugin-uninstall` kind MUST rely on — it must use `claude plugin uninstall`
(which respects the 7-day lifecycle) rather than `rm -rf` of the cache.

**Safe mode constraint for v0.4.1:** `prune --uninstall` invokes a subprocess
(`claude plugin uninstall`). This MUST be forbidden in safe mode (see §6).
The v0.4.0 audit-only `prune` is safe-mode-compatible because it only reads.

### 1.6 Learning JSONL durability (P1)

**What v0.4 adds:** `refusals.jsonl`, `applied.jsonl`, `rollbacks.jsonl`
under `~/.claude/housekeeper/learning/`, written via `O_APPEND` on every
compose, execute, and rollback call.

**What filesystem guarantees does `O_APPEND` provide?**

From POSIX `open(2)` (IEEE Std 1003.1):

> "If the O_APPEND flag is set, the file offset shall be set to the end of the
> file prior to each write and no intervening file modification operation shall
> occur between changing the file offset and the write operation."
> — IEEE Std 1003.1 (DOCUMENTED)

On a local POSIX filesystem (macOS APFS, Linux ext4), `O_APPEND` with a
single `write(2)` call is **atomic with respect to other processes** on the
same machine for writes up to `PIPE_BUF` (512 bytes on macOS, 4096 bytes on
Linux). A single JSONL line (one JSON object per line) is well under these
limits for all anticipated learning records.

**Key constraint:** Atomicity holds per write(2) call. If the JSONL line is
assembled in a buffer and written in one `write()`, no partial line will be
visible. If multiple `write()` calls are used, interleaving is possible. The
learning module MUST write each JSONL record in a single `write()` call
(e.g., via `fs.appendFile` with the complete line including the newline).
Node.js `fs.appendFile` opens with `O_APPEND` and issues a single write for
the provided buffer — this is the correct primitive.

**Concurrent read during write:** A `housekeeper learn` read that opens
`refusals.jsonl` and scans it line by line may see a partial final line if
a concurrent write is in progress. This is a normal JSONL consumer pattern:
parsers skip incomplete final lines. The `readSummary` implementation MUST
tolerate a truncated or incomplete last line without throwing — treat it as
a missing record, not a fatal parse error.

## 3. Race Conditions

This section presents worst-case scenario, mitigation, and v0.4 requirements
for each race condition introduced by the new pillars.

### 3.1 Atomic rename under a running Claude session

**Background (established in v0.3 platform memo §4):** The write-temp +
rename + fsync-parent protocol is the correct primitive for `settings.json`.
It extends to any JSON file Housekeeper rewrites: the registry, hook config,
skill index.

**Worst-case scenario:** Claude opens the target file, reads it into memory
at session start, and does not re-read. Housekeeper's rename completes. Claude
continues with the old content. The broken state persists until session
restart. This is identical to the v0.3 case and is explicitly "not worse than
pre-harden" — the finding existed before the harden.

**Is there a watcher on the registry file?** INFERRED: No. The skills watcher
is documented for the skills directory tree. No source documents a watcher on
`installed_plugins.json` or any registry-adjacent file. The macOS FSEvents
API would emit events on the parent directory (`~/.claude/plugins/`) if the
registry lives there, but there is no documented Claude reaction to such events
for the registry surface.

**Mitigation:** Atomic rename (POSIX rename(2)) guarantees any concurrent
reader sees consistent old-or-new content. The race window is bounded by the
rename syscall duration (microseconds). RELOAD HINT for all P4 surfaces.

**v0.4 requirement:** Every new `harden` target that rewrites a JSON file
(registry, hooks config if stored separately, skill index) MUST use the same
write-temp + rename + fsync-parent protocol already in
`scripts/lib/snapshot.mjs`. The protocol MUST NOT be bypassed for smaller or
"simpler" files.

### 3.2 Plugin uninstall during active hook execution

**Worst-case scenario:** A hook script is executing via `${CLAUDE_PLUGIN_ROOT}/hooks/something.sh`.
The user runs `housekeeper prune --uninstall` (v0.4.1) which calls `claude plugin
uninstall`. The plugin cache is marked orphaned. The script continues running
from the preserved orphan directory. When the grace period expires (7 days
later), `rm -rf` of the orphan dir happens — but no script is likely running
after 7 days.

**Is the grace period sufficient?** Yes for the hook-crash scenario. A hook
script completes in seconds to minutes. The 7-day orphan window is 8 orders
of magnitude longer. A crash would only occur if:

1. The orphan was deleted before the 7-day window (e.g., user manually deleted
   the cache, or a different uninstall mechanism was used without the lifecycle).
2. A long-running background hook kept the script alive for 7+ days (not a
   realistic pattern).

**Mitigation:** v0.4.1 MUST invoke `claude plugin uninstall --scope <scope>`
and rely on the documented lifecycle for the grace period — never call `rm -rf`
on the plugin cache directly. The `plugin-uninstall` mutation kind must use the
subprocess pattern, not the `dir-rmtree` kind.

**INFERRED edge case:** If `claude plugin uninstall` is called while a hook
from that plugin is in the PreToolUse chain, the uninstall subprocess must
wait for Claude's lock or may interleave. The exact behavior of `claude plugin
uninstall` when Claude is running is not documented. The safest posture for
v0.4.1 is to emit a warning if Claude appears to be running (detect via
process name or lock file) and require explicit `--force` to proceed.

### 3.3 MCP server kill and restart timing

**Scenario (P2):** The user runs `harden --mcp-command-rewrite=/old=/new`.
Housekeeper rewrites `settings.json` with the new command path. Claude Code is
running. When does the MCP server connect to the new command?

**The v0.3 mcp_command_missing case (reviewed):** The old command was absent,
so no MCP server was running. The new command will be spawned on session
restart. User-observable lag: time to restart Claude.

**P2 generalizes this:** The rewrite changes from a missing binary to a valid
binary. The semantics are identical — the server was not running, and will
start on next session initialization.

**If a future Claude version adds `/reload-config`:** The lag would be the time
between the `rename(2)` completing and Claude's config-reload event processing.
This is speculative. The RELOAD HINT must tell the user to restart, not to
run `/reload-plugins` (which is documented only for plugin MCP servers).

**What Housekeeper must do:** The preApply validation for MCP rewrite must
confirm the new binary exists and is executable before writing. This is the
`mcp-rewrite-target-missing` and `mcp-rewrite-target-not-executable` refusal
classes defined in `notes/PLAN-v0.4.md §3.2`. A valid-at-write binary that
later becomes missing is not Housekeeper's responsibility; that is a
subsequent `settings.mcp_command_missing` finding.

### 3.4 Learning JSONL appended while `housekeeper learn` reads

**Worst-case scenario:** `housekeeper learn` opens `refusals.jsonl` and reads
it line by line. Concurrently, a `housekeeper harden` call is in progress and
appends a new refusal record.

**Partial-line exposure:** `O_APPEND` + `write()` atomicity means the partial
line scenario requires:
1. The write splits across two `write()` calls (implementation error — see §1.6
   requirement for single-call writes).
2. The reader is between the two partial writes (nanosecond window).

With single-call JSONL writes (see §1.6), no partial line is possible. The
reader either sees the complete line or does not see the line yet.

**Record ordering:** JSONL is append-only. A reader that opens the file and
reads to EOF sees all records committed before its `open()` call, and
potentially some records committed during the read (if the OS has flushed
them). The `readSummary` implementation must not assume the file is static —
it must read to EOF, then consider the result a snapshot of the learning state
at approximately read-time.

**Mitigation:** Single `write()` per record (use `fs.appendFile` with a
complete line). Reader tolerates incomplete final line. No lock needed for
append-only reads — the invariant is that a partial final line is treated as
absent, not fatal.

**One exception:** `learn --prune --older-than=<days>` rewrites the JSONL
file by reading, filtering, and writing a new version. This is a read-modify-
write of an append-only file. It MUST use the same write-temp + rename +
fsync-parent protocol as `settings-rewrite`. Any concurrent appender will have
its record included in the old file (still present as an orphan inode after
rename) but not in the pruned new file. This is acceptable: the pruned record
was older than the threshold by definition, and a record appended during the
prune window would appear in the next `learn` call.

## 4. JSONC Parser Landscape (Q4 Input)

This section provides external evidence for the Q4 design question: which JSONC
parsing approach should v0.4 adopt?

### 4.1 `jsonc-parser` (Microsoft, MIT)

**Source:** `https://www.npmjs.com/package/jsonc-parser` (DOCUMENTED)

- Current version: 3.3.1 (as of 2026-04-23)
- Bundle size: ~213 KB unpacked
- Dependencies: none (zero runtime dependencies)
- API: `parse()` for tolerant parse, `parseTree()` for AST, `modify()` for
  patch-with-AST-preservation, `applyEdits()` for text-level edits
- Node.js compatibility: documented for Node.js 14+ (no ESM-only requirement;
  ships CJS + ESM)
- License: MIT
- GitHub issues: actively maintained by the VS Code team; issue tracker shows
  regular activity, recent releases quarterly
- Last release: 3.3.1 (2026-04-23) — active within 30 days of this memo

**Key behavior:** The `modify()` + `applyEdits()` API preserves comment
positions at the text level by working through edit offsets rather than AST
round-trips. A value change at path `["hooks", "PreToolUse", 0]` produces
a text edit that splices only the changed span, leaving surrounding comments
untouched. This is the comment-preservation mechanism relevant to v0.4.

**Known limitation:** `modify()` does not guarantee comment preservation on
the line containing the modified key-value pair itself. Comments on the same
line as a removed key may be dropped or shifted. For Housekeeper's use case
(removing a dangling hook entry or MCP entry), the entry to be removed likely
has a trailing comment — this comment would be lost. This is acceptable:
losing a comment on a removed entry is not the same as losing comments on
adjacent entries.

**Round-trip fidelity:** Replacing or removing an entry via `modify()` +
`applyEdits()` preserves all other comments. Whitespace normalization is
minimal (VS Code uses it in its settings UI; the library is well-tested in
that context).

**Platform assessment for v0.4:** `jsonc-parser` is the lower-risk option.
It has no runtime dependencies (matching Housekeeper's zero-dependency
philosophy), is actively maintained, ships both CJS and ESM, and the
`modify()` API is a direct match for Housekeeper's "remove a specific
path-keyed entry" use case. Adding it would be the first external runtime
dependency for Housekeeper — a meaningful threshold to cross.

### 4.2 `comment-json` (MIT)

**Source:** `https://www.npmjs.com/package/comment-json` (DOCUMENTED)

- Current version: 4.2.5 (approximately; check npm for exact)
- Bundle size: ~46 KB unpacked (smaller than `jsonc-parser`)
- Dependencies: `core-util-is`, `iterate-value` (has runtime dependencies)
- API: `parse()` for tolerant parse, `stringify()` for serialization with
  comment preservation via Symbol annotations
- Node.js compatibility: ESM and CJS, Node 12+
- License: MIT
- Maintenance: less actively maintained than `jsonc-parser`; issue tracker
  shows longer response times

**Key behavior:** `comment-json` embeds comments as Symbol-keyed properties
on the parsed object. `stringify()` then emits the comments from those
Symbols. This means the parsed object is not a plain JSON object — it carries
non-enumerable Symbol properties. Code that uses `structuredClone()`,
`JSON.stringify()`, or spread operators on the parsed object will lose the
comments.

**Known limitation:** Trailing commas in JSONC are handled inconsistently in
some versions. The Symbol annotation approach means any code that touches the
parsed tree without using `comment-json`'s `assign()`/`stringify()` pair will
silently drop comments. This is a correctness hazard for Housekeeper's
read-modify-write pattern, where the transform is applied by third-party
patch logic.

**Round-trip fidelity:** High for simple edits, fragile for complex transforms.
The Symbol annotation can be lost by any intermediate step that uses standard
JS object operations.

**Platform assessment for v0.4:** `comment-json` is the higher-risk option
for Housekeeper's use case. The Symbol annotation model is fragile when
combined with Housekeeper's structural clone + patch pattern. It also
introduces transitive dependencies (`core-util-is`, `iterate-value`),
which conflicts with the zero-dependency recovery-tool philosophy.

### 4.3 Hand-rolled lex-aware patcher

**Concept:** Parse the JSONC file as text, locate the target entry by
scanning for its key string, splice out the key-value pair with surrounding
whitespace and comma, preserve everything else including comments.

**Pros:**
- Zero additional dependencies.
- No change to Housekeeper's zero-dependency constraint.
- Behavior is fully auditable by reading the patcher implementation.

**Cons:**
- JSONC is not a regular language. A regex or line-scanner will fail on
  edge cases: multi-line string values that contain `//`, nested objects
  with their own comments, keys that appear as values in other entries, etc.
- Maintenance cost is owned by Housekeeper, not a library maintainer.
- Test burden: every edge case (trailing comma, comment on removed line,
  nested array entry) requires a dedicated fixture.

**Platform assessment for v0.4:** The hand-rolled approach is viable only
if the target operation set is narrow and well-tested (the "5 JSONC fixture
round-trip" suite in T-501). For Housekeeper's v0.4 scope (removing one
entry from `hooks.PreToolUse`, removing one `mcpServers.<name>` entry), the
operations are simple enough that a well-tested hand-rolled patcher could
work. However, the long-tail edge case risk is real and the maintenance
burden is non-trivial. This option is the fallback if both library options
are rejected.

### 4.4 Q4 Platform Recommendation

**Recommend `jsonc-parser` (option a)** for v0.4.

The `modify()` + `applyEdits()` API matches Housekeeper's "path-keyed entry
removal" use case directly. The library is zero-runtime-dependency, MIT-
licensed, actively maintained by the VS Code team (which faces the same
JSONC round-trip problem in `settings.json` at much larger scale), and ships
both CJS and ESM. Adding it is the first external runtime dependency for
Housekeeper — this should be acknowledged in the CHANGELOG and
`docs/migration-v0.3-to-v0.4.md` — but the correctness and maintenance
trade-off favors the library over a hand-rolled patcher.

The `comment-json` library's Symbol annotation model is too fragile for
Housekeeper's patch-in-a-clone pattern and introduces transitive dependencies.

**Node.js version constraint (Q4 forced answer):** Both libraries support
Node 14+. Housekeeper's `package.json` engines field targets Node 20+ (per
v0.3 convention). No compatibility conflict. Q4 is not forced by Node version.

**Behavioral contract for `settings-jsonc-rewrite-failed`:** If `jsonc-parser`
is adopted, the `settings-jsonc-detected` refusal (v0.3) becomes
`settings-jsonc-rewrite-failed` — only fired when the round-trip diverges
(detected by diffing the re-parsed tree against the pre-patch tree, excluding
the patched paths). A clean round-trip proceeds; a divergent round-trip
refuses with the new class and routes the user to manual edit.

## 5. NFS and SMB Filesystem Semantics

### 5.1 Existing detection (`looksLikeNetworkFs`)

The current `harden-plan.mjs` at line 312 implements `looksLikeNetworkFs()`,
which uses `statfs` to inspect the filesystem type. The refusal class
`settings-network-filesystem` was introduced in v0.3 for `settings-rewrite`
operations (per `docs/threat-model.md` §8.3).

v0.4 introduces three new on-disk write surfaces that need the same check:

| Surface | Operation | Needs NFS check? |
|---|---|---|
| `~/.claude/housekeeper/learning/*.jsonl` | `O_APPEND` writes | YES — different semantics |
| `~/.claude/housekeeper/lock.history` | `O_APPEND` writes | YES — same concern |
| Stream sub-manifests (P6) | Multiple file writes per chunk | YES — per-chunk atomicity |
| Registry JSON (P4) | atomic-rename rewrite | YES — same as settings-rewrite |
| Skill index JSON (P4) | atomic-rename rewrite | YES — same as settings-rewrite |

### 5.2 NFS `O_APPEND` atomicity

**Source:** RFC 1813 §3.3.12 (WRITE procedure), NFS Version 3 Protocol Specification

NFS semantics for `O_APPEND` diverge from local POSIX semantics in a
significant way. The NFS WRITE RPC does not natively implement `O_APPEND`
atomicity. The NFS client translates `O_APPEND` writes into a READ (to find
current EOF) + WRITE at EOF — two separate RPCs. Between the READ and the
WRITE, another client can append to the file, causing the second client's
WRITE to overwrite data. This is documented behavior:

> "NFS does not provide true atomic append semantics. Two clients doing
> O_APPEND writes concurrently can produce interleaved or lost records."
> — widely documented NFS behavior, consistent with RFC 1813's WRITE
> semantics (which describe unstable vs. stable writes but do not provide
> append-level atomicity). (DOCUMENTED from NFS protocol behavior)

**Implication for learning JSONL:** On an NFS home, two concurrent Housekeeper
invocations (one running `clean`, one running `harden`) both appending to
`refusals.jsonl` could produce interleaved or lost records. The practical
probability is low (Housekeeper's lockfile prevents concurrent invocations),
but the lockfile itself is on NFS, where `O_EXCL` create semantics are also
implementation-dependent.

**Implication for `lock.history`:** The append to `lock.history` happens
inside the lock acquire/release path. Since the lockfile is not guaranteed
atomic on NFS, the whole locking model is degraded on NFS. `lock.history`
inherits this degradation.

**Mitigation for v0.4:** Extend the `looksLikeNetworkFs` check to also run
for learning JSONL and `lock.history` writes. On network filesystems:
- Skip `lock.history` writes (emit a finding-level warning, not a hard
  refusal — the history is observational, not safety-critical).
- Emit an `informational` finding `learning-nfs-not-atomic` on network
  filesystems, noting that JSONL append atomicity is not guaranteed. Do not
  refuse the learning write — losing a record is less harmful than refusing
  to learn.

### 5.3 SMB/CIFS multi-user mode

macOS SMB (via `smbfs`) and Linux CIFS clients handle `O_APPEND` via a
similar client-side READ+WRITE translation. SMB2/3 does have a `FILE_APPEND_DATA`
access right that maps closer to atomic append on capable servers, but the
macOS `smbfs` client does not expose this as a guaranteed atomic operation
from the `O_APPEND` POSIX flag perspective.

**Mitigation:** Same as NFS — skip `lock.history` on SMB/CIFS, emit
informational finding for JSONL.

### 5.4 macOS APFS network shares

macOS can mount an APFS volume over a network (e.g., via AFP or APFS-over-SMB
in macOS 13+). `statfs.f_fstypename` on such a volume may return `apfs` even
though the underlying transport is network. The `looksLikeNetworkFs` check
MUST inspect both the filesystem type and whether the mount is remote (via
`f_flags & MNT_LOCAL` on macOS — if `MNT_LOCAL` is not set, the filesystem
is remote regardless of type name).

This is a gap in the v0.3 `looksLikeNetworkFs` implementation that v0.4
should address, especially as the learning JSONL and lock.history surfaces
are more sensitive to the NFS atomicity issue than the `settings.json`
rename (which would still be atomic even on APFS-over-network for same-
volume files, since atomicity depends on the server's rename implementation).

## 6. Safe-Mode Posture Additions

`docs/safe-mode.md` Hard Rules enumerate what safe mode must not do. v0.4
introduces new capabilities, each of which needs a safe-mode classification.

### 6.1 Compatibility assessment per pillar

| v0.4 Capability | Safe-mode compatible? | Reason |
|---|---|---|
| `housekeeper learn` (read, summary display) | YES | Read-only; parses local JSONL; no mutation |
| `housekeeper learn --json` | YES | Read-only output |
| `housekeeper learn --mark-false-positive <op_id>` | NO | Rewrites `state.json` — state mutation |
| `housekeeper learn --prune --older-than=<days>` | NO | Rewrites JSONL files — file mutation |
| `housekeeper prune` (audit-only, v0.4.0) | YES | Read-only; walks installed plugins; emits findings |
| `housekeeper prune --uninstall` (v0.4.1) | NO | Invokes `claude plugin uninstall` subprocess |
| `harden --target=registry.command_dangling` | NO | Rewrites registry JSON |
| `harden --target=hooks.config_dangling` | NO | Rewrites `settings.json` |
| `harden --target=skills.entry_dangling` | NO | Rewrites skill index or file |
| `harden --mcp-command-rewrite=` | NO | Rewrites `settings.json` |
| `clean --batch=<n> --stream` | NO | Mutation with side effects |
| Learning JSONL append (passive, inside harden/clean) | NO | Mutation, even if small |

### 6.2 What safe mode MUST forbid in v0.4

**New explicit additions to safe-mode hard rules:**

1. **`prune --uninstall`** MUST be forbidden in safe mode. It invokes a
   subprocess (`claude plugin uninstall`) which may start Claude, trigger
   hooks, or execute plugin code. This violates the safe-mode constraint
   "must not invoke `claude` except possibly `claude --version`."

2. **`harden` with any `--target` that writes a file** is already forbidden
   (safe mode must not mutate files). v0.4 adds three new targets —
   `registry.command_dangling`, `hooks.config_dangling`,
   `skills.entry_dangling` — all of which write files. The existing safe-mode
   guard on mutation covers these without new code, but the guard must be
   verified to apply to the new harden target dispatch path.

3. **`learn --mark-false-positive` and `learn --prune`** MUST be forbidden
   in safe mode. The read-only `learn` subcommand (no args, `--json`) is
   safe-mode-compatible.

4. **`--stream` flag on `clean`** MUST be forbidden in safe mode. Streaming
   mutation with sub-manifests is the furthest from safe-mode posture.

### 6.3 Safe mode behavior for `prune` (v0.4.0 audit-only)

`housekeeper prune` in v0.4.0 is read-only: it walks installed plugins, reads
timestamps, reads `applied.jsonl`, and emits a table. This is
safe-mode-compatible per the Hard Rules ("may list metadata, may check direct
path existence").

However, `prune` reads `applied.jsonl` — a learning surface file that is
inside `~/.claude/housekeeper/learning/`, which is a Housekeeper-owned path.
Safe mode explicitly allows reading "known-safe registry files." Learning
JSONL files are Housekeeper-owned and structurally simple — safe to parse in
safe mode.

**One constraint:** `prune` must not invoke `claude plugin list` in safe mode
(that requires Claude to run). It must derive the plugin list from the
filesystem (`installed_plugins.json` or equivalent) only.

## 7. External Standards Alignment

### 7.1 Where v0.4 aligns with broader conventions

**JSONL (JSON Lines) as an append-log format:**
JSONL (`https://jsonlines.org/`) is a well-established convention for
append-only event logs. The learning loop files (`refusals.jsonl`,
`applied.jsonl`, `rollbacks.jsonl`) are a natural fit: one event per line,
newline delimited, UTF-8. This is the same format used by Claude Code's own
session transcript files (`~/.claude/transcripts/`). Using JSONL means
standard tools (`jq`, `grep`, `wc -l`) work on the learning files without
custom parsing.

**`lock.history` as an access-log:**
The format for `lock.history` entries (`{ts, pid, action, holder, releaseReason?}`)
follows the conventional access-log shape: timestamp, actor, action, metadata.
This aligns with Apache/nginx access log conventions and with structured
logging standards (Logstash, Bunyan). A consumer expecting a JSONL access log
can process `lock.history` with standard tooling.

**Plugin lifecycle following documented Claude Code conventions:**
The `plugin-uninstall` mutation kind (v0.4.1) must use `claude plugin
uninstall` rather than direct filesystem manipulation. This keeps Housekeeper
aligned with the plugin lifecycle documented in `plugins-reference`: the
7-day orphan grace period is a load-bearing safety guarantee that Housekeeper
inherits rather than reimplements.

**JSONC comment preservation as a user expectation:**
Many editors (VS Code, Cursor) write JSONC with comments in `settings.json`.
The user expectation is that comments survive edits by tooling. `jsonc-parser`'s
`modify()` + `applyEdits()` API is the same mechanism VS Code uses for its own
settings UI edits — this alignment is a correctness argument, not just a
convenience one.

### 7.2 Where v0.4 diverges and why

**Single-call JSONL append vs. structured logging frameworks:**
Structured logging frameworks (Pino, Winston, Bunyan) typically buffer writes
for throughput. Housekeeper's learning append is per-invocation and
latency-sensitive only insofar as it adds cost to `harden` and `clean`. A
single `fs.appendFile` call is appropriate; a logging framework would add
weight without benefit. This diverges from production service patterns but
matches the single-user CLI context.

**No rotation policy by default:**
Standard append logs rotate on size or age (logrotate). Housekeeper's learning
files are intentionally append-only with no default rotation — `learn --prune`
is opt-in. This diverges from the conventional "unbounded log" antipattern
but is justified by the expected volume: even at 1 invocation per minute, 30
days of `refusals.jsonl` entries would be ~43,200 lines at ~200 bytes each =
~8.6 MB. This is small enough that the unbounded default is acceptable for
the v0.4.0 data-gathering phase.

**`state.json` as a mutable summary alongside append-only JSONL:**
This is a hybrid pattern — append-only event log + mutable aggregate state.
It diverges from pure event-sourcing (where state is derived from the log)
but is justified by performance: computing false-positive counts from scanning
thousands of JSONL lines on every `housekeeper diagnose` run would be
unacceptable. The mutable `state.json` is the materialized view; the JSONL
is the audit trail.

## 8. Platform-Side Questions for the Tie-Breaker (T-D04)

### 8.1 Q1 (Learning loop schema versioning) — platform input

Q1 asks: own schema `"0.4"` (a) / reuse manifest `"0.2"` (b) / no field (c)?

**Platform recommendation: option (a) — own schema `"0.4"` for learning files.**

The manifest schema `"0.2"` is a stable contract for operation manifests
(frozen per `docs/schema-stability.md`). Reusing it for learning files would
couple two independent schema lines — a bump in one would require explaining
why the other is unaffected. The learning files are a new surface with their
own evolution path (the suggestion engine in v0.5 may add fields). Own schema
is cleaner.

The `state.json` schema field should be `"schemaVersion": "0.4"` to match the
Housekeeper version that defined it. JSONL event records should each include
a `schemaVersion: "0.4"` field for forward-compatibility (a reader from v0.5
can distinguish v0.4 records from any new field shape v0.5 introduces).

**No platform constraint forces this answer** — it is a recommendation based
on schema hygiene.

### 8.2 Q2 (`settings-rewrite` vs `json-rewrite`) — platform input

Q2 asks: keep `settings-rewrite` with more kinds (a) / generalize to one
`json-rewrite` (b) / drop P4 to v0.5 (c)?

**Platform input:** The atomic-rename protocol applies identically to any
JSON file rewrite — settings, registry, skill index. A generalized `json-rewrite`
kind with a `targetPath` parameter (the file path, not a JSON path within the
file) is architecturally cleaner and avoids proliferating identical code for
each surface.

**Platform constraint:** If `json-rewrite` is adopted (option b), the v0.3
`settings-rewrite` kind MUST be preserved as an alias (not removed) for
backward compatibility with existing operation manifests. The alias requirement
means option (b) adds no migration risk but requires the alias to be verified
against v0.3 fixtures byte-for-byte (per TASKBOARD T-400).

**Platform recommendation: option (b) with alias.** The generalization is
the right architecture for v0.4's expanded surface. The alias preserves
backward compatibility.

### 8.3 Q3 (Plugin pruning grace window) — platform input

Q3 asks: 30 days (a) / 7 days (b) / 90 days (c) / require explicit config (d)?

**Platform constraint:** The documented Claude Code orphan grace period is
7 days (per `plugins-reference`, confirmed by two independent citations in
`notes/LOADER-SEMANTICS-AUDIT.md` §2). Using 7 days as the grace window for
`plugin.unused_past_grace` would mean Housekeeper flags plugins as "candidate
for pruning" at the same horizon that Claude considers caches eligible for
deletion. This is not useful — it would flag plugins that Claude itself may
prune before Housekeeper acts.

**Platform recommendation: option (a) — 30 days.** The 30-day window is long
enough to distinguish deliberate non-use from the orphan lifecycle. It also
matches the 30-day window used for `learn --prune` default consideration,
making the retention policy consistent across Housekeeper surfaces. Option
(d) (require explicit config) is defensible but creates friction that conflicts
with v0.4's goal of making `prune` usable out of the box for audit purposes.

### 8.4 Q4 (JSONC parser choice) — platform recommendation

See §4.4 above. **Recommend `jsonc-parser` (option a).**

**Platform constraint (forced answer):** Neither `jsonc-parser` nor
`comment-json` conflicts with Node.js 20+ compatibility (Housekeeper's engine
constraint). The choice is not forced by platform compatibility. It is forced
by the correctness argument: the Symbol annotation model in `comment-json`
is fragile for Housekeeper's patch pattern.

### 8.5 Q5 (Batch stream chunking model) — platform input

Q5 asks: fixed 50 (a) / adaptive under 10-MiB budget pressure (b) / time-
bounded chunks (c)?

**Platform input:** The existing snapshot budget is 50 files / 10 MiB per
operation (per `docs/threat-model.md` §3 T4). The `--stream` extension for
N>50 must respect this budget per chunk, not per stream. Adaptive sizing
(option b) is architecturally cleaner: if a chunk of 50 would exceed 10 MiB,
the chunk is split at the budget boundary. This makes the per-chunk invariant
"budget not exceeded" rather than "exactly 50 items."

**Platform constraint:** Time-bounded chunks (option c) require a reliable
wall-clock measurement that is not currently part of the snapshot protocol.
Time bounds also interact poorly with NFS latency variability. Fixed 50 (option
a) is simpler but wastes budget when items are small. Adaptive (option b) uses
the existing budget invariant as the split criterion.

**Platform recommendation: option (b) — adaptive chunk sizing under the
10-MiB budget.** The fixed 50 is the default maximum, with early split when
the accumulated snapshot size approaches 10 MiB.

### 8.6 New platform questions surfaced by this analysis

**PQ-1: Is there a skill index file?** The platform analysis in §1.3 notes
that the documented skill surface is a directory tree, not an index manifest.
Before T-403 (`skills.entry_dangling` harden target) can be designed, the
implementation team must determine whether an index file exists and where it
lives. If no index file exists, the "dangling entry" concept does not apply
to skills in the same way it applies to the registry. This is a prerequisite
investigation for T-403.

**PQ-2: Does `claude plugin uninstall` check for a running Claude session?**
The platform analysis in §3.2 notes that the interaction between `claude plugin
uninstall` and a live session is undocumented. The v0.4.1 `plugin-uninstall`
kind should either:
- Check for a running Claude session before invoking the uninstall, or
- Document in the refusal that the user should close Claude before running.
The tie-breaker should assign a probe task to determine whether `claude plugin
uninstall` is safe to call while Claude is running.

**PQ-3: Does `looksLikeNetworkFs` check `MNT_LOCAL` on macOS?** The current
implementation at `harden-plan.mjs:312` was designed for `settings-rewrite`.
The gap identified in §5.4 (APFS-over-network returning `apfs` as the type)
needs verification. If the current implementation uses only `f_fstypename`
without `f_flags & MNT_LOCAL`, learning JSONL and lock.history writes on
APFS-mounted network shares would not be flagged.

**PQ-4: What is the `ConfigChange` hook event trigger?** The hooks doc
mentions `ConfigChange` as a plugin-supportable event (audit §5
NEW_RULE_AVAILABLE). If `ConfigChange` fires on `settings.json` edits via
atomic rename, the RELOAD HINT posture may be unnecessarily conservative —
a future version of Housekeeper could emit a `ConfigChange` trigger hint
instead of a restart hint. This is a research item for the v0.4.x audit cycle.

## 13. Summary

The platform-interop bottom line for v0.4:

1. **Registry and hooks re-read: session-start-only (INFERRED).** RELOAD HINT
   required for all P4 targets. Same posture as v0.3 settings-rewrite.

2. **Skills: the one documented hot-reload case, but P4 targets the index,
   not the SKILL.md.** Investigate whether an index file exists before T-403.

3. **MCP rewrite hot-reload: not documented.** RELOAD HINT required; must not
   claim hot-reload. The `mcp_command_missing` case means no running server —
   same safe scenario as v0.3.

4. **Plugin uninstall race: 7-day orphan grace period is the safety net.**
   v0.4.1 MUST use `claude plugin uninstall`, not direct `dir-rmtree`. Safe
   mode MUST block `prune --uninstall`.

5. **Learning JSONL durability: single-call write = safe on local POSIX.** NFS
   degrades atomicity — emit informational warning, not hard refusal.

6. **JSONC parser: `jsonc-parser` (option a).** Zero deps, MIT, active
   maintenance, `modify()` + `applyEdits()` matches the use case.

7. **Adaptive stream chunking: budget-driven (option b).** Fixed 50 maximum
   per chunk; split early on 10-MiB pressure.

8. **Four new platform questions (PQ-1 through PQ-4)** are inputs for T-D04
   to assign as research tasks before the corresponding implementation phases
   begin.
