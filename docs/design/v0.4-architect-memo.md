## §0 TL;DR — the seven load-bearing decisions

Product, platform, and tie-breaker most need to react to these before code
lands:

1. **The learning loop ships as four append-only JSONL files plus one
   read-write `state.json`, under `<home>/.claude/housekeeper/learning/`.** Each
   line carries its own `schemaVersion: "0.4"` (the recommended Q1 ruling)
   because file-mtime is not a stable schema signal across stream chunks (P6)
   and the data is meant to outlive a single binary version. The writer is a
   new module `scripts/lib/learning.mjs`, called from `composeCleanPlan`,
   `composeBatchCleanPlan`, `composeHardenPlan`, `executeCleanPlan`,
   `executeBatchCleanPlan`, `executeHardenPlan`, and `executeRollbackPlan`.
   See §2.

2. **MCP repair beyond stripping extends `settings-rewrite`, it does not
   generalize.** The recommended Q2 ruling is "keep `settings-rewrite`, add
   three new compose-time refusal classes inside `composeHardenPlan` — do not
   coin a new `json-rewrite` mutation kind." The argument is that v0.3's
   `MUTATION_REGISTRY["settings-rewrite"]` already keys on `op.targetPath`, not
   on a "settings" concept — the only new dimension is the patch builder. A
   generalized `json-rewrite` would force a `no-mutation.test.mjs` allowlist
   review for what is essentially the same surface. See §3.

3. **Plugin pruning ships as audit-only in v0.4.0; the grace window is 30
   days.** The recommended Q3 ruling is 30 days, matching the human "I haven't
   used this plugin in a month" mental model and aligning with the
   `gcSnapshots` 10-op retention horizon (~30 days of weekly use). The 7-day
   `PLUGIN_ORPHAN_GRACE_DAYS` constant in `audit.mjs:31` is for *cache
   versions* (a different surface) and intentionally stays distinct. See §4.

4. **The three new P4 hardenable detectors use the existing
   `settings-rewrite` mutation kind UNCHANGED.** Registry rewrites, hooks
   config rewrites, and skills index rewrites all flow through the same
   `MUTATION_REGISTRY["settings-rewrite"]` in `snapshot.mjs:773` — the `apply`
   hook is generic across JSON files. The only per-target work is the patch
   builder. This means Q2 ruling drives Q4 / P4: if Q2 keeps `settings-rewrite`
   (recommended), P4 is purely a `HARDENABLE_DETECTORS_V03` map extension
   renamed `HARDENABLE_DETECTORS_V04`. See §6.

5. **JSONC v2 ships with `jsonc-parser` (Microsoft, MIT, zero runtime deps).**
   The recommended Q4 ruling is option (a) — its `modify()` API is the only
   one of the three candidates that lets us produce a minimal in-place
   edit-script (rather than a re-serialised whole file), which preserves
   comments and trailing commas byte-for-byte outside the edit window.
   `comment-json` (option b) has documented edge cases around comments inside
   merged objects (re-confirmed by reading its GitHub issue tracker); a
   hand-rolled lex-aware patcher (option c) is a re-implementation tax we
   should not pay for a pattern Microsoft already solved in production for
   VS Code. See §7.

6. **Batch streaming uses fixed 50-item chunks; `--stream` requires N>50.**
   The recommended Q5 ruling is fixed chunks because every other model
   (adaptive, time-bounded) breaks the contract that ONE chunk = ONE snapshot
   manifest under the existing v0.3 budget (50 files, 10 MiB), and any user
   who needs adaptive sizing can drop to the existing single-op flow. Per-chunk
   sub-manifests share a parent `streamId`; rollback walks sub-manifests in
   reverse. See §8.

7. **The 4 → 7 mutation-allowlist growth is the v0.4 schema-stability
   tripwire.** v0.4 adds three modules that touch the filesystem under
   `<home>/.claude/housekeeper/`:
   - `scripts/lib/learning.mjs` (JSONL appends + `state.json` rewrites)
   - `scripts/lib/lock-history.mjs` (JSONL append on lock acquire/release)
   - one of `scripts/lib/prune-plan.mjs` (P3 audit-only) OR a flag on
     `audit.mjs` (architect's recommendation: separate module — keep audit
     side-effect-free)
   See §9.

The rest of the memo backs these with on-disk schema, every new refusal class
mapped to its trigger site, concrete code references against the v0.3 HEAD,
the cross-cutting threat-model and schema-stability deltas, and detailed
rationale for each Q1–Q5 recommendation.

Every new path lives inside the existing Housekeeper-owned subtree. None of

identical to the existing `operations/` and `snapshots/` directories:

- `ownerClass: "housekeeper-owned"`
- `loadBearingClass: "not-load-bearing"` (no other tool reads these)
- `sensitivityClass: "private-path"` (per the `--redact` collapse rule)
- `executionClass: "inert"` (pure data, no shell semantics)
- `rollbackClass: "snapshot-possible"` for `state.json` only; the JSONL files

- `scopeClass: "in-scope"`

This is intentional: the existing `pathMatchesProtection` / sector-boundary
checks need no extension, the `--redact` token scrubber already covers the
directory, and the diagnose pipeline reads nothing here (see §2.5 — the
learning data is write-only from compose/execute paths, read-only by the new
`learn` subcommand).

## §2 Learning loop (P1) deep dive

### §2.1 File-on-disk schemas

Four JSONL files plus one JSON state. Each JSONL line is a self-contained
record: appending a line is atomic on POSIX up to PIPE_BUF (4096 bytes on
Linux, 512 on macOS — every record we write fits).

**`refusals.jsonl`** — one line per `CleanPlanRefusal` or `HardenPlanRefusal`
returned in a `plan.refused[]` array at compose time.

```jsonc
{
  "schemaVersion": "0.4",
  "kind": "refusal",
  "ts": "2026-06-01T14:23:11.802Z",
  "command": "harden",                          // "clean" | "harden" | "rollback"
  "detectorId": "settings.mcp_command_missing", // empty string for batch-wide refusals
  "reason": "mcp-rewrite-target-not-executable",
  "targetPath": "/Users/u/.claude/settings.json",
  "redactedTargetPath": "<home>/.claude/settings.json", // produced by lib/redact.mjs
  "pid": 4711,
  "opId": "op_20260601_a1b2c3d4",               // empty string if no op was generated
  "evidenceHash": "f7e2..."                     // sha256 of finding.evidence; for dedupe in summaries
}
```

Field rules:

- `evidenceHash` is `sha256(JSON.stringify(finding.evidence))` so the summary
  can dedupe "the same MCP server keeps failing every session" without
  storing the evidence payload.
- `redactedTargetPath` is computed once at write time so the read path can
  honor `--redact` without re-running the scrubber against millions of lines.
- `opId` is empty for refusals that fire before snapshot — most of v0.3's
  refusals — and populated only for the rare case where a refusal happens
  post-snapshot (currently none, but reserved for v0.4.1 plugin uninstall).

**`applied.jsonl`** — one line per verified manifest OR per `partialApply`.

```jsonc
{
  "schemaVersion": "0.4",
  "kind": "applied",
  "ts": "2026-06-01T14:23:14.119Z",
  "command": "clean",                           // "clean" | "harden"
  "detectorId": "plugin.cache_unreferenced",
  "targetPath": "/Users/u/.claude/plugins/cache/m/p/v1",
  "redactedTargetPath": "<home>/.claude/plugins/cache/m/p/v1",
  "mutationKind": "dir-rmtree",                 // for v0.4 prune: "plugin-uninstall" reserved
  "opId": "op_20260601_a1b2c3d4",
  "bytesAffected": 1421337,
  "filesAffected": 42,
  "partialApply": false,
  "durationMs": 2811                            // takeSnapshot → verify wall-clock
}
```

**`rollbacks.jsonl`** — one line per terminal rollback (status `rolled_back`
or `aborted`):

```jsonc
{
  "schemaVersion": "0.4",
  "kind": "rollback",
  "ts": "2026-06-02T09:14:02.001Z",
  "originatingOpId": "op_20260601_a1b2c3d4",
  "rollbackKind": "rollback",                   // "rollback" | "abort"
  "originatingCommand": "clean",
  "filesRestored": 42,
  "durationMs": 1922,
  "userInitiated": true                         // false reserved for v0.5 auto-rollback
}
```

**`state.json`** — counters and last-N false-positive markers. The only
read-write file in the learning surface; the JSONLs are append-only.

```jsonc
{
  "schemaVersion": "0.4",
  "kind": "state",
  "createdAt": "2026-05-25T00:00:00.000Z",
  "lastWrittenAt": "2026-06-02T09:14:02.001Z",
  "counters": {
    "refusalsAllTime": 142,
    "appliedAllTime": 38,
    "rollbacksAllTime": 2,
    "refusalsLast30d": 27,
    "appliedLast30d": 14,
    "rollbacksLast30d": 0
  },
  "falsePositives": [
    {
      "opId": "op_20260530_xxxxxxxx",
      "detectorId": "plugin.cache_unreferenced",
      "evidenceHash": "9f12...",
      "markedAt": "2026-05-31T22:18:00.000Z",
      "note": ""                                // free-text from --note=
    }
  ]
}
```

The counters duplicate aggregate data that `readSummary()` could compute by
scanning the JSONLs each time. The duplication is deliberate — for a heavy
user (~10k lines/yr), summary should be sub-100-ms; recomputing from disk on
each `housekeeper learn` invocation breaks that. Counters are *advisory*; if
they drift from the JSONL truth (e.g. someone manually trimmed
`refusals.jsonl`), the summary can detect the divergence and prompt `learn
--rebuild-state`.

### §2.2 Append protocol — atomicity and lock interaction

Three sources of writes converge on the learning surface:

| Caller | Functions | When |
|---|---|---|
| `composeCleanPlan` / `composeBatchCleanPlan` | `learning.appendRefusal()` | one per `CleanPlanRefusal` |
| `composeHardenPlan` | `learning.appendRefusal()` | one per `HardenPlanRefusal` |
| `executeCleanPlan` / `executeBatchCleanPlan` / `executeHardenPlan` | `learning.appendApplied()` | one per terminal verify OR partial apply |
| `executeRollbackPlan` / `abortRollbackOperation` | `learning.appendRollback()` | one per terminal rollback/abort |
| `learn --mark-false-positive` | `learning.markFalsePositive()` | rewrites `state.json` |

The compose-time writes can happen WITHOUT the housekeeper lockfile held —
compose is a read-only operation in v0.3 and we should not change that
contract. The execute-time writes happen INSIDE the lock window. Rollback
writes also happen inside the lock window.

**Implication for race conditions:** two concurrent compose invocations from
different terminals can both refuse and both append to `refusals.jsonl` at
the same time. Per POSIX `O_APPEND`, writes ≤ `PIPE_BUF` are atomic — they
do not interleave. Our records are well under 4096 bytes (worst case ~1500
chars after redaction), so the interleaving risk is bounded. We do NOT need
a separate lock for the JSONL files.

`state.json` is a different story. Two concurrent `learn
--mark-false-positive` calls would lose one of the marker entries (last
write wins). The recommended posture is:

- `state.json` rewrites go through the *existing* `atomicWrite` helper from
  `snapshot.mjs:217` (write-temp + rename + fsync-parent).
- Concurrent `learn --mark-false-positive` invocations are rare enough that
  last-write-wins is acceptable for v0.4. If telemetry shows real concurrent
  conflict, v0.5 adds a small `<home>/.claude/housekeeper/learning/.lock`
  file using the same `O_EXCL` pattern as `acquireLock`.

The `learning.mjs` module is intentionally tiny:

```js
// scripts/lib/learning.mjs — sketch (~120 LOC target)
import { open, readFile, stat } from "node:fs/promises";
import { existsSync } from "node:fs";
import { join } from "node:path";
import { atomicWrite } from "./snapshot.mjs";

const SCHEMA = "0.4";

export async function appendRefusal(home, payload) {
  const line = JSON.stringify({ schemaVersion: SCHEMA, kind: "refusal", ...payload }) + "\n";
  await appendJsonl(home, "refusals.jsonl", line);
}
// ... appendApplied, appendRollback identical shape ...

async function appendJsonl(home, filename, line) {
  const dir = join(home, ".claude", "housekeeper", "learning");
  await mkdir(dir, { recursive: true });
  const handle = await open(join(dir, filename), "a");
  try { await handle.appendFile(line); } finally { await handle.close(); }
}

export async function readSummary(home, { since } = {}) { /* see §2.4 */ }
export async function markFalsePositive(home, opId, note) { /* atomicWrite state.json */ }
export async function prune(home, { olderThan }) { /* see §2.7 */ }
```

Note `appendFile` is on the mutation allowlist forbidden list in
`test/no-mutation.test.mjs:14-32` — `appendFile(` is listed alongside `writeFile(`.
So `learning.mjs` MUST be added to `MUTATION_ALLOWLIST` (the 5th entry after
v0.3's 4). This is the v0.4 schema-stability tripwire mentioned in §0.

### §2.3 Why JSONLs are NOT rollback targets

The learning data is observational. If a user is concerned about its content,
they can:

1. Delete the file (no Housekeeper logic depends on the JSONL existing).
2. Run `housekeeper learn --prune --older-than=0` to truncate from the
   official path.

Adding rollback support for these would mean every clean/harden also
snapshots the JSONL it's about to append to — a 50x increase in snapshot
budget for the most common operation. The simpler shape is to keep these as
append-only artifacts outside the snapshot/rollback contract entirely. This
also keeps the v0.3 invariant that rollback restores Claude-visible state,
not Housekeeper-internal telemetry.

### §2.4 Read path — `housekeeper learn` (no args)

Summary output (target: one screen, ≤ 200 ms on a 30 k-line JSONL pair):

```
Last 30 days (since 2026-04-30):
  Refusals:    27  (top:  no-mutation-mapping-in-v0.3 ×12,
                          settings-jsonc-detected ×6,
                          plugin-cache-has-mcp-server ×4)
  Applied:     14  (top:  plugin.cache_unreferenced ×11,
                          settings.hook_path_dangling ×2,
                          housekeeper.stale_lock ×1)
  Rollbacks:    0
  False-positives marked: 1 (latest: plugin.cache_unreferenced @ 2026-05-31)

All-time: 142 refusals, 38 applied, 2 rollbacks (since 2026-05-25)
```

Implementation:

- Stream `refusals.jsonl` / `applied.jsonl` / `rollbacks.jsonl` line-by-line
  using `readline` over a `createReadStream`. Do NOT load the full file into
  memory — at 10k entries we are looking at multi-MB files.
- For each line, parse as JSON; skip lines that fail parse (shouldn't happen
  but a corrupted half-line at the end of a crashed write should not break
  the summary).
- Filter by `ts >= now - 30d`.
- Build `{ reason: count }`, `{ detectorId: count }` histograms.
- Print the top-5 of each.

`--json` output dumps the histograms as objects, with the all-time counters
from `state.json` alongside.

**Performance budget (T-107 in TASKBOARD):** append cost < 5 ms p99 on a
10k-line JSONL. Our `appendFile` is one open + one write + one close — on
APFS / ext4 / Linux NVMe this is dominated by the `fsync` we DON'T call
(intentional — `O_APPEND` is durable enough for observation, and a missing
last line on crash recovery is acceptable). Bench numbers will live in
`test/learning.test.mjs` per T-106.

### §2.5 `diagnose` decoration (T-105)

Per `PLAN-v0.4.md §3.1`, diagnose grows `falsePositiveSeenBefore: N` on
findings whose `evidenceHash` matches an entry in `state.json`. This is the
only place `audit.mjs` ever reads the learning surface. The recommended
shape:

```js
// pseudocode in audit.mjs:buildFinding (~ line 256, after hardenable flag)
if (raw.evidenceHash && context.falsePositiveMarkers) {
  const count = context.falsePositiveMarkers[raw.evidenceHash] || 0;
  if (count > 0) finding.falsePositiveSeenBefore = count;
}
```

`falsePositiveMarkers` is populated once at `loadContext` time by reading
`state.json` and bucketing `falsePositives[]` by `evidenceHash`. Cost is a
single read of a small JSON file; if missing, the map is empty and nothing
is decorated.

**Important non-promise:** the v0.4.0 decoration is *purely informational*.
It does not change stance, claim-level, or ordering. The suggestion engine
deferred to v0.5 will use this signal; v0.4 just surfaces it.

### §2.6 Q1 — Schema versioning for learning files

Three candidates from `PLAN-v0.4.md §4 Q1`:

**(a) Own schema `"0.4"`** — each line carries `schemaVersion: "0.4"`.

- Pros: completely decoupled from `snapshot.mjs:73 SCHEMA_VERSION_V2 = "0.2"`.
  We can bump the learning schema without thinking about the manifest schema
  (they evolve at different rates — manifests change once a year, learning
  fields likely once per release). Per-line versioning means we can mix v0.4
  and v0.5 records in the same file during a tool upgrade without breaking
  the reader.
- Cons: one more `schemaVersion` field a human reader has to track. Not a
  real cost — every Housekeeper file already has one.

**(b) Reuse manifest `"0.2"`** — borrow `SCHEMA_VERSION_V2` from
`snapshot.mjs`.

- Pros: one fewer constant.
- Cons: forces the manifest schema and the learning schema to bump in
  lockstep. If we add a manifest field in v0.5 we don't want to also be
  forced to re-version every learning JSONL.

**(c) No version field, freeze the shape** — accept the file is what it is
and never break it.

- Pros: even smaller files.
- Cons: We *will* want to add fields (e.g. `mode: "safe" | "confirm"` for
  cross-cutting analytics). Without a schema field there is no signal to
  the reader that this is a v0.4 line vs a v0.5 line; old code reading new
  files breaks silently.

**Recommendation: (a) own schema `"0.4"`.** The cost of an extra field per
line is trivial (12 bytes); the value of independent evolution between the
manifest and the learning surface is high (they share no real contract
beyond living under `<home>/.claude/housekeeper/`). The product memo should
ratify the field name (`schemaVersion` matches the manifest convention;
no reason to rename).

The tie-breaker (T-D04) should know: this is the *least* contentious of the
five questions. The architect's veto is on (b); options (a) and (c) are both
defensible if the synthesizer prefers fewer fields.

### §2.7 Pruning the learning surface

`learn --prune --older-than=<days>` is a tool the user invokes manually. It
is *not* a clean/harden side effect — we never silently truncate the user's
observational record.

Implementation sketch:

- Stream the JSONL.
- Filter to keep lines with `ts >= now - olderThan days`.
- Write the kept lines to a sibling `.jsonl.tmp.<random>`.
- Rename atomically (same `atomicWrite` helper pattern).
- Update `state.json` counters to reflect the prune (decrement
  `refusalsAllTime` by the dropped line count, etc.).

This is the only place we ever *delete* from the JSONL surface, and the user
asked for it explicitly. No surprise.

## §3 MCP repair beyond stripping (P2) deep dive

### §3.1 The CLI flag

```
housekeeper harden --confirm --yes \
  --target=settings.mcp_command_missing \
  --path=/abs/.claude/settings.json \
  --mcp-command-rewrite=/old/path/to/server=/new/path/to/server
```

The parser parses `--mcp-command-rewrite=<old>=<new>` as a single string,
splits on the first `=` after the option name, then splits the value on `=`.
Both halves are required to be non-empty and absolute paths. Empty or
relative values produce a parse error before `composeHardenPlan` runs (T-200
in TASKBOARD).

### §3.2 Threading through `composeHardenPlan`

Today `composeHardenPlan` (harden-plan.mjs:341) calls a patch builder from
`HARDENABLE_DETECTORS_V03` that produces a remove-only patch. v0.4 adds an
options parameter:

```js
// before (v0.3, harden-plan.mjs:341)
export async function composeHardenPlan(home, options = {}) {
  const targetDetectorId = options.target || "";
  const targetPath       = options.path   || "";
  const mode             = options.mode   || "safe";
  // …
}

// after (v0.4)
export async function composeHardenPlan(home, options = {}) {
  // …existing parameters…
  const mcpRewrite = options.mcpCommandRewrite || null;
  // mcpRewrite shape: { oldPath: "/abs/...", newPath: "/abs/..." } | null
  // The CLI parser produces null when --mcp-command-rewrite is absent.
}
```

The mode where `mcpRewrite` is present takes a different patch-builder branch
inside `HARDENABLE_DETECTORS_V04` for `settings.mcp_command_missing`:

- If `mcpRewrite === null` (v0.3 behaviour): build a remove-patch on
  `["mcpServers", name]` for every server whose command is missing.
- If `mcpRewrite !== null`: build a `set`-patch on
  `["mcpServers", name, "command"]` replacing exactly the matching old path.
  Servers whose command does not match `mcpRewrite.oldPath` are left
  untouched.

The Map-based registry in `harden-plan.mjs:115` does not have a place to
carry the rewrite parameter; the recommended refactor is to change the value
type from `(finding) => patch` to `(finding, options) => patch | PreApplyRefusal`
so the patch builder can self-decide whether to surface a refusal for
"target-missing" before the snapshot is taken.

### §3.3 Three new refusal classes

| Class | Reason | Trigger site |
|---|---|---|
| `HardenPlanRefusal` | `mcp-rewrite-target-missing` | `existsSync(mcpRewrite.newPath)` returns false at compose |
| `HardenPlanRefusal` | `mcp-rewrite-target-not-executable` | `statSync(mcpRewrite.newPath).mode & 0o111` is zero |
| `HardenPlanRefusal` | `mcp-rewrite-source-not-found` | No `mcpServers.<name>.command === mcpRewrite.oldPath` in parsed settings |

All three fire at compose time, before any snapshot. They produce the same
refusal-set shape as v0.3:

```js
refused.push({
  class: "HardenPlanRefusal",
  reason: "mcp-rewrite-target-missing",
  targetPath: settingsPath,
  detectorId: "settings.mcp_command_missing",
  message: `Rewrite target ${mcpRewrite.newPath} does not exist`,
  nextStep: nextStepFor("mcp-rewrite-target-missing"),
  exitCode: 2
});
```

The `nextStep` strings are product-memo territory but the architect's
recommendation is "tell the user what's broken and how to fix it, do not
suggest re-running with a different flag — that's a guess." Example for
target-missing:

> Target `<path>` does not exist. Install the MCP binary at that path, or
> pass `--mcp-command-rewrite=<old>=<existing path>` with a path that exists.

### §3.4 Threat: hostile user supplies PATH-shadowing target

`PLAN-v0.4.md §6` flags this as a Medium risk. The concrete attack:

1. User has `/usr/local/bin/legit-mcp` in their settings.
2. Attacker convinces user to run `housekeeper harden ...
   --mcp-command-rewrite=/usr/local/bin/legit-mcp=/tmp/attacker/legit-mcp`
3. `/tmp/attacker/legit-mcp` is +x and exists.
4. Housekeeper writes the new path into settings.
5. Claude session subsequently starts the attacker-controlled binary.

This is in scope for v0.4 because it's the first time Housekeeper writes a
user-supplied path into a load-bearing config file. The existing
`detectMcpCommandMissing` (audit.mjs:594) doesn't have this problem because
it removes — it never writes user-supplied data into settings.

Recommended mitigations, in priority order:

1. **No mitigation, just clear consent.** The `harden --confirm --yes`
   contract requires the user to type both flags. The CLI prints the
   exact rewrite (old → new path) and the rewrite target. If the user
   typed an attacker path, they consented. This is the v0.3 contract for
   `harden`.

2. **Soft warning when target is under `/tmp`, `/var/tmp`, or
   `~/Downloads`.** These are common attacker drops. The product memo
   should design the warning copy. Architect's view: this is a useful
   UX nudge that costs little.

3. **Refuse if target's resolved owner is not the current user.**
   `statSync(newPath).uid !== process.getuid()` triggers refusal. This
   blocks the privileged-escalation variant (attacker drops a root-owned
   binary). Architect's view: yes, ship this — it's the cheapest hard
   boundary against the strongest attacker.

Threat model addendum lands in `docs/threat-model.md` per T-701b.

### §3.5 Q2 — Settings-rewrite vs json-rewrite generalization

**Three candidates from `PLAN-v0.4.md §4 Q2`:**

**(a) Keep `settings-rewrite` and add three more kinds** (one per P4
target):

- `registry-rewrite`, `hooks-rewrite`, `skills-rewrite`
- Each is a parallel entry in `MUTATION_REGISTRY` with its own `preApply` /
  `apply` / `rollback` hooks.
- Pros: detector-specific validation in `preApply` is co-located with the
  mutation kind. Easy to reason about per-kind ownership.
- Cons: four entries that all do the same thing (parse JSON, apply patch,
  serialize JSON, atomic-write). Snapshot.mjs grows linearly.

**(b) Generalize to one `json-rewrite` kind and alias `settings-rewrite` to
it.**

- The single kind keys on `op.targetPath` (no change) and `op.parserChoice`
  (new — "strict" | "jsonc" per Q4 ruling).
- Pros: one entry in `MUTATION_REGISTRY`, one allowlist entry in
  `no-mutation.test.mjs`. P4 detectors plug in without `snapshot.mjs`
  changes.
- Cons: `preApply` validation (e.g. "is the patch result a valid
  Claude-settings shape?") would need to be per-detector. Either
  `preApply` takes a `validatorFn` parameter, or per-detector validation
  moves entirely into `composeHardenPlan` (architect's preference — see
  below).

**(c) Drop P4 to v0.5** and ship v0.4 with just P1, P2, P3, P5, P6.

- Pros: smaller v0.4. Q2 stays unresolved.
- Cons: leaves a known wart — three detectors are review-only despite
  having clean patch semantics.

**Recommendation: (b) generalize.** The argument for (a) — co-location of
preApply with kind — doesn't hold up against the v0.3 evidence:
`MUTATION_REGISTRY["settings-rewrite"].preApply` (snapshot.mjs:787-848)
already does *generic* JSON validation (parse, apply, round-trip,
idempotency). There is no settings-specific logic in preApply. Renaming
the kind to `json-rewrite` is mechanical; aliasing `settings-rewrite` to
it for back-compat is one line:

```js
export const MUTATION_REGISTRY = Object.freeze({
  "json-rewrite":    JSON_REWRITE_HANDLER,
  "settings-rewrite": JSON_REWRITE_HANDLER  // alias for v0.3 callers
});
```

The detector-specific shape validation (e.g. "registry must have a
top-level `commands` array") goes into the patch builder in
`harden-plan.mjs`, where it already lives by virtue of the builder being
the only place that knows what the target document should look like. The
patch builder returns either a patch or a synthesized `PreApplyRefusal`
with a detector-specific reason like `registry-shape-unknown`. That's
already a pattern in v0.3 (see `buildInvalidJsonSentinel` in
`harden-plan.mjs:235`).

The `no-mutation.test.mjs` allowlist stays at 4 → 5 (the new
`learning.mjs`), not 4 → 8. P4 is purely a `HARDENABLE_DETECTORS_V04` map
extension and three new patch builders.

The tie-breaker should note: this is the architect's *strongest*
recommendation in the memo. If the product or platform memo pushes
back, it should be on copy or threat-model grounds, not architecture.

## §4 Plugin pruning automation (P3) deep dive

### §4.1 The `plugin.unused_past_grace` detector

New entry in `audit.mjs` `SCOPE_TO_DETECTORS.plugins`:

```js
plugins: [
  "plugin.expected_orphan",
  "plugin.cache_unreferenced",
  "plugin.duplicate_registration",
  "plugin.cache_size",
  "plugin.unused_past_grace",  // NEW in v0.4 (T-300)
  "settings.hook_path_dangling",
  "settings.hook_command_shell_ambiguous"
]
```

Detector pseudocode:

```js
function detectPluginUnusedPastGrace(context) {
  const graceMs = (context.config.pruneGraceDays || 30) * 24 * 60 * 60 * 1000;
  const now     = context.now;
  const out = [];

  for (const entry of context.pluginEntries) {
    if (!entry.installPath || !existsSync(entry.installPath)) continue;
    const installedAtMs = installedAt(entry, context);
    if (now - installedAtMs < graceMs) continue;

    const recentActivity = countLearningActivityFor(entry.key, context);
    const shellHistoryHits = scanShellHistoryForSlashCommand(entry.key, context);

    if (recentActivity > 0 || shellHistoryHits > 0) continue;

    out.push({
      id: "plugin.unused_past_grace",
      class: "hygiene",
      claimLevel: "observation",
      targetPath: entry.installPath,
      surface: /* claude-managed surface, see audit.mjs:1190 */,
      evidence: {
        structural: [
          `plugin installed at ${entry.installPath}`,
          `installed ${daysAgo(installedAtMs)} days ago`,
          `no clean/harden activity in last ${graceDays} days`,
          `no slash-command invocation in shell history`
        ],
        freshness: [`grace window: ${graceDays}d`]
      },
      missingKeys: [
        "live evidence the user does not want this plugin",
        "telemetry of plugin use beyond shell history"
      ],
      summary: `plugin ${entry.key} has not been touched in ${graceDays} days`,
      nextAllowedStep: "review and consider `claude plugin uninstall` manually",
      blockedActions: [
        "uninstall plugin automatically",
        "call plugin not wanted"
      ],
      forceStance: "inform"
    });
  }
  return out;
}
```

Three signals feed the detector. Each is its own subsection.

### §4.2 Signal: `installed-at` from `installed_plugins.json`

`installed_plugins.json` records each plugin entry but does not currently
have an `installedAt` field — both the array form (`audit.mjs:1372`) and the
object form (`audit.mjs:1386`) are silent on time. Three sources of truth
the detector can use:

1. **`mtimeMs` of the plugin's install directory.** Cheap, always available.
   Vulnerable to `touch` shenanigans and to the user's filesystem behaviour
   (some restore-from-backup flows reset mtimes).
2. **A new `installedAt` field in future `claude plugin install`.** Not
   under our control — Claude Code may or may not add this. We cannot
   depend on it for v0.4.0.
3. **The `<home>/.claude/housekeeper/learning/applied.jsonl` first-seen
   timestamp** for a target path under the plugin's install directory.
   Available only for plugins active during prior Housekeeper sessions.

Recommended approach: use (1) as primary, fall back to "unknown" if mtime
is suspicious (more than 1 year old AND less than the grace window —
indicates a touched directory). Detector returns `historyAvailable: false`
in `evidence.freshness` when fallback engaged. The `prune-history-unavailable`
refusal class in T-303 covers the case where shell history can't be read
(see §4.3).

### §4.3 Signal: shell history scan

The recommended scope:

- Read `~/.bash_history`, `~/.zsh_history`, `~/.config/fish/fish_history`.
- For each line, look for substrings matching the plugin's slash-command
  prefix or its package name.
- Match is case-insensitive substring, no regex. We accept false positives
  (plugin name happens to appear in a `git` command).

This is best-effort. If a user has `HISTFILE` set elsewhere, or uses a shell
we don't scan, or has `HISTCONTROL=ignoreboth`, we under-detect activity
and a plugin appears more "unused" than it is. The mitigation is the
`historyAvailable: false` evidence flag (T-303 in TASKBOARD):

```js
{
  id: "plugin.unused_past_grace",
  evidence: {
    structural: [/* ... */],
    freshness: ["shell history not readable; activity signal degraded"]
  },
  historyAvailable: false   // surfaces to renderer / JSON
}
```

The user should be able to see "we couldn't scan history, so this signal is
weak" in the diagnose output.

### §4.4 Signal: learning surface activity

This is the cleanest signal because Housekeeper owns the data. The
detector calls `learning.readApplied({ since: now - graceMs })` and
filters to entries whose `targetPath` starts with the plugin's
`installPath`. Any hit means the plugin was recently cleaned or hardened
(at least in our view), which is weak evidence it's actively maintained.

Note this signal is empty until v0.4 has been running for at least one
grace window — bootstrapping the heuristic requires data accumulation.
The architect's recommendation:

- v0.4.0: ship audit-only so the data accumulates without risk.
- v0.4.1: ship mutation after ≥30 days of data have accumulated.

The 30-day audit window is the actual justification for the grace-window
default (see §4.6).

### §4.5 Audit-only protocol — why no mutation in v0.4.0

PLAN-v0.4.md §3.3 explicitly defers mutation to v0.4.1. The architect's
endorsement: v0.4.0 builds the surface; v0.4.1 builds the action. This
mirrors how v0.2 shipped diagnose-only for `plugin.cache_unreferenced`
findings before v0.3 added `clean --confirm --yes`.

The audit-only protocol:

- Detector emits `forceStance: "inform"` (no clean/harden action available).
- `housekeeper prune` subcommand filters diagnose output to the new
  detector id and renders as a table (T-301).
- No `clean --target=plugin.unused_past_grace` is offered. The
  `CLEANABLE_DETECTORS_V02` set is unchanged. `HARDENABLE_DETECTORS_V03/V04`
  does not include it.

When v0.4.1 adds mutation, the path is:

- New `plugin-uninstall` mutation kind in `MUTATION_REGISTRY`.
- The kind wraps `claude plugin uninstall <key> --scope <scope>` in a
  subprocess. Snapshot captures the plugin cache directory tree before the
  subprocess runs (snapshot budget will need to grow for this; current 50
  files / 10 MiB will not cover a real plugin). Rollback: restore the
  cache + re-run `claude plugin install` with the captured version.

Phase 4.1's design is out of scope for this memo, but the architect notes:
plugin-uninstall is the v0.4 surface that *most* needs the
`learning/applied.jsonl` data to validate its heuristic before going live.
That's why audit-only is non-negotiable.

### §4.6 Q3 — Grace window default

Four candidates from `PLAN-v0.4.md §4 Q3`:

**(a) 30 days, matching plugin cache GC behaviour** (when a user reinstalls
a plugin, the old cache version is cleaned up after ~30 days of being
unreferenced — though formally we ship 7 days in `audit.mjs:31`
PLUGIN_ORPHAN_GRACE_DAYS, that's a different surface).

**(b) 7 days, matching `plugin.cache_unreferenced`** (`audit.mjs:31`).

**(c) 90 days, conservative.**

**(d) Require explicit config, refuse if unset.**

**Recommendation: (a) 30 days.**

Rationale:

- **Human mental model.** "I haven't used this plugin in a month" is the
  threshold at which most users would actually consider uninstall. A week
  is too short (vacations, switched-projects); 90 days is too long (data
  accumulation slows the v0.4.1 mutation rollout).
- **Audit window alignment.** v0.4.0 ships audit-only. The data we collect
  in `applied.jsonl` becomes the v0.4.1 grace-window evidence. 30 days of
  v0.4.0 in the wild gives us roughly one cycle of every weekly cron in
  every typical Housekeeper user's flow.
- **Cache GC alignment.** Plugin caches that are orphaned (no live plugin
  references them) get cleaned via the v0.3 path with a 7-day grace
  (`PLUGIN_ORPHAN_GRACE_DAYS`). Plugins that are *installed but unused*
  are a different surface — they have a live registry entry but no
  observable activity. 30 days is the natural step up.
- **Config override.** The 30-day default is just a default. Users who
  want shorter can set `pruneGraceDays: 7` in
  `<home>/.claude/housekeeper/config.json`. Loading from config follows
  the existing `loadConfig` pattern in `policy.mjs:loadConfig`.

(b) is rejected because cache versions and installed-but-unused plugins
are different things — sharing a constant blurs the distinction.

(c) is rejected because 90 days delays the v0.4.1 mutation rollout by 60+
days for no good reason.

(d) is rejected because it's hostile UX. Every diagnose run shouts about
a missing config field. The whole point of audit-only is to let the
default-config user see the signal.

The tie-breaker should know: this question has weak architectural
implications. It's mostly a product call. The architect's case for 30
days is the audit-data argument in bullet 2; the rest is opinion.

## §5 Harden non-settings surfaces (P4) deep dive

### §5.1 Three new target ids

| Target id | Description | Patch shape |
|---|---|---|
| `registry.command_dangling` | Local `<home>/.claude/commands/<name>.md` whose plugin is no longer installed | Remove the file (file-unlink, not json-rewrite) OR remove a registry-tracking-JSON entry, depending on §5.4 |
| `hooks.config_dangling` | Project `<project>/.claude/hooks/*.json` with missing `cwd` or `command` keys | json-rewrite removing the broken entry |
| `skills.entry_dangling` | Local `<home>/.claude/skills/<name>` whose plugin is no longer installed | Remove the skill directory (dir-rmtree) OR remove a registry-tracking-JSON entry |

Two of the three (`registry.command_dangling`, `skills.entry_dangling`) are

sub-options:

- **(i)** P4 ships as a mix: hooks.config_dangling uses json-rewrite (the
  Q2 (b) generalization); the other two use existing `file-unlink` and
  `dir-rmtree` kinds. This pushes the two filesystem detectors into the

- **(ii)** P4 ships as pure-JSON-rewrite by writing only to a tracking
  index file (which doesn't exist today — registry/skills don't have a
  tracking file in `<home>/.claude/`). Effectively this means inventing
  a tracking JSON. Not recommended.

**Recommendation: (i) split P4 between cleanable and hardenable lanes.**

- `registry.command_dangling` → `cleanable: true`, mutation kind
  `file-unlink`, lives in `CLEANABLE_DETECTORS_V04` (the v0.2 side table
  the v0.3 design left as-is).
- `skills.entry_dangling` → `cleanable: true`, mutation kind
  `dir-rmtree`, lives in `CLEANABLE_DETECTORS_V04`.
- `hooks.config_dangling` → `hardenable: true`, mutation kind
  `json-rewrite` (or `settings-rewrite` if Q2 (a) wins), patch builder
  in `harden-plan.mjs`.

This means the P4 task list is actually two PRs:

1. T-401, T-403: cleanable additions. Each gets a fixture + acceptance card.
2. T-402: hardenable addition. Patch builder + fixture + acceptance card.

This is more honest about the surface than the PLAN-v0.4 framing, but the

Each patch builder must prove idempotency. The proofs:

- `registry.command_dangling`: file-unlink. Already proven idempotent in
  v0.3 (`housekeeper.stale_lock` / `registry.local_command_identical`).
- `skills.entry_dangling`: dir-rmtree. Already proven idempotent in v0.2
  (`plugin.cache_unreferenced`).
- `hooks.config_dangling`: removes broken entries from the hooks JSON.
  Re-running removes nothing more (entry already gone). Same proof shape
  as `settings.hook_path_dangling`.

The `MUTATION_REGISTRY["json-rewrite"].preApply` runtime check from
`snapshot.mjs:830-845` covers the runtime side.

### §5.5 Tie to Q2 ruling

If Q2 ruling is (a) keep `settings-rewrite`, then `hooks.config_dangling`
ships as a new `hooks-rewrite` mutation kind — one more entry in the
registry, one more `no-mutation.test.mjs` allowlist entry, identical
shape to `settings-rewrite`.

If Q2 ruling is (b) generalize to `json-rewrite`, then
`hooks.config_dangling` just plugs in. No new mutation kind.

The architect's strong preference for (b) is partially driven by this
P4 work: shipping one new mutation kind that *behaves identically to
`settings-rewrite`* is duplicate code for no benefit. The platform memo
may have an argument that hooks JSON has a different parser
(e.g. supports a different commented-JSON dialect); if so, that's a
genuine reason for a separate kind. The architect's reading of the
existing hook files (`<plugin>/hooks/*.json`) is that they are strict JSON.

## §6 JSONC v2 (P5) deep dive

### §6.1 Why v0.3 refused JSONC and what changes in v0.4

`docs/design/v0.3-design.md §2.2` ruled REFUSE because all three available
parsers had a documented failure mode. The architect's v0.3 §5.2 analysis
said the same. v0.4 revisits with the goal of producing a *minimal-edit*
output that preserves comments and trailing commas outside the edit window.

### §6.2 Three candidates

**`jsonc-parser` (Microsoft, MIT)**

- Used by VS Code, TypeScript language server, several other Microsoft
  tools. Production-grade.
- Two relevant APIs:
  - `parse(text, errors?, options?)` — returns a strict JS value, drops
    comments. Equivalent to `JSON.parse` with comment tolerance.
  - `modify(text, path, value, options)` — returns an array of edit
    operations `[{ offset, length, content }]` that, when applied to the
    original text, produce the modified file. Comments and formatting
    outside the edit are preserved byte-for-byte.
- Pros: edit-script approach is the cleanest comment-preservation story
  available. Microsoft maintains it actively. Zero transitive
  dependencies (we verified by reading `package.json` in the repo).
- Cons: external dependency. Forces `claude-housekeeper`'s
  zero-runtime-dep posture to be revisited (see §6.5).

**`comment-json` (MIT)**

- Wraps `JSON.parse` to attach comments as non-enumerable properties on
  the parsed object, then provides a custom `stringify` that re-emits
  them.
- Pros: same parse/stringify API as native JSON. Minimal API surface.
- Cons: documented edge cases around comments inside merged objects
  (issues tracked on GitHub: comment positions can shift when keys are
  reordered or removed, since the property metadata follows the *key*
  but comment placement is text-relative). For our use case — removing
  a key from `hooks.<event>[]` — this risks moving a comment that was
  attached to a sibling key.

**Hand-rolled lex-aware patcher**

- We already have a lex-aware comment SCANNER in `audit.mjs:hasJsonComments`
  (audit.mjs:491-520). The PATCHER is the missing half.
- Pros: zero external dependency. Total control over edge cases. Reusable
  by us for future JSONC dialect quirks.
- Cons: ~300–500 LOC of new tokenizer + edit logic. We'd be writing
  what Microsoft already wrote, debugging the same edge cases.

### §6.3 Round-trip fidelity test plan (T-501)

Five fixtures, each parsed → modified → re-serialized → byte-compared:

1. **`single-line-comment.json`** — `{ "a": 1, // comment\n "b": 2 }`,
   modify `["a"]` → 99. Expected: comment preserved, only the `1` changes
   to `99`.
2. **`block-comment.json`** — `{ /* block */ "a": 1 }`, remove `["a"]`.
   Expected: block comment preserved, `"a": 1` removed cleanly (no
   trailing comma artifact).
3. **`trailing-comma.json`** — `{ "a": 1, "b": 2, }`, modify `["c"]` →
   3. Expected: trailing comma preserved, `"c": 3` appended.
4. **`mixed.json`** — `{ // line\n "a": /* inline */ 1, "b": 2 }`,
   remove `["b"]`. Expected: `// line` and `/* inline */` both
   preserved.
5. **`deeply-nested.json`** — `{ "x": { "y": { /* c */ "z": 1 } } }`,
   modify `["x", "y", "z"]` → 2. Expected: comment intact, value
   changes.

Each fixture is asserted byte-for-byte equal to a hand-authored expected
output. Failures map to refusal class `settings-jsonc-rewrite-failed`.

### §6.4 New refusal class `settings-jsonc-rewrite-failed`

Fires when the chosen parser produces a different byte output than the
identity-patch round-trip. This is a defense-in-depth guard: if the
parser ever silently mangles a comment, we refuse the operation rather
than write the mangled output.

```js
// In MUTATION_REGISTRY["json-rewrite"].preApply (extending v0.3's
// settings-rewrite preApply at snapshot.mjs:787)
if (op.parserChoice === "jsonc") {
  const identityRoundTrip = modify(source, [], parse(source));
  const reSerialised = applyEdits(source, identityRoundTrip);
  if (reSerialised !== source) {
    return new PreApplyRefusal({
      reason: "settings-jsonc-rewrite-failed",
      targetPath: op.targetPath,
      message: "JSONC round-trip is not byte-identical; refusing to mutate"
    });
  }
}
```

This guards against the failure mode where a parser bug masks a real
mutation. Cost: one extra parse + re-serialize per JSONC harden, which
on a ~10 KiB settings file is sub-millisecond.

### §6.5 Q4 — JSONC parser choice (round 2)

**Recommendation: (a) `jsonc-parser`.**

Rationale:

- **Edit-script API.** `modify()` returns offset+length edit ops. We do
  not have to re-serialize the document — we apply the edits in place.
  This is the only API of the three candidates that lets us prove
  "everything outside the edit window is byte-identical to the
  original."
- **Production track record.** Microsoft uses this in VS Code's
  `settings.json` editor — exactly our use case at a much higher
  invocation count.
- **Zero transitive dependencies.** `jsonc-parser` is its own package
  with no `dependencies` block. The runtime footprint is one ~30 KiB
  module. Acceptable.

The cost is that we go from zero runtime deps to one runtime dep. The
`docs/design/v0.3-design.md §6.2` "no runtime dependencies" stance
was *for the recovery tool to work when Claude itself is broken*. A
JSONC parser does not violate that — it does not call out to any
external service, does not depend on Node modules beyond Node's own
core, and ships as a bundled commonJS module.

(b) `comment-json` is rejected because of the documented merge edge
cases — they are exactly the cases we'd hit when removing hooks
entries.

(c) hand-rolled is rejected because the round-trip test plan (§6.3) is
where 80% of the work is, and it's hard to be more rigorous than
Microsoft's existing test suite on this.

(d) stay refused is rejected because P4's `hooks.config_dangling`
detector and P2's MCP rewrite are both more useful if they work on
JSONC files — and many real users have JSONC settings (a fact the
v0.3 platform memo's research confirmed but couldn't tie to a pinned
upstream source).

The tie-breaker should know: option (d) is the only honest fallback.
If the platform memo finds in T-D03 that `jsonc-parser` has an
issue we missed, falling back to (d) is fine. v0.4 ships without
P5; everything else still works.

## §7 Batch beyond N=50 (P6) deep dive

### §7.1 The `--stream` flag

```
housekeeper clean --batch=200 --stream --confirm --yes \
  --target=plugin.cache_unreferenced --path=... \
  --target=plugin.cache_unreferenced --path=... \
  ...
```

The parser:

- `--batch=N` without `--stream`: must satisfy N ≤ 50. Rejected otherwise.
  Existing v0.3 behaviour (cap 50, default 10).
- `--batch=N` with `--stream`: N > 50 allowed; N ≤ 50 rejected with
  `stream-chunk-budget-exceeded` (paradoxical phrasing but accurate —
  there is no chunk if N ≤ 50, so streaming is meaningless).

### §7.2 Stream plan composition — a generator

Today `composeBatchCleanPlan` (clean-plan.mjs:1019) returns one plan with
all operations. In stream mode, we instead return a generator:

```js
export async function* composeStreamCleanPlan(home, options = {}) {
  const pairs = options.pairs;
  const chunkSize = options.chunkSize || 50;
  const streamId = generateStreamId();

  // Pre-flight: run assembleReport ONCE for the full set; reuse the report
  // for every chunk's per-pair compose. Cost is paid once, not N/50 times.
  const report = assembleReport(home, { mode: options.mode || "safe" });
  // (Drift detection at execute time validates each chunk's portion of the
  // report independently — see §7.3.)

  for (let offset = 0; offset < pairs.length; offset += chunkSize) {
    const chunk = pairs.slice(offset, offset + chunkSize);
    const plan = await composeBatchCleanPlan(home, {
      pairs: chunk,
      batchCap: chunkSize
    });
    yield { streamId, chunkIndex: offset / chunkSize, plan };
  }
}
```

Each yielded plan is independently `executeBatchCleanPlan`-able. The
consumer (CLI dispatcher) iterates the generator, executes each plan,
and accumulates results.

### §7.3 Per-chunk snapshot + apply + verify state machine

```
       ┌────────────────────────────────┐
       │ for each yielded chunk plan:   │
       └──────────────┬─────────────────┘
                      │
                      ▼
         takeSnapshot (chunk's targets) → manifest at
            operations/stream_<id>/chunk_NNN.json
                      │
                      ▼
         applyOperation per-file (existing v0.3 dispatch)
                      │
              ┌───────┴───────┐
              ▼               ▼
         all applied      any failed
              │               │
              ▼               ▼
            verify        partialApply: true
              │               │
              ▼               ▼
       chunk verified    HALT STREAM
              │               │
              ▼               ▼
       continue loop     parent.json
                          streamPartial: true
                          stopChunk: NNN
```

The state machine matches the v0.3 ruling on `partialApply` (manifest-atomic,
no auto-rollback). Within a single chunk, the existing v0.3 batch semantics
apply unchanged. Across chunks, halting on the first failure preserves the
invariant that the user can roll back the *completed* chunks if they choose,
and the failed chunk remains in `applied/partialApply` state for the
interrupted-operation detector.

### §7.4 Sub-manifest schema

Under `<home>/.claude/housekeeper/operations/stream_<id>/`:

**`parent.json`** — written first, updated incrementally:

```jsonc
{
  "schemaVersion": "0.2",
  "kind": "stream-parent",
  "streamId": "stream_20260615_xxxxxxxx",
  "createdAt": "2026-06-15T...",
  "command": "clean",
  "totalPairs": 200,
  "chunkSize": 50,
  "totalChunks": 4,
  "completedChunks": ["chunk_001", "chunk_002"],
  "haltedAtChunk": null,            // chunk filename on halt; null otherwise
  "streamPartial": false,
  "status": "in_progress"           // "in_progress" | "verified" | "halted"
}
```

**`chunk_NNN.json`** — a normal v0.3 operation manifest, identical schema
to `op_<id>.json`. The opId for each chunk is `<streamId>_chunk_NNN`. This
lets `housekeeper.interrupted_operation` (audit.mjs:895) detect halted
chunks without needing a new detector — the existing detector already
walks `operations/` and surfaces non-terminal manifests.

### §7.5 Rollback semantics for a stream

A user who rolls back `stream_<id>` rolls back all completed chunks in
*reverse order*:

```
chunk_004 (verified) ───┐
chunk_003 (verified) ───┤
chunk_002 (verified) ───┼─── rollback chunk_004 → chunk_003 → chunk_002 → chunk_001
chunk_001 (verified) ───┘
```

If the stream halted, the halted chunk (status `applied`, `partialApply:
true`) gets rolled back FIRST, then the completed chunks in reverse:

```
chunk_004 (applied, partial) ─── rollback FIRST
chunk_003 (verified)           ─── then in reverse:
chunk_002 (verified)           ─── chunk_003 → chunk_002 → chunk_001
chunk_001 (verified)
```

Reverse order matters because each chunk's snapshot captures the state
*before* that chunk ran. Restoring chunk_002 first would leave chunk_003's
mutations in place but with chunk_002's pre-state — internally
inconsistent.

`composeRollbackPlan` in `rollback-plan.mjs` needs a new mode:
`composeRollbackPlan(home, { streamId })` returns a list of sub-rollback
plans, one per chunk, in reverse order. `executeRollbackPlan` runs them
serially.

### §7.6 Two new refusal classes

| Class | Reason | Trigger |
|---|---|---|
| `CleanPlanRefusal` | `stream-chunk-budget-exceeded` | `--stream` with N ≤ 50, OR any single chunk exceeds 50 files / 10 MiB after expansion |
| `CleanPlanRefusal` | `stream-resume-not-supported` | User attempts to resume a halted stream — explicit refusal because resume is deferred to v0.5 |

### §7.7 Q5 — Chunk model

Three candidates from `PLAN-v0.4.md §4 Q5`:

**(a) Fixed 50** — every chunk is exactly 50 pairs.
**(b) Adaptive shrink** — start at 50, halve on each
`SnapshotBudgetError` until under budget.
**(c) Time-bounded** — chunks sized to fit a `--max-chunk-time=<seconds>`
wall-clock budget.

**Recommendation: (a) Fixed 50.**

Rationale:

- **One chunk = one snapshot manifest under v0.3's existing 50 / 10 MiB
  budget.** The chunk size MUST be ≤ 50 because `takeSnapshot` enforces
  `MAX_OPERATION_FILES = 50` at `snapshot.mjs:28`. Fixed-50 maxes that
  out per chunk; any other model is sub-maximal.
- **Adaptive (b) breaks composability with existing batch semantics.** A
  chunk that shrinks mid-stream becomes a different kind of object than
  a v0.3 batch. The consumer would have to handle variable-size chunks
  in the parent manifest; the rollback path would need to reverse
  variable-size chunks; the interrupted-operation detector would need to
  understand variable-size chunks. Each is a small wart; together they
  add up to a different shape.
- **Time-bounded (c) doesn't compose with the budget.** A chunk fits in
  a 30-second window only by coincidence; some chunks have 50 small
  files (fast), some have 50 large files (slow). Time-bounding turns the
  chunk size into a function of file sizes, which is exactly what the
  byte-budget already does at a finer granularity.

(b) and (c) are also harder to test. Fixed-50 has one test case (full
chunk). Adaptive has 4 (full, shrunk-once, shrunk-twice, shrunk-to-1).
Time-bounded has unbounded variance.

The tie-breaker should know: the architect's argument for (a) is
operational, not philosophical. If the product memo wants variable
chunks for UX reasons (e.g. "show progress every 10 ops"), that's
display-side concern and doesn't require a different chunking model.

## §10 Risk re-evaluation

`PLAN-v0.4.md §6` lists 10 risks. After this architectural pass, the
sharpened picture:

### §10.1 Risks sharpened by this memo

**R1 (Learning append latency).** Sharpened: the 5 ms p99 bench target
in T-107 is achievable only if we avoid `fsync` on the JSONL writes.
That choice means a *missing last line* on hard crash is possible. The
architect's view: acceptable for observation data. The product memo
should consider whether to surface this in `learn --help` copy.

**R3 (MCP rewrite hostile path).** Sharpened: the per-user-owner check
(§3.4 bullet 3) is the cheapest hard boundary and should ship. The
PATH-shadowing scenario can't be fully mitigated without filesystem
ACLs we don't control; the user-owner check at least blocks
privilege-escalation.

**R7 (`json-rewrite` generalization breaks callers).** Sharpened: only
breaks if the alias is removed. v0.4 keeps `settings-rewrite` as an
alias for `json-rewrite`. v0.5 can remove the alias if telemetry shows
no callers — the architect's view: don't remove. The alias costs
nothing.

**R6 (Stream halt inconsistency).** Sharpened: the reverse-order
rollback semantic (§7.5) is non-obvious and must be documented in the
rollback contract addendum (T-700). If we forget this, a v0.5 user
could roll back chunk_002 first and corrupt the state.

### §10.2 New risks surfaced

**R11 (Learning surface ages out of relevance).** `applied.jsonl` will
contain entries from `dir-rmtree` paths that no longer exist (the
plugin cache version was deleted, the path is gone). The summary
output should not pretend these are meaningful. Mitigation: summary
collapses by detector ID, not by path; paths are only surfaced in
`--json` output where the user can filter.

**R12 (`parent.json` race during stream halt).** Two concurrent
`executeStreamCleanPlan` invocations under the same `streamId` are
impossible (lock held) — but the same `streamId` written to disk by
one process and rolled back by another *could* race on
`parent.json` updates. Mitigation: `parent.json` writes go through
`atomicWrite`; the rollback consumer reads a consistent snapshot.

**R13 (`jsonc-parser` zero-day in a network-air-gapped dependency).**
By taking a runtime dep, we accept the risk that a future
`jsonc-parser` release introduces a bug we can't avoid. Mitigation:
pin a specific version in `package.json` and the lockfile; treat
upgrades as a Phase 5 task with the round-trip fidelity test as the
acceptance gate.

**R14 (False-positive markers grow `state.json` unboundedly).** A user
who diagnoses every day for a year, marks each new false positive,
ends up with hundreds of entries in `state.json`. The `decorate`
lookup is O(N) per finding; at thousands of findings × hundreds of
markers, this is millisecond-scale and fine. But the JSON file size
grows. Mitigation: `learn --prune` covers JSONLs, should also accept
`--state` to age out marker entries past N days.

```
B9.   append refusal (if any)        learning.appendRefusal(home, {reason, detectorId, ...})
C. validate                       harden-plan.mjs::validateHardenPlan(plan, home)
C1.   re-audit, hash-equal
C2.   re-run preApply
D. execute                        harden-plan.mjs::executeHardenPlan(plan, home)
D1.   acquire lock                  +write to lock.history
D2.   takeSnapshot
D3.   applyOperation               (json-rewrite handler.apply)
D4.   verify
D5.   append applied                 learning.appendApplied(home, ...)
D6.   release lock                  +write to lock.history
E. CLI render
E1.   primary success message
E2.   reload hint                   "settings.json updated; restart Claude session for the rewritten MCP command"
```

Steps B3–B6 are the new compose-time refusals. B9 + D5 are the new
learning writes. D1 + D6 are the new lock.history writes. Everything
else is v0.3-shaped.

## §13 Decision summary — implementation order for the tie-breaker

The buildable surface area, restated in implementation order:

1. **Phase 0**: this memo + product + platform memos land; T-D04
   synthesizes into `docs/design/v0.4-design.md`.

   T-100–T-107 + T-099a. Append-only JSONL, `state.json`, `learn`

   new refusal classes + acceptance card + 10+ tests.

   (audit-only).
5. **Phase 4**: P4 three new detectors. Two cleanable (file-unlink,

This memo's three peers — product (T-D02), platform (T-D03), and
tie-breaker (T-D04) — will fill in the surface the architect explicitly

The seven load-bearing decisions are restated for the tie-breaker:

1. Learning loop is four JSONLs + one state.json, schemaVersion
   `"0.4"`.

   adds three compose-time refusal classes; ships a user-owner check as
   the hard boundary against PATH-shadowing.
3. Plugin pruning is audit-only in v0.4.0; 30-day grace; v0.4.1 ships
   mutation after a 30-day audit window of accumulated data.
4. P4 three new detectors split between cleanable (2) and hardenable
   (1); no new mutation kinds beyond Q2's ruling.
5. JSONC v2 uses `jsonc-parser`'s edit-script API; new
   `settings-jsonc-rewrite-failed` refusal class as defense-in-depth.
6. Batch streaming uses fixed-50 chunks; one snapshot manifest per
   chunk under one parent `streamId`; reverse-order rollback.
7. Mutation allowlist grows 4 → 6 in v0.4.0 (+`learning.mjs` and
   `lock-history.mjs`), 4 → 7 in v0.4.1 (+`prune-plan.mjs`).

All five Open Design Questions have proposed defaults (§9). New risks
beyond `PLAN-v0.4.md §6` are flagged in §10.2. The tie-breaker has
authority to reverse any of the above; the architect's role is to put
the strongest possible case on the table, backed by the v0.3 code.
