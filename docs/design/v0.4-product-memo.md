# Product memo — v0.4 CLI surface, refusal phrasing, and end-to-end transcripts

Author: product engineering · Companion to architect memo (T-D01), platform memo (T-D03), and tie-breaker (T-D04)
Lane: T-D02 product surface · Status: design draft, not normative until tie-breaker accepts
Decision Log reference: `notes/PLAN-v0.4.md` §4 (Q1–Q5 open at memo time)

This memo answers a different question than the architect memo. The architect
asks how the six pillars are built. This memo asks what the user types, what
they see, how refusals are phrased, and what the output formats commit to.
Where these memos disagree on user-visible surface, T-D04 resolves it before
Phase 1 starts.

v0.3 earned trust by shipping the most conservative useful `harden` verb.
v0.4 must extend that trust to three new entry points (`learn`, `prune`,
`--stream`), two new flags (`--mcp-command-rewrite=`, `--target=registry.*`
families), and a JSONC round-trip that the user specifically asked for
without fear of comment deletion.

The pattern that worked in v0.2 and v0.3: every new capability is narrower
than it sounds, backed by snapshot proof, and refuses rather than guesses
when the situation is ambiguous. v0.4 extends the same pattern.

## §1. New CLI surface inventory

### §1.1 `housekeeper learn`

New subcommand. Read-only by default; one write path (`--mark-false-positive`).

#### Synopsis

```
claude-housekeeper learn
claude-housekeeper learn --json
claude-housekeeper learn --prune --older-than=<days>
claude-housekeeper learn --mark-false-positive <op_id>
```

#### Flags

| Flag | Argument hint | Required? | Validation rules |
|---|---|---|---|
| _(no flag)_ | — | — | Prints the 30-day one-screen summary (§3) |
| `--json` | — | no | Switches output to the stable JSON schema (§3.2) |
| `--prune` | paired with `--older-than` | no | Marks records older than N days for deletion |
| `--older-than=<days>` | positive integer | required when `--prune` is set | Must be a positive integer; values ≤ 0 refuse with exit 2 |
| `--mark-false-positive` | `<op_id>` | no | Rewrites `state.json` to increment the false-positive counter for this detector |

`--prune` without `--older-than` refuses with exit 2 and the message:
> `--prune requires --older-than=<days>. No records deleted.`

`--mark-false-positive` without an op_id argument refuses with exit 2 and the message:
> `--mark-false-positive requires an operation id (e.g. op_20260612091223_b8e4f0c2). Nothing updated.`

`--mark-false-positive` combined with `--prune` refuses with exit 2:
> `--mark-false-positive and --prune cannot be combined. Run each separately.`

#### Exit codes

| Exit | Meaning |
|---|---|
| 0 | Read or write completed without error |
| 1 | Internal error (JSONL unreadable, disk full, learning directory missing and not creatable) |
| 2 | Refused — structured message on stderr |

`learn` does not require `--confirm --yes`. Its only write path (`--mark-false-positive`) marks a counter in `state.json` — not a mutation of user files — so it does not carry the double-confirmation gate. Prune (`--prune --older-than=<days>`) truncates Housekeeper's own JSONL history files and is similarly self-contained; no user file is touched.

If the learning directory does not yet exist (fresh install, no prior clean or harden runs), `learn` prints the empty-state message (§3.3) and exits 0. It does not create the directory on read-only paths.

### §1.2 `harden --mcp-command-rewrite=<old>=<new>`

Extension to the existing `harden` verb. Rewrites an MCP server `command`
field rather than stripping the entry.

#### Synopsis

```
claude-housekeeper harden --confirm --yes \
    --target=settings.mcp_command_missing \
    --path=<absolute settings.json path> \
    --mcp-command-rewrite=<old-path>=<new-path>
```

#### Argument-hint for `--mcp-command-rewrite`

`--mcp-command-rewrite=<old-path>=<new-path>`

The value is split on the first `=` after the flag separator. Both sides must be non-empty strings. The `<old-path>` must match the current `command` value in the settings file; the `<new-path>` must exist on disk and be executable.

#### Validation rules

1. Value must contain at least one `=` after the flag prefix. If not: refuse, exit 2, `mcp-rewrite-source-not-found`.
2. `<old-path>` must match the `command` field of at least one `mcpServers` entry in the target settings file. If not: refuse, exit 2, `mcp-rewrite-source-not-found`.
3. `<new-path>` must exist on disk (`existsSync`). If not: refuse, exit 2, `mcp-rewrite-target-missing`.
4. `<new-path>` must be executable (mode `+x`). If not: refuse, exit 2, `mcp-rewrite-target-not-executable`.
5. All other pre-apply checks from `harden` apply unchanged (JSONC detection, shape validation, idempotency, valid-JSON post-patch).

Without `--mcp-command-rewrite`, `harden --target=settings.mcp_command_missing --confirm --yes` continues to remove the broken entry (v0.3 behavior). The new flag is additive: pass it to rewrite instead of remove.

#### Exit codes

Same as `harden` in v0.3: 0 (verified), 1 (internal error), 2 (refused).

### §1.3 `housekeeper prune`

New subcommand. **Audit-only in v0.4.0**. Mutation ships in v0.4.1.

#### Synopsis

```
claude-housekeeper prune
claude-housekeeper prune --json
```

#### Behavior (v0.4.0)

Runs the `plugin.unused_past_grace` detector, formats the results as a
table, and exits. No files are removed. The command makes this explicit at
the top of its output:

```
HOUSEKEEPER PRUNE (audit only — v0.4.0 does not remove plugins)
```

Mutation flags (`--confirm`, `--yes`) are parsed and rejected in v0.4.0:

> `housekeeper prune --confirm is not available in v0.4.0. Plugin removal ships in v0.4.1.`
> Exit 2.

This prevents users from running a mutation that does not yet exist and
expecting it to work.

#### Flags

| Flag | Argument hint | Required? | Notes |
|---|---|---|---|
| `--json` | — | no | Stable JSON output (same envelope shape as `diagnose --json`) |
| `--home=<path>` | absolute path | no | Same as `diagnose` |
| `--config=<path>` | absolute path | no | Same as `diagnose` |

#### Exit codes

| Exit | Meaning |
|---|---|
| 0 | Audit complete (zero or more findings reported) |
| 1 | Internal error |
| 2 | Refused (mutation flags passed) |

### §1.4 `harden --target=registry.*` / `--target=hooks.*` / `--target=skills.*`

Extension to `harden` that accepts three new target families.

| Target id | What it patches |
|---|---|
| `registry.command_dangling` | Removes entries from the local command registry whose plugin is not installed |
| `hooks.config_dangling` | Patches hook config entries with a missing `cwd` or `command` field |
| `skills.entry_dangling` | Removes entries from the skill index whose skill file is missing |

These targets use the same `harden --confirm --yes --target=<id> --path=<file>` syntax as v0.3 settings targets. The `--mcp-command-rewrite` flag is not valid for these targets; passing it alongside a non-settings target refuses with exit 2:

> `--mcp-command-rewrite is only valid with --target=settings.mcp_command_missing. Nothing written.`

No new flags are introduced for P4 targets. The consent gate, snapshot contract, and rollback path are identical to the v0.3 `settings-rewrite` flow.

### §1.5 `clean --batch=<n> --stream`

Extension to the existing `clean --batch` surface. Adds `--stream` for
batches larger than 50.

#### Synopsis

```
claude-housekeeper clean --confirm --yes \
    --batch=<n> \
    --stream \
    --target=<id> --path=<path> \
    [--target=<id> --path=<path> ...]
```

#### New flag: `--stream`

| Flag | Required? | Validation rules |
|---|---|---|
| `--stream` | no | Only valid when `--batch=<n>` is also set; refuses if used alone. `n` must be > 50; values ≤ 50 without `--stream` follow the v0.3 path unchanged. |

`--stream` without `--batch` refuses with exit 2:
> `--stream requires --batch=<n>. Nothing written.`

`--stream` with `--batch=<n>` where `n ≤ 50` refuses with exit 2:
> `--stream is only needed when --batch exceeds 50. For n ≤ 50, omit --stream.`

The maximum value of `n` with `--stream` is not hard-capped by a fixed number in v0.4.0; the chunking model (Q5) is the limit. If the architect memo selects fixed-50-chunk (Q5 option a), then the practical limit is however many chunks fit in the 10-MiB aggregate per-chunk budget.

#### Interaction with `--dry-run`

`--dry-run` with `--stream` prints the planned chunks without snapshotting or applying. Each chunk is listed with its item count and estimated bytes.

#### Exit codes

| Exit | Meaning |
|---|---|
| 0 | All chunks verified |
| 1 | Internal error (mid-stream crash, snapshot fs failure) |
| 2 | Refused (stream-specific refusal classes, see §2) |
| 124 | `--timeout` deadline exceeded (matches `timeout(1)` convention, existing) |

## §2. Refusal phrasing and nextStep copy

All refusal classes follow the v0.3 pattern from `scripts/lib/clean-plan.mjs`
`NEXT_STEP_BY_REASON`. Each carries: `class`, `reason`, `targetPath`,
`detectorId`, `message`, `nextStep`, `exitCode: 2`. The `nextStep` field
is non-empty for every reason — the G7 invariant.

No refusal message uses internal vocabulary (`ownerClass`, `executionClass`,
`rollbackClass`, `surface classification`). No refusal message uses the
forbidden phrases from `test/forbidden-language.test.mjs`:
"safe to delete", "safe cleanup", "auto-fix", "guaranteed rollback",
"deletion-ready", "definitely unused", "optimized", "clean bill of health",
"fixed everything", "rollback guaranteed".

### §2.1 MCP rewrite refusal classes

#### `mcp-rewrite-source-not-found`

The `<old-path>` value passed to `--mcp-command-rewrite` does not match any
`command` field in the target settings file.

**Rendered:**

```
REFUSED
  detector:   settings.mcp_command_missing
  target:     /Users/mara/.claude/settings.json
  reason:     mcp-rewrite-source-not-found
  message:    --mcp-command-rewrite source path "/old/path/to/server" does not
              match the command field of any mcpServers entry in settings.json
  nextStep:   Run diagnose to see the exact command path recorded in the
              failing MCP entry, then pass that exact string as the source
              side of --mcp-command-rewrite=<source>=<new-path>.
```

**JSON:**

```json
{
  "class": "HardenPlanRefusal",
  "reason": "mcp-rewrite-source-not-found",
  "targetPath": "/Users/mara/.claude/settings.json",
  "detectorId": "settings.mcp_command_missing",
  "message": "--mcp-command-rewrite source path \"/old/path/to/server\" does not match the command field of any mcpServers entry in settings.json",
  "nextStep": "Run diagnose to see the exact command path recorded in the failing MCP entry, then pass that exact string as the source side of --mcp-command-rewrite=<source>=<new-path>.",
  "exitCode": 2
}
```

---

#### `mcp-rewrite-target-missing`

The `<new-path>` passed to `--mcp-command-rewrite` does not exist on disk.

**Rendered:**

```
REFUSED
  detector:   settings.mcp_command_missing
  target:     /Users/mara/.claude/settings.json
  reason:     mcp-rewrite-target-missing
  message:    --mcp-command-rewrite new path "/new/path/to/server" does not
              exist on disk; harden will not write a path that cannot be verified
  nextStep:   Confirm the correct path to your MCP server binary or script,
              then re-run harden with the corrected --mcp-command-rewrite value.
```

---

#### `mcp-rewrite-target-not-executable`

The `<new-path>` exists but lacks execute permission.

**Rendered:**

```
REFUSED
  detector:   settings.mcp_command_missing
  target:     /Users/mara/.claude/settings.json
  reason:     mcp-rewrite-target-not-executable
  message:    --mcp-command-rewrite new path "/new/path/to/server" exists
              but is not executable; harden will not write a non-executable
              MCP server command
  nextStep:   Run chmod +x /new/path/to/server and then re-run harden, or
              confirm you have passed the correct path.
```

### §2.2 Prune refusal class

#### `prune-history-unavailable`

The shell history file could not be read (missing, permission denied, or
binary format). The finding is still emitted, but the `historyAvailable`
field is set to `false` to indicate the activity signal is incomplete.

This is an **informational accompaniment** to a `plugin.unused_past_grace`
finding, not a standalone refusal that blocks the output. It renders as a
note inside the prune table row rather than a top-level `REFUSED` block.

**Rendered in prune table:**

```
  note:     shell history not readable — activity check incomplete
            (historyAvailable: false). The plugin appears inactive based
            on learning records, but shell usage could not be confirmed.
  nextStep: If you use this plugin from the shell, confirm before treating
            it as a candidate for removal. Run with --json to see the full
            activity evidence record.
```

The `nextStep` does not suggest a command that does not exist in v0.4.0
(removal requires v0.4.1). The wording is forward-neutral.

### §2.3 Stream refusal classes

#### `stream-chunk-budget-exceeded`

A single chunk's snapshot or apply would exceed the 10-MiB per-chunk
budget. The stream halts at this chunk; completed prior chunks are not
rolled back automatically.

**Rendered:**

```
REFUSED (stream halted at chunk 3 of 6)
  reason:     stream-chunk-budget-exceeded
  message:    chunk 3 estimated size 12.4 MiB exceeds the per-chunk budget
              of 10 MiB; stream halted before this chunk was applied
  nextStep:   Completed chunks (1–2) remain applied. Run
              `rollback <stream-parent-id> --confirm --yes` to restore
              completed chunks, or leave them and re-run with a smaller
              --batch size to process the remaining findings individually.
  streamId:   stream_20260718134500_a1b2c3d4
  chunksCompleted: 2
  chunksTotal: 6
```

**JSON:**

```json
{
  "class": "StreamRefusal",
  "reason": "stream-chunk-budget-exceeded",
  "message": "chunk 3 estimated size 12.4 MiB exceeds the per-chunk budget of 10 MiB; stream halted before this chunk was applied",
  "nextStep": "Completed chunks (1–2) remain applied. Run rollback <stream-parent-id> --confirm --yes to restore completed chunks, or leave them and re-run with a smaller --batch size.",
  "streamId": "stream_20260718134500_a1b2c3d4",
  "chunksCompleted": 2,
  "chunksTotal": 6,
  "exitCode": 2
}
```

---

#### `stream-resume-not-supported`

A user passes a `--resume=<stream-id>` flag that does not exist in v0.4.0.
Stream resume is deferred to v0.5.

**Rendered:**

```
REFUSED
  reason:     stream-resume-not-supported
  message:    stream resume is not available in v0.4. If a prior stream
              halted mid-run, use rollback to restore completed chunks and
              re-run the full batch from the beginning.
  nextStep:   Run `housekeeper diagnose` to see current state, then
              `rollback <stream-parent-id> --confirm --yes` to undo
              completed chunks if desired.
```

This refusal also fires if the user passes `--stream --resume=` (the v0.5
flag shape is blocked at parse time with a clear explanation rather than an
opaque "unknown argument" error).

### §2.4 JSONC v2 refusal class

#### `settings-jsonc-rewrite-failed`

Replaces `settings-jsonc-detected` from v0.3. In v0.4, JSONC files are
attempted via the chosen parser. If the round-trip diverges (parsed output
does not match the byte-for-byte reconstruction expected by the fidelity
test), harden refuses with this class instead of proceeding with a lossy
write.

**Rendered:**

```
REFUSED
  detector:   settings.hook_path_dangling
  target:     /Users/mara/.claude/settings.json
  reason:     settings-jsonc-rewrite-failed
  message:    JSONC round-trip check failed: the parser could not reconstruct
              settings.json byte-for-byte after parsing; harden will not write
              output that diverges from the original formatting
  nextStep:   The specific formatting feature that caused divergence has been
              logged to the operation attempt record. You can strip the comments
              from settings.json by hand and re-run harden, or file an issue
              with the divergence log attached.
```

Unlike the v0.3 `settings-jsonc-detected` refusal (which refused all JSONC
files unconditionally), `settings-jsonc-rewrite-failed` is the fallback for
JSONC files that the parser cannot round-trip cleanly. Plain JSONC that the
parser handles correctly proceeds to apply without this refusal.

The v0.3 refusal class `settings-jsonc-detected` is **deprecated** but not
removed from the taxonomy. Files that were surfacing `settings-jsonc-detected`
in v0.3 will now surface one of two outcomes: either the patch applies (JSONC
was round-trippable) or `settings-jsonc-rewrite-failed` fires (JSONC was not
round-trippable). No user file is touched in the failure case.

### §2.5 Registry, hooks, and skills refusal classes

These reuse the existing refusal taxonomy wherever the semantics carry over:

- `plan-state-error` — an interrupted operation is present; run `rollback` first.
- `protected-path` — the registry file or hook config is under a `doNotTouch` rule.
- `no-mutation-mapping-in-v0.4` — a target id not in the v0.4 hardenable set.

New refusal specific to P4:

#### `json-rewrite-shape-unknown`

The target file (registry, hook config, or skills index) does not match the
expected top-level shape for that file type. The rewrite refuses rather than
patching an unrecognized structure.

**Rendered:**

```
REFUSED
  detector:   registry.command_dangling
  target:     /Users/mara/.claude/registry.json
  reason:     json-rewrite-shape-unknown
  message:    registry.json top-level shape does not match the documented
              format; harden will not write to an unrecognized structure
  nextStep:   Compare registry.json to the documented schema. If the file
              has been hand-edited into an unsupported shape, restore the
              expected structure before re-running harden.
```

## §3. Learning summary output format

### §3.1 `housekeeper learn` no-args output (30-day one-screen summary)

The no-args output is designed to fit on one terminal screen (80×40 baseline).
Section ordering is fixed:

1. Header with date range
2. Top-5 refusal classes by 30-day count
3. Top-5 cleaned detectors by 30-day count
4. Last-10 rollbacks
5. False-positive count and marked operations
6. Footer (prune hint if records are older than 30 days)

**Shape:**

```
HOUSEKEEPER LEARN
30-day window: 2026-04-17 – 2026-05-17

TOP REFUSAL CLASSES (last 30 days)
  settings-jsonc-detected          14 occurrences
  mcp-rewrite-target-missing        6 occurrences
  settings-shape-unknown            3 occurrences
  budget-exceeded-batch             2 occurrences
  patch-not-idempotent              1 occurrence

TOP CLEANED DETECTORS (last 30 days)
  plugin.cache_unreferenced        31 operations (29 verified, 2 rolled back)
  registry.local_command_identical  4 operations (4 verified, 0 rolled back)
  settings.hook_path_dangling       3 operations (3 verified, 0 rolled back)
  housekeeper.stale_lock            2 operations (2 verified, 0 rolled back)
  skills.entry_dangling             1 operation  (1 verified, 0 rolled back)

LAST 10 ROLLBACKS
  op_20260515102301_a1b2c3d4  plugin.cache_unreferenced       rolled_back  2026-05-15
  op_20260512083412_e5f6a7b8  settings.hook_path_dangling     rolled_back  2026-05-12
  op_20260501141500_c9d0e1f2  registry.local_command_identical rolled_back 2026-05-01
  (no further rollbacks in window)

FALSE POSITIVES
  2 operations marked as false positives
  op_20260503121000_b3c4d5e6  settings.mcp_command_missing  marked 2026-05-03
  op_20260428094500_f7a8b9c0  plugin.cache_unreferenced     marked 2026-04-28

HINT
  14 refusals for settings-jsonc-detected. If you use JSONC in settings.json,
  v0.4 now supports comment-preserving rewrites for many common patterns.
  Run diagnose to see if your file is now hardenable.

To prune records older than 90 days:
  claude-housekeeper learn --prune --older-than=90
```

**Formatting rules:**

- Columns are aligned with two-space separators; no box-drawing characters.
- Counts use singular "occurrence" / "operation" when count is 1.
- The rollbacks section shows at most 10 entries, oldest first within the
  window.
- The HINT section appears only when a refusal class accounts for ≥ 10
  occurrences and there is a relevant v0.4 capability to mention. If no
  refusal meets the threshold, the section is omitted.
- The prune hint appears only when records exist outside the 30-day summary
  window.

### §3.2 `--json` schema

The `--json` schema is the stable contract. Field names must not change
without a `learnSchemaVersion` bump. The schema carries its own version
field separate from the report schema and the operation manifest schema,
per the Q1 recommendation in §7.

```json
{
  "learnSchemaVersion": "0.4",
  "generatedAt": "2026-05-17T14:00:00.000Z",
  "windowDays": 30,
  "windowStart": "2026-04-17T00:00:00.000Z",
  "windowEnd": "2026-05-17T00:00:00.000Z",
  "topRefusalClasses": [
    { "reason": "settings-jsonc-detected", "count": 14 },
    { "reason": "mcp-rewrite-target-missing", "count": 6 },
    { "reason": "settings-shape-unknown", "count": 3 },
    { "reason": "budget-exceeded-batch", "count": 2 },
    { "reason": "patch-not-idempotent", "count": 1 }
  ],
  "topCleanedDetectors": [
    {
      "detectorId": "plugin.cache_unreferenced",
      "count": 31,
      "verified": 29,
      "rolledBack": 2
    },
    {
      "detectorId": "registry.local_command_identical",
      "count": 4,
      "verified": 4,
      "rolledBack": 0
    }
  ],
  "lastRollbacks": [
    {
      "opId": "op_20260515102301_a1b2c3d4",
      "detectorId": "plugin.cache_unreferenced",
      "rolledBackAt": "2026-05-15T10:23:05.000Z"
    }
  ],
  "falsePositives": {
    "count": 2,
    "operations": [
      {
        "opId": "op_20260503121000_b3c4d5e6",
        "detectorId": "settings.mcp_command_missing",
        "markedAt": "2026-05-03T12:10:01.000Z"
      }
    ]
  },
  "pruneHint": {
    "recordsOutsideWindow": true,
    "oldestRecord": "2026-01-04T09:15:00.000Z"
  }
}
```

**Stable field names (contract):**

- `learnSchemaVersion` — string, own versioning line
- `generatedAt` — ISO 8601
- `windowDays`, `windowStart`, `windowEnd`
- `topRefusalClasses[].reason`, `topRefusalClasses[].count`
- `topCleanedDetectors[].detectorId`, `.count`, `.verified`, `.rolledBack`
- `lastRollbacks[].opId`, `.detectorId`, `.rolledBackAt`
- `falsePositives.count`, `falsePositives.operations[].opId`, `.detectorId`, `.markedAt`

Fields that may be added in future minor versions without a schema bump:
array members under `topRefusalClasses`, `topCleanedDetectors`, `lastRollbacks`
(new entries are additive). New top-level fields require a `learnSchemaVersion`
bump.

### §3.3 Empty-state behavior

When no learning records exist (directory absent or all JSONL files empty):

```
HOUSEKEEPER LEARN
No activity recorded yet.

Housekeeper records refusals, applied operations, and rollbacks automatically
as you use clean, harden, and rollback. Run diagnose to get started.

No records to prune.
```

Exit 0. No error. The empty state is a normal condition on a fresh install or
when the learning directory has been pruned to zero.

With `--json`:

```json
{
  "learnSchemaVersion": "0.4",
  "generatedAt": "2026-05-17T14:00:00.000Z",
  "windowDays": 30,
  "windowStart": "2026-04-17T00:00:00.000Z",
  "windowEnd": "2026-05-17T00:00:00.000Z",
  "topRefusalClasses": [],
  "topCleanedDetectors": [],
  "lastRollbacks": [],
  "falsePositives": { "count": 0, "operations": [] },
  "pruneHint": { "recordsOutsideWindow": false, "oldestRecord": null }
}
```

## §4. CHANGELOG shape for v0.4.0

The v0.4.0 entry follows the Keep-a-Changelog format established in
`CHANGELOG.md` and mirrored in the v0.3.0 entry shape from the v0.3
product memo §5.

```markdown
## [0.4.0] — 2026-XX-XX

First release of the v0.4 line. Adds the learning loop (`housekeeper learn`),
MCP command rewriting (`harden --mcp-command-rewrite`), plugin pruning audit
(`housekeeper prune`), three non-settings harden targets (`registry.*`,
`hooks.*`, `skills.*`), comment-preserving JSONC rewrite (P5), and stream
batching for N > 50 (`clean --batch=<n> --stream`). NNN tests across the
Ubuntu + macOS × Node 20 + 22 matrix.

### Added

- **`housekeeper learn` subcommand.** Read-only 30-day summary of
  refusals, applied operations, rollbacks, and false-positive markers.
  `--json` outputs a stable schema (`learnSchemaVersion: "0.4"`).
  `--prune --older-than=<days>` trims Housekeeper's own JSONL history.
  `--mark-false-positive <op_id>` records a false-positive signal in
  `state.json` for a past operation.
- **`harden --mcp-command-rewrite=<old>=<new>`.**  Rewrites an MCP
  server `command` field in `settings.json` instead of stripping the
  entry. Three new refusal classes: `mcp-rewrite-source-not-found`,
  `mcp-rewrite-target-missing`, `mcp-rewrite-target-not-executable`.
  Requires `--target=settings.mcp_command_missing`.
- **`housekeeper prune` subcommand (audit-only in v0.4.0).** Lists
  plugins past the configured grace window with zero activity in
  learning records and shell history. No files are removed; mutation
  ships in v0.4.1. New refusal accompaniment: `prune-history-unavailable`
  (informational, not a blocking refusal).
```

### §6.2 New FAQ entries

**Why does `housekeeper prune` not remove anything?**
`housekeeper prune` is audit-only in v0.4.0. The audit-first approach lets
Housekeeper validate the grace-window heuristic against real usage before
risking unintended removal. Plugin removal behind snapshot protection ships
in v0.4.1 once the v0.4.0 audit window provides enough signal.

**How do I rewrite an MCP server command instead of removing it?**
Use `harden --mcp-command-rewrite=<old-path>=<new-path>` with
`--target=settings.mcp_command_missing`. The source path must match the
current `command` field in your settings.json exactly. The new path must
exist on disk and be executable. Run with `--dry-run` first to preview the
patch as a unified diff before applying.

**What does `housekeeper learn` show?**
A 30-day one-screen summary: the top refusal classes (why harden or clean
refused), the top cleaned detectors (what was actually removed), the last
ten rollbacks, and false-positive markers you have applied. It does not make
recommendations — the suggestion engine ships in v0.5. Use `--json` to pipe
the summary to other tools.

**Why does `--stream` refuse with `--batch=50` or less?**
`--stream` enables chunked processing for batches larger than 50. For 50 or
fewer findings, the standard `--batch=<n>` path (v0.3) applies without
chunking. Adding `--stream` to a batch of 50 or fewer is a no-op that
would make the output misleading, so harden refuses it with a clear message.

**Why does JSONC rewrite still fail on some settings files?**
v0.4 adds comment-preserving JSONC support using a parser that preserves the
AST through a round-trip. For some JSONC patterns the parser cannot
reconstruct the original formatting byte-for-byte, and harden refuses with
`settings-jsonc-rewrite-failed` to avoid writing output that diverges from
your original file. The specific pattern that caused divergence is logged to
the operation attempt record. Stripping comments by hand and saving as plain
JSON remains the fallback path that works in all cases.

## §7. Open questions for T-D04

### Q1 — Learning schema versioning

**Product position:** Use a separate `learnSchemaVersion: "0.4"` field on
`state.json` and in `--json` output. Do not reuse the operation manifest
`schemaVersion: "0.2"` or the report `schemaVersion: "0.1"`.

**Rationale:** Three independent schema lines (`"0.1"` for diagnose reports,
`"0.2"` for operation manifests, `"0.4"` for learning summary JSON) prevents
a future bump in any one from forcing a bump in the others. The product surface
for `learn --json` has different field shapes and evolution cadence than
operation manifests. Coupling them would make it harder to add learning fields
without touching the manifest contract.

**User-visible impact of Q1:** The `learnSchemaVersion` field name appears in
`--json` output and is therefore user-visible. It should not appear in the
human-readable summary output (§3.1). The tie-breaker should confirm that
`learnSchemaVersion` is the right name (not `schemaVersion`, which would
conflict with the other schemas).

---

### Q3 — Prune grace window default

**Product position:** 30 days (option a), matching the plugin cache GC grace
window already documented in `README.md §FAQ`.

**Rationale:** Users already have a mental model of 7 days (plugin cache
`plugin.expected_orphan` grace) and 30 minutes (stale lock grace). Prune
operates on a longer lifecycle (plugin install → disuse → removal candidate)
and the 30-day window matches what users have seen in the FAQ. A 90-day
default (option c) would delay audit findings so long that users would get no
signal from `housekeeper prune` for months after a fresh install. Requiring
explicit config (option d) adds friction with no safety benefit — the audit
is read-only in v0.4.0 anyway.

**What users see:** The prune table column header reads `GRACE` and shows the
configured window alongside the expiry date. The config key name should be
confirmed by the architect memo; the product surface just needs a human-readable
label.

---

### Q4 — JSONC parser choice and FAQ impact

**Product position:** No preference between `jsonc-parser` (option a) and
`comment-json` (option b) — that is an architect and platform decision. The
product constraint is:

1. The refusal message `settings-jsonc-rewrite-failed` must fire when
   round-trip diverges, regardless of which parser is chosen.
2. The user-facing FAQ entry must not name the parser library (that is an
   implementation detail).

**Proposed FAQ wording (parser-neutral):**

> "Housekeeper uses a comment-preserving JSONC parser that reconstructs your
> file through a read-parse-serialize round-trip. For some uncommon JSONC
> patterns (certain trailing comma positions, nested block comments, or
> multi-line string edge cases) the round-trip output diverges from the
> original formatting. In those cases harden refuses rather than writing
> output that changes your file beyond the intended patch."

The FAQ should not say "this will be fixed" without a version commitment. The
wording above describes the behavior without over-promising.

**Impact on `settings-jsonc-detected` deprecation timeline:** If T-D04 selects
option (d) (stay refused, revisit v0.5), then `settings-jsonc-detected` is not
deprecated in v0.4.0 and the CHANGELOG section §4 should drop the Deprecated
row. The product memo is written assuming option (a) or (b) wins; if (d) wins,
the product surface for P5 collapses to zero and the CHANGELOG section is
revised accordingly.

### Additional product-side questions for T-D04

**P1: Does `housekeeper prune` inherit `--safe`?**
If `--safe` is passed, the prune command should skip the shell history scan
(because history reading could be considered a live probe) and emit
`historyAvailable: false` for all plugins. The product position is yes —
`prune --safe` scans learning records only, not shell history. The architect
memo should confirm whether the shell history scan is within the `--safe`
boundary.

**P2: Should `housekeeper learn` decorate `diagnose` output?**
The plan notes that `diagnose` should decorate matching findings with
`falsePositiveSeenBefore: N`. The product question is where this appears in
the human-readable report. This memo proposes: a new line under the finding's
`evidence` block, only when `N > 0`, reading:
> `false-positive signal: N previous operations marked as false positive for this detector`

The decoration should not change the stance or the ranking. It is informational
only — a reminder, not a recommendation.

**P3: Should the stream rollback accept the `streamId` or require individual
chunk `opId`s?**
The product position is: accept both. `rollback stream_<id> --confirm --yes`
rolls back all completed chunks in reverse order (chunk 2 first, then chunk 1).
`rollback op_<id>` for an individual chunk op id rolls back that chunk only.
This mirrors the principle of keeping user agency — users who want to undo
only one chunk can do so without undoing the rest.
