## §1 v0.4 buildable spec — synthesis overview

v0.4 ships six pillars in TASKBOARD order. **P1 (learning loop) lands first
because P2/P3/P4 write to its files; P5 (JSONC v2) unblocks any home with
comments in `settings.json`; P6 (`--stream`) is the final gate before release
prep.** The cross-pillar carry-overs from v0.2 readiness (N5 marketplace prep,
N6 lock-history JSONL, N8 forbidden-language pre-commit hook) land alongside
the six pillars without expanding the schema contract.

The six pillars, in resolved form:

| Pillar | Status after T-D04 | User-visible surface |
|---|---|---|
| P1. Learning loop | Schema field `learnSchemaVersion: "0.4"` per JSONL line (Q1); four append-only JSONL files plus one mutable `state.json` under `<home>/.claude/housekeeper/learning/`; lock-history append-only JSONL `lock.history` at the same per-line schema (N6 carry-over) | `housekeeper learn`, `learn --json`, `learn --prune --older-than=<days>`, `learn --mark-false-positive <op_id>`; passive writes from every clean/harden/rollback |
| P2. MCP rewrite beyond stripping | New flag `--mcp-command-rewrite=<old>=<new>` on `harden`; **five** new compose-time refusal classes (target-missing, target-not-executable, source-not-found, malformed-arg, foreign-owner per item 6); routes through generalised `json-rewrite` per Q2 | `harden --confirm --yes --target=settings.mcp_command_missing --path=<settings> --mcp-command-rewrite=<old>=<new>` |
| P3. Plugin prune (audit-only) | New detector `plugin.unused_past_grace` at `inform` stance; 30-day default grace (Q3); `pruneGraceDays` additive config field (item 5); shell-history fallback emits `prune-history-unavailable` accompaniment when unreadable | new `housekeeper prune` subcommand, audit-only in v0.4.0; v0.4.1 will add `--confirm --yes` for mutation |
| P4. Non-settings surfaces | **Split lane** per Conflict A: `hooks.config_dangling` is JSON-rewrite under `harden`; `registry.command_dangling` is filesystem `file-unlink` under `clean`; `skills.entry_dangling` is filesystem `dir-rmtree` or `file-unlink` under `clean` | `harden --target=hooks.config_dangling`; `clean --target=registry.command_dangling`; `clean --target=skills.entry_dangling` |
| P5. JSONC v2 | Adopt `jsonc-parser` (Microsoft, MIT, zero runtime deps) (Q4); `modify()` + `applyEdits()` edit-script API; `settings-jsonc-detected` deprecated; new refusal `settings-jsonc-rewrite-failed` only on round-trip divergence | comment-preserving `harden` against `settings.json` with `//` and `/* */` |
| P6. Batch `--stream` | Fixed 50-item chunks (Q5); one snapshot manifest per chunk under a shared `streamId`; parent manifest records `streamPartial: true` on halt; stream rollback by `streamId` (reverse-order) or per-chunk `opId` (item P3) | `clean --batch=<n> --stream --confirm --yes`; `housekeeper rollback --stream=<id>` |

Six independently-shippable pillars, **eleven** new refusal classes, **one**
new mutation kind (`json-rewrite`, with `settings-rewrite` aliased to it), one
new top-level subcommand (`learn`), one new audit-only subcommand (`prune`),
**no** operation-manifest schema bump (stays at `"0.2"`), no report schema
bump (stays at `"0.1"`), one **new** schema line (`learnSchemaVersion: "0.4"`)
for the learning + lock-history surfaces.

The `MUTATION_ALLOWLIST` in `test/no-mutation.test.mjs` grows **4 → 6** in
v0.4.0 (adding `scripts/lib/learning.mjs` and `scripts/lib/lock-history.mjs`)
and projects to **4 → 7** in v0.4.1 (adding `scripts/lib/prune-plan.mjs` when
plugin mutation ships). The v0.4.0 growth is the cross-pillar
schema-stability tripwire flagged by the architect (`v0.4-architect-memo.md
§8.3`).

## §3 Resolved pipeline contracts (per pillar — deep)

### §3.1 P1 — Learning loop

**On-disk layout** under `<home>/.claude/housekeeper/learning/`:

| File | Append protocol | Schema field |
|---|---|---|
| `refusals.jsonl` | One line per compose-time refusal from `composeCleanPlan` / `composeBatchCleanPlan` / `composeHardenPlan`. `O_APPEND` + single `write(2)` is atomic on POSIX up to `PIPE_BUF` (512 bytes macOS, 4096 Linux); records sized to fit (`v0.4-platform-memo.md §1.6`, `v0.4-architect-memo.md §2.1`) | `learnSchemaVersion: "0.4"` on every line |
| `applied.jsonl` | One line per terminal manifest at `verified` or `applied+partialApply`. Append happens after manifest is closed. | same |
| `rollbacks.jsonl` | One line per terminal rollback (`reverted`, `aborted`) — userInitiated flag reserved for v0.5 auto-rollback. | same |
| `state.json` | Counters (`refusalsLast30d`, `appliedLast30d`, etc., plus all-time totals) + last-N false-positive markers keyed by `{detectorId, evidenceHash}`. Rewritten in place via atomic write-temp + rename + fsync, reusing `snapshot.mjs:217` `atomicWrite` helper. | same |

**Write path.** `composeCleanPlan` / `composeBatchCleanPlan` /
`composeHardenPlan` call `appendRefusal()` per refusal they emit; the executors
call `appendApplied()` after the manifest is terminal; `executeRollbackPlan` /
`abortRollbackOperation` call `appendRollback()` on terminal state.
**Compose-time writes happen WITHOUT the housekeeper lockfile held** — compose
is read-only in v0.3 and we preserve that contract (per
`v0.4-architect-memo.md §2.2`). Execute-time and rollback writes happen inside
the lock window. POSIX `O_APPEND` atomicity makes the lock-free compose-time
write safe up to `PIPE_BUF`.

**Lock-history relationship (N6 carry-over, T-099a).**
`<home>/.claude/housekeeper/lock.history` is a sibling JSONL appended by
`acquireLock` / `releaseLock` in `scripts/lib/clean-plan.mjs:827`,
`scripts/lib/clean-plan.mjs:882`, `scripts/lib/harden-plan.mjs:538`, and
`scripts/lib/harden-plan.mjs:588` (per the architect's call-site enumeration
in `v0.4-architect-memo.md §8.4`). Each entry:
`{learnSchemaVersion: "0.4", ts, pid, hostname, action, holderOpId, releaseReason?}`.
Same append protocol, same per-line schema. Lives outside `learning/` because
lock events predate any mutation lane and are independently truncatable via
`learn --prune --lock-history --older-than=<days>`.

**Read path.**

- `housekeeper learn` (no args) — one-screen 30-day summary per `v0.4-product-memo.md §3.1`:
  - Top 5 refusal classes by 30-day count
  - Top 5 cleaned-detector IDs by 30-day count (verified vs rolled-back broken out)
  - Last 10 rollbacks (op_id + detectorId + timestamp)
  - False-positive marker count + last marked operations
  - Optional HINT section when a refusal class crosses 10 occurrences with a v0.4 capability to mention
  - Footer prune-hint when records exist outside the 30-day window
- `housekeeper learn --json` — `v0.4-product-memo.md §3.2` defines the stable contract: `learnSchemaVersion`, `generatedAt`, `windowDays`, `windowStart`, `windowEnd`, `topRefusalClasses[].{reason,count}`, `topCleanedDetectors[].{detectorId,count,verified,rolledBack}`, `lastRollbacks[].{opId,detectorId,rolledBackAt}`, `falsePositives.{count,operations[]}`, `pruneHint.{recordsOutsideWindow,oldestRecord}`.
- `housekeeper learn --prune --older-than=<days>` — truncate JSONL to entries newer than threshold; default never. Read-modify-write of an append-only file uses the same write-temp + rename + fsync-parent protocol per `v0.4-platform-memo.md §3.4`. Refuses `--older-than=0` with `learn-prune-threshold-zero`.
- `housekeeper learn --mark-false-positive <op_id>` — rewrite `state.json` via `atomicWrite`; idempotent re-mark on the same `op_id` is a no-op (verified by T-106).

**Diagnose decoration (T-105).** `falsePositiveSeenBefore: N` is a top-level
optional field on the finding object (item P2 ruling). Present only when
`state.json` shows the same `detectorId + evidenceHash` pair has been marked.
No stance change, no ranking change in v0.4 (suggestion engine = v0.5). Read
of `state.json` happens once per `assembleReport` in `loadContext`; the
in-memory map is keyed by `evidenceHash` for O(1) lookup at finding-build
time.

**Empty-state behavior** (`v0.4-product-memo.md §3.3`): `learn` with no
records prints "No activity recorded yet." and exits 0; `--json` returns
`{ ..., topRefusalClasses: [], topCleanedDetectors: [], ... }`. The empty
state is a normal condition on a fresh install.

**Invariants.**
- JSONL is append-only; truncation only via `learn --prune`.
- Same redaction posture as `diagnose --redact` (`redactedTargetPath` computed *at write time* per architect §2.1 so the read path can honor `--redact` without re-running the scrubber against millions of lines).
- No `fsync` on JSONL writes (per architect §2.4 perf budget); missing last line on hard crash is acceptable for observational data.

### §3.2 P2 — MCP rewrite beyond stripping

**CLI surface** (`v0.4-product-memo.md §1.2`):
```
harden --confirm --yes \
    --target=settings.mcp_command_missing \
    --path=<absolute settings.json path> \
    --mcp-command-rewrite=<old-path>=<new-path>
```

The parser splits the value on the first `=` after the flag separator. Both
halves are required, both must be non-empty, both must be absolute paths.
Malformed values reject before `composeHardenPlan` runs.

**Compose-time pipeline** (extends `composeHardenPlan`, per
`v0.4-architect-memo.md §3.2 + §11 apply-order trace`):

1. CLI parser validates flag shape; emits `mcp-rewrite-malformed-arg` refusal if shape is wrong.
2. `statSync(newPath).isFile()` — fail emits `mcp-rewrite-target-missing`.
3. `statSync(newPath).mode & 0o111` — zero emits `mcp-rewrite-target-not-executable`.
4. **Item 6 hard boundary:** `statSync(newPath).uid !== process.getuid()` — emits `mcp-rewrite-foreign-owner` (refuses rewrite to an attacker-owned binary).
5. Locate the `mcpServers.<name>` entry whose current `command` matches `oldPath`; if no match, emit `mcp-rewrite-source-not-found`.
6. Compose a single `json-rewrite` op (per Q2) that sets `mcpServers.<name>.command = newPath`. Patch builder lives in `harden-plan.mjs` (`HARDENABLE_DETECTORS_V04`) — architect §3.2 details the registry-value shape change from `(finding) => patch` to `(finding, options) => patch | PreApplyRefusal`.
7. `MUTATION_REGISTRY["json-rewrite"].preApply` runs the existing v0.3 generic JSON validation (parse, apply, round-trip, idempotency).
8. Emit the plan; on terminal success, `executeHardenPlan` appends to `applied.jsonl` and emits the RELOAD HINT per `v0.4-product-memo.md §5 Transcript B`.

**RELOAD HINT for P2** (`v0.4-platform-memo.md §1.4`): "settings.json updated;
restart Claude session for the rewritten MCP command to take effect." Must
NOT claim hot-reload — `/reload-plugins` is documented only for plugin MCP
servers, and the audit (`notes/LOADER-SEMANTICS-AUDIT.md §6`) records the gap
for non-plugin MCP entries.

**Refusal taxonomy for P2:** see §5 below.

### §3.5 P5 — JSONC v2

**Parser adopted:** `jsonc-parser` (Q4 ruling).

**API used:** `parse()`, `parseTree()`, `modify(text, path, value, options)`,
`applyEdits(text, edits)`. `modify()` returns offset+length edit ops; we apply
the edits in place. This is the only candidate API where everything outside
the edit window is provably byte-identical to the original.

**Defense-in-depth guard** (`v0.4-architect-memo.md §6.4` + Q4 ruling):
`MUTATION_REGISTRY["json-rewrite"].preApply` extends to perform an
*identity-patch round-trip* against any JSONC file: `parse → identity modify →
applyEdits`; if the re-serialised output is not byte-identical to the source,
refuse with `settings-jsonc-rewrite-failed`. Cost: one extra parse + reserialize
per JSONC harden, sub-millisecond on ~10 KiB settings.

**Refusal class rename:**
- `settings-jsonc-detected` (v0.3, refuses every JSONC home) — **deprecated** in v0.4, not removed from the taxonomy until v0.5. JSON consumers of `--json` should handle both classes per `v0.4-product-memo.md §6.5`.
- `settings-jsonc-rewrite-failed` (v0.4) — fires only when the round-trip diverges (byte-for-byte mismatch on identity patch).

**Round-trip fidelity test (T-501)** — five JSONC fixtures (`v0.4-architect-memo.md §6.3`):
1. Single-line `//` between keys, modify a value → comment preserved, only the value changes.
2. Block `/* */` before a key, remove the key → block comment preserved, no trailing-comma artifact.
3. Trailing comma after last key, add a new key → trailing comma preserved, new key appended.
4. Mixed `//` line + `/* */` inline on the same value, remove a sibling → both preserved.
5. Deeply nested `/* */` inside a 3-level nested object, modify the inner value → comment intact.

Each fixture asserts byte-equal expected output. Any failure prevents Q4
adoption (architect's strongest fallback: option d "stay refused").

**Plain-JSON behavior is unchanged.** Files without comments parse through
`JSON.parse` as before; `jsonc-parser` is invoked only when v0.3's two-phase
tokenizer flags `settings.jsonc_detected`.

**First runtime dependency.** `jsonc-parser` v3.3.1 pinned in `package.json`
(`v0.4-platform-memo.md §4.1`). CHANGELOG and `docs/migration-v0.3-to-v0.4.md`
must call out: this is Housekeeper's first external runtime dependency. Risk
R13 in `v0.4-architect-memo.md §10.2` flags the zero-day concern; mitigation
is version pinning and treating upgrades as a Phase 5 task gated by the
round-trip fidelity test.

### §3.6 P6 — Batch `--stream`

**CLI surface** (`v0.4-product-memo.md §1.5`):
```
clean --batch=<n> --stream --confirm --yes \
    --target=<id> --path=<path> [--target=<id> --path=<path> ...]
```

- `--stream` is rejected when `n <= 50` (refusal `stream-redundant-for-small-batch`).
- `--stream` with `n > 50` produces a parent manifest and N sub-manifests in fixed 50-item chunks.
- `--stream --resume=<id>` is rejected: `stream-resume-not-supported` (deferred to v0.5).
- `--dry-run --stream` prints planned chunks without snapshotting.

**Chunking model (Q5 ruling):** fixed 50 items per chunk. The final chunk may
be smaller. Each chunk fits cleanly under the existing v0.3 snapshot budget
(`MAX_OPERATION_FILES = 50`, `MAX_OPERATION_BYTES = 10 MiB` at
`snapshot.mjs:28`). If a *composed* fixed-50 chunk exceeds 10 MiB before
snapshot, the chunk emits `stream-chunk-budget-exceeded` — the budget check
is unchanged from v0.3.

**Composition** (`v0.4-architect-memo.md §7.2`): `composeStreamCleanPlan` is an
async generator yielding `{ streamId, chunkIndex, plan }` objects where each
`plan` is a normal `CleanPlan`. Pre-flight `assembleReport` runs ONCE for the
full set; drift detection at execute time validates each chunk's portion
independently.

**Sub-manifest schema** (`v0.4-architect-memo.md §7.4`):
- `<home>/.claude/housekeeper/operations/stream_<id>/parent.json` — written first, updated incrementally; carries `streamId`, `chunkSize`, `totalChunks`, `completedChunks[]`, `haltedAtChunk` (null otherwise), `streamPartial`, `status` (`in_progress` | `verified` | `halted`).
- `<home>/.claude/housekeeper/operations/stream_<id>/chunk_NNN.json` — normal v0.3 operation manifest, identical schema. `opId` for each chunk is `<streamId>_chunk_NNN`. `housekeeper.interrupted_operation` (`audit.mjs:895`) surfaces halted chunks via existing detector — no new detector needed.

**Per-chunk failure handling.** On any chunk's failure the stream halts.
Parent manifest records `streamPartial: true`. Completed sub-manifests stay
at `verified`. The halted chunk stays at `applied + partialApply: true`.

**Rollback by streamId (item P3 ruling).**
`housekeeper rollback --stream=<streamId>` rolls back every sub-manifest in
reverse chunk order. Reverse order matters because each chunk's snapshot
captures the state *before* that chunk ran (architect §7.5). If the stream
halted, the halted chunk (status `applied`, `partialApply: true`) rolls back
FIRST, then completed chunks in reverse. `composeRollbackPlan(home, {
streamId })` returns the reverse-ordered sub-rollback plan list;
`executeRollbackPlan` runs them serially. Per-chunk
`housekeeper rollback <opId>` is supported for surgical recovery.

**Refusal classes for P6:**

| Class | Reason | Trigger |
|---|---|---|
| `CleanPlanRefusal` | `stream-chunk-budget-exceeded` | Composed chunk exceeds 50-file / 10-MiB snapshot budget |
| `CleanPlanRefusal` | `stream-resume-not-supported` | User attempts `--resume=<streamId>` or to resume a halted stream |
| `PreApplyRefusal` | `stream-redundant-for-small-batch` | `--stream` passed with `--batch=n` where `n <= 50` |

### §4.2 Threat model addendum (T-701a + T-701b)

**T-701a — Learning surface (PII, read/write trust boundary)** per
`v0.4-architect-memo.md §8.2`:

- JSONLs contain `redactedTargetPath` strings, computed *at write time* by `lib/redact.mjs`. A bug in the scrubber that leaks an un-redacted path would persist in the JSONL indefinitely. Mitigation: redact-at-write; new `learn --redact-rewrite` rewrites old lines (manual user trigger).
- `housekeeper learn --json | curl ...` to ship data to a third party is a user-initiated leak; doc surfaces it but does not mitigate.
- `state.json` last-write-wins between two `--mark-false-positive` calls is acceptable for v0.4; v0.5 adds a dedicated lock if telemetry shows real conflict.
- `learn` summary tolerates partial final lines (no fatal parse on incomplete write).

**T-701b — MCP rewrite injection** per `v0.4-architect-memo.md §3.4` + item 6 ruling:

- Concrete attack: user is convinced to run `harden --mcp-command-rewrite=/legit=/tmp/attacker` against a writable executable in `/tmp`. The next session start spawns the attacker's binary.
- **Item 6 hard boundary (this ruling):** refuse when `statSync(newPath).uid !== process.getuid()`. This blocks the privilege-escalation variant (root-owned binary in user-writable directory).
- The `--confirm --yes` contract continues to require explicit user consent. The CLI prints the exact rewrite (old → new) before applying so the user has a final chance to abort.
- Soft warnings for `/tmp`, `/var/tmp`, `~/Downloads` targets are deferred to v0.5 (architect's bullet 2 — useful nudge, not required for v0.4).

## §8 What v0.4 does NOT include — finalised list

Carry-forward exclusions from `notes/PLAN-v0.4.md §1`:

- Multi-home / fleet support (not scheduled).
- Interactive TTY consent (v1.0). `--yes` remains required.
- Auto-rollback of partial-apply batches (v1.0). v0.3 Q3 ruling holds.
- Cross-detector batch composition (v0.5). Kept disjoint per v0.3 C6.
- `learn` suggestion engine (v0.5). v0.4 records only; no inference.
- Plugin install via `prune --reverse` (v1.0). Prune is uninstall-only.

New exclusions surfaced during synthesis:

- **Plugin uninstall mutation (PQ-2).** v0.4.0 is audit-only. Mutation ships in v0.4.1 after a 30-day data-collection window — and uses `claude plugin uninstall` subprocess, never `rm -rf`.
- **ConfigChange auto-reload (PQ-4).** No documented Claude-side reload event. RELOAD HINT block continues from v0.3.
- **Wider exotic-filesystem coverage (PQ-3).** v0.3's `settings-network-filesystem` refusal class extends to learning JSONL writes (warn-only) and `lock.history` (skip). Atomic-rename guarantees on transports beyond NFS / SMB / APFS-over-SMB wait for v1.0.
- **Skill-index canonicalization (PQ-1).** Phase 3 reads what the audit already classifies; codification waits for T-300 runtime verification.
- **`comment-json` parser path.** Q4 chose `jsonc-parser`. The comment-json branch is not retained.
- **Per-pillar mutation kinds.** Q2 chose generalization to `json-rewrite`. Three per-pillar kinds (`registry-rewrite`, `hooks-rewrite`, `skills-rewrite`) are not introduced; the Conflict A split means only `hooks.config_dangling` even needs JSON-rewrite — the other two are filesystem kinds already shipped.
- **Stream resume.** Halted streams must be rolled back and re-run. Resume deferred to v0.5 with refusal class `stream-resume-not-supported`.
- **Adaptive stream chunk sizing.** Q5 ruled fixed-50. Adaptive split under 10-MiB pressure (platform's recommendation) is deferred — re-evaluate in v0.5 if telemetry shows the 10-MiB cap is the dominant `stream-chunk-budget-exceeded` trigger.
- **Soft warnings for `/tmp`-rooted MCP rewrite targets.** Item 6 hard refusal on foreign-owner covers the privilege-escalation variant; user-owned `/tmp` targets remain permitted with explicit consent. Deferred to v0.5.
- **`housekeeper learn --redact-rewrite`.** Architect §8.2 flagged the need for retroactive redaction of JSONL records if a `lib/redact.mjs` bug leaked an unredacted path. Out of scope for v0.4.0; only needed if such a bug surfaces.
- **State.json concurrent-write lock.** Last-write-wins on simultaneous `--mark-false-positive` is acceptable for v0.4. A dedicated `<home>/.claude/housekeeper/learning/.lock` ships in v0.5 if telemetry shows real conflict.
