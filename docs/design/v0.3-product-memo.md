# Product memo — `harden --confirm` and `clean --batch` for Claude Housekeeper v0.3

Author: product engineering · Companion to architect memo, platform memo, and tie-breaker (parallel pass)
Lane: T-D02 product surface · Status: design draft, not normative until tie-breaker accepts
Decision Log reference: `notes/PLAN-v0.3.md` §4 (Q1–Q5 open at memo time)

This memo answers a different question than the v0.3 architect memo. The
architect asks "how does `settings-rewrite` work end-to-end." This memo asks
"what does the user type, what do they see, what refusal phrasing keeps the
v0.2 promise intact, and which Q1–Q5 stance does the product take." If the
two memos disagree on user-visible surface, the tie-breaker resolves it
before Phase 1 starts.

The v0.2 product memo earned trust by shipping the most conservative useful
`clean`. v0.3 must extend that trust to a second verb (`harden`) and a
second mode (`--batch`) without re-introducing the broad-cleanup risk that
v0.1 / v0.2 explicitly refused.

---

## 0. Premise and stance

v0.2 shipped one mutation verb — `clean` — and three cleanable detectors.
Every product decision in v0.2 traced to one observation: people installed
v0.1 because it was read-only. They tolerated v0.2's mutation only because
the surface was narrow, the rollback was byte-equal, and the refusal taxonomy
was visible.

v0.3 inherits that posture. The new pieces — `harden --confirm` and
`clean --batch` — must feel like reversible extensions of the report, not
new tools that automate judgement. Specifically:

- `harden` is the verb the README has reserved since v0.1. It always refused
  mutation. v0.3 finally lets it act, but only on a narrow set of settings
  patches the user already saw in `diagnose` output, only with snapshot
  proof, and only behind the same `--confirm --yes --target=... --path=...`
  consent gate that `clean` uses.
- `clean --batch` does not invent a new verb. It re-uses `clean`'s pipeline
  and lets the user authorize multiple findings in one operation manifest,
  capped at 10 findings. The aggregate budget (50 files / 10 MiB) applies
  to the batch, not per-finding.

If `harden` looks like a tool that "hardens your settings" (broad sweep,
opinionated defaults), v0.3 breaks the v0.2 promise. If `harden` looks like
"the report told me settings.hook_path_dangling references a missing path;
the consent gate showed me the exact patch; I typed `--confirm --yes`; the
snapshot proved the byte change," v0.3 keeps the promise.

This memo proposes the smallest useful surface for both features. It will
feel small. That is intentional. v0.3 is not "Housekeeper learns to harden
your home." It is "Housekeeper learns to apply one approved settings patch
with snapshot proof, and to bundle up to ten previously-approved findings
into one operation."

The mode doctrine (`docs/mode-doctrine.md` §7) reinforces this: harden is
allowed to *propose guards*, *show hook/policy additions*, and *require
consent*. It is forbidden to silently add SessionStart hooks, make broad
policy changes, or run hidden background automation. The CLI surface in
this memo is the operational expression of those rules.

## 1. `harden --confirm` CLI surface

### 1.1 Command form

```
claude-housekeeper harden --confirm --yes \
    --target=<detector-id> \
    --path=<absolute path> \
    [--dry-run] \
    [--timeout=<seconds>] \
    [--json] \
    [--home=<.claude path>]
```

Every flag has the exact same semantics as the v0.2 `clean` line. The
parser, the consent gate, the deadline (G15), and the JSON envelope are
shared. `harden` is a sibling of `clean` in the runtime, not a parallel
binary. The only thing that changes is the underlying mutation kind
(`settings-rewrite` instead of `dir-rmtree` or `file-unlink`) and the
detector allowlist (the three settings detectors graduating in Phase 3).

### 1.2 Flag semantics

| Flag | Required? | Meaning |
|---|---|---|
| `--confirm` | yes | Arms the mutation path. Without it, the run is a dry-run that prints the patch preview and exits 0. |
| `--yes` | yes (with `--confirm`) | Skips the (currently non-existent) interactive prompt. Without `--yes`, the runtime refuses with exit 2 and the message "Refusing mutation: `--yes` not passed." |
| `--target=<id>` | yes | One of `settings.hook_path_dangling`, `settings.mcp_command_missing`, or `settings.invalid_json` (the three Phase 3 detectors). Any other detector id refuses with `no-mutation-mapping-in-v0.3` and a `nextStep` pointing at `clean` if applicable. |
| `--path=<absolute>` | yes | The absolute path to the settings file. Together with `--target`, identifies exactly one finding from the most recent `diagnose`. |
| `--dry-run` | no | Equivalent to omitting `--confirm` — composes the plan, runs validation, prints the patch preview, exits 0 without mutating. Allowed *with* `--confirm`; in that case the mutation is still skipped but the consent gate is logged as if it would have fired. |
| `--timeout=<seconds>` | no | Same G15 deadline that `clean` exposes. Default: 300 s. The deadline covers compose + validate + snapshot + apply + verify. |
| `--json` | no | Switches the output envelope to machine-readable JSON; same shape as `clean --json`. |
| `--home=<path>` | no | Test/fixture override. Resolves to the `.claude` subdirectory under the home. |

### 1.3 Exit codes

`harden` mirrors `clean`'s exit code contract exactly:

| Exit | Meaning |
|---|---|
| 0 | Plan composed, validated, snapshot taken, patch applied, verify passed. (Or `--dry-run` succeeded.) |
| 1 | Internal error (snapshot fs failure, disk full, JSON write failed, deadline exceeded with unclear state). Worth a CI Slack page. |
| 2 | Refused. Structured refusal in stderr (or JSON envelope). Legitimate scriptable state; not a CI failure. |

The product principle is: exit code 2 is information, not error. CI jobs
chaining `diagnose | harden | clean` should treat exit 2 as "this finding
is not yet eligible; continue."

### 1.4 Output format — happy path

```
$ claude-housekeeper harden --confirm --yes \
    --target=settings.hook_path_dangling \
    --path=/Users/mara/.claude/settings.json
HOUSEKEEPER HARDEN
1 operation planned. Op id: op_20260612091223_b8e4f0c2

  settings-rewrite  /Users/mara/.claude/settings.json
    remove hook entry: SessionStart[0].hooks[2]
    command:          node /Users/mara/.claude/plugins/cache/oldplugin/1.2.0/hook.mjs
    reason:           hook command path does not exist on disk

  snapshot taken    → ~/.claude/housekeeper/snapshots/op_.../settings.json
  applied           → patch written (atomic temp + rename)
  verified          → sha256 matches expected; file parses as valid JSON;
                      patch is idempotent (re-apply yields byte-equal output)

DONE. Operation verified.

NEXT STEP
  Inspect the rewritten settings: cat /Users/mara/.claude/settings.json
  Re-run diagnose to confirm the finding cleared: claude-housekeeper diagnose

To roll back: claude-housekeeper rollback op_20260612091223_b8e4f0c2
```

The output preserves the v0.2 `clean` shape exactly. Stance language
("snapshot taken", "applied", "verified") stays the same. The only new
line is the per-operation detail block that names the JSON pointer of
the entry being removed and the reason from the audit finding.

### 1.5 Output format — refusal path

```
$ claude-housekeeper harden --confirm --yes \
    --target=settings.hook_path_dangling \
    --path=/Users/mara/.claude/settings.json
HOUSEKEEPER HARDEN
0 operations planned. 1 refused.

REFUSED
  detector:   settings.hook_path_dangling
  target:     /Users/mara/.claude/settings.json
  reason:     settings-jsonc-detected
  message:    settings.json contains JSONC comments; harden refuses to
              round-trip JSONC and risk reformatting your file
  nextStep:   Strip comments from settings.json by hand, save as plain JSON,
              and re-run harden. Housekeeper does not auto-strip comments.

$ echo $?
2
```

The refusal carries `class`, `reason`, `targetPath`, `message`, `nextStep`,
and `exitCode` — same fields as `CleanPlanRefusal`. The `nextStep` text is
mandatory per G7 (`scripts/lib/clean-plan.mjs` `NEXT_STEP_BY_REASON`).

### 1.6 JSON envelope

```
$ claude-housekeeper harden --confirm --yes --json \
    --target=settings.hook_path_dangling \
    --path=/Users/mara/.claude/settings.json
{
  "schemaVersion": "0.2",
  "command": "harden",
  "opId": "op_20260612091223_b8e4f0c2",
  "status": "verified",
  "operations": [
    {
      "detectorId": "settings.hook_path_dangling",
      "targetPath": "/Users/mara/.claude/settings.json",
      "mutationKind": "settings-rewrite",
      "patch": {
        "op": "remove",
        "path": "/hooks/SessionStart/0/hooks/2"
      },
      "estimatedBytes": 412,
      "expectedExitState": "verified"
    }
  ],
  "refused": [],
  "snapshotPath": ".../housekeeper/snapshots/op_20260612091223_b8e4f0c2/",
  "verifiedAt": "2026-06-12T09:12:25.118Z"
}
```

The envelope adds `patch` (a JSON-pointer + RFC-6902-style operation) but
otherwise reuses the operation-manifest schema 0.2. No `schemaVersion`
bump is needed; the architect memo confirms `settings-rewrite` is a new
mutation kind value, not a new schema shape.

### 1.7 What `harden` does NOT do in v0.3

- It does NOT add new hooks, MCP servers, or guards. Hardening is
  subtractive in v0.3 — it removes broken entries the user already saw in
  `diagnose`. The `harden` *concept* will broaden in v0.4+ (e.g. installing
  the SessionStart prevention hook from `hooks/session-start.mjs`), but
  v0.3 ships only the remove-broken-entry pipeline.
- It does NOT batch. `harden --batch` is deferred to v0.4; v0.3 is
  one-finding-per-invocation, same as v0.2 `clean`. The `clean --batch`
  flow in §2 informs the v0.4 `harden --batch` design but does not ship
  for `harden` in v0.3.
- It does NOT prompt interactively. `--yes` is required. Interactive TTY
  prompts ship in v1.0 per `PLAN-v0.3.md §1`.
- It does NOT touch the home outside the named settings file. The
  snapshot is a single-file snapshot. Rollback restores that one file.

## 2. `clean --batch` CLI surface

### 2.1 The question this surface answers

A v0.2.0-beta.1 user who runs `diagnose` against a real home today
typically sees 4–8 `plugin.cache_unreferenced` findings (one per stale
plugin cache version) plus 1–3 `registry.local_command_identical`
findings. Each needs a separate `clean --confirm --yes` invocation. The
user has to copy-paste the target and path eight times.

This is not unsafe — every invocation goes through the full pipeline —
but it is **friction the user did not sign up for**. v0.3 should make
the multi-finding path one invocation, while preserving every safety
property of v0.2: snapshot proof per file, atomic rollback, refusal
taxonomy per finding, aggregate budget cap.

### 2.2 The product question — repeated flags or manifest file?

This is the key product question for §2. There are two plausible shapes:

**Option A — Repeated `--target` / `--path` pairs on the command line:**

```
claude-housekeeper clean --batch --confirm --yes \
    --target=plugin.cache_unreferenced \
    --path=/Users/mara/.claude/plugins/cache/foo/1.0.0 \
    --target=plugin.cache_unreferenced \
    --path=/Users/mara/.claude/plugins/cache/bar/2.0.0 \
    --target=registry.local_command_identical \
    --path=/Users/mara/.claude/commands/old-helper.md
```

**Option B — A manifest file:**

```
$ cat /tmp/clean-batch.json
{
  "schemaVersion": "0.2",
  "operations": [
    { "target": "plugin.cache_unreferenced", "path": "/Users/mara/.claude/plugins/cache/foo/1.0.0" },
    { "target": "plugin.cache_unreferenced", "path": "/Users/mara/.claude/plugins/cache/bar/2.0.0" },
    { "target": "registry.local_command_identical", "path": "/Users/mara/.claude/commands/old-helper.md" }
  ]
}

$ claude-housekeeper clean --batch --confirm --yes --manifest=/tmp/clean-batch.json
```

### 2.3 Product position — Option A (repeated flags)

**This memo argues for Option A.** Rationale:

1. **Composability with `diagnose --json`.** A user (or CI script) can do
   `diagnose --json | jq` to extract finding ids and target paths, then
   pipe them straight into `xargs claude-housekeeper clean --batch`. A
   manifest file forces a write-to-disk intermediate step that breaks the
   pipe-friendly shape.
2. **No new file format.** Option B introduces a manifest schema that has
   to be versioned, validated, and documented. Option A's input is just
   shell arguments — the same surface every user already understands.
3. **The same refusal taxonomy applies.** Every batched finding goes
   through `composeCleanPlan`'s 12-rule classifier. Refusals appear in
   `plan.refused[]` exactly as they do for single-finding clean. A
   manifest file would tempt designers to add manifest-level validation
   ("file does not exist", "JSON malformed") that duplicates this work.
4. **It mirrors familiar tools.** `git checkout`, `cp`, `rm`, `kubectl
   delete -f` all accept repeated positional or repeated `--flag`
   arguments. `apt install pkg1 pkg2 pkg3` is the closest analog and
   sets the user's expectation.
5. **The 10-finding cap is human-readable on one screen.** A manifest
   file invites scope creep ("I'll batch 50, why not"). A literal command
   line with 10 `--target` / `--path` pairs visibly exceeds normal
   one-line tolerance and trains the user to break large batches up.

The cost of Option A is shell-line length. At 10 findings × ~80 chars per
`--target=X --path=Y` pair = 800 characters. That is verbose but not
unreadable, and tools like `shellcheck` and shell aliases handle it
fine. The cost of Option B (new file format, intermediate write step,
duplicated validation) is higher and recurring.

If a user genuinely wants a file-driven workflow, they can build one
themselves: `jq -r '...' findings.json | xargs -n 4 claude-housekeeper
clean --batch ...`. We do not have to ship the file format ourselves.

### 2.4 Flag semantics

| Flag | Required? | Meaning |
|---|---|---|
| `--batch` | yes (to enter batch mode) | Switches the parser to accept multiple `--target=` / `--path=` pairs. Without `--batch`, repeated `--target` is a parse error. |
| `--target=<id>` | yes (1 or more) | Repeated; each instance must be paired with a `--path=`. The parser pairs them positionally — the Nth `--target` binds to the Nth `--path`. |
| `--path=<absolute>` | yes (matches --target count) | Repeated; must match `--target` count. Mismatch is a parse error with exit 2. |
| `--batch-cap=<n>` | no | Aggregate cap on findings. Default 10, max 10. Values >10 refuse with exit 2 and a message naming the architectural cap. |
| `--confirm` `--yes` `--dry-run` `--timeout` `--json` `--home` | as in v0.2 | Same semantics. |

### 2.5 Batch behavior — atomicity model

Per `PLAN-v0.3.md §4 Q3`, this memo takes a product stance:

**Stance: Atomic. All-or-none. No partial commit, no resume semantics.**

- The snapshot is taken once for the whole batch.
- Apply runs per-operation, but the manifest status becomes `verified`
  only when every operation verifies.
- If any operation fails mid-batch, the manifest stays `applied` (not
  `verified`), and the existing `housekeeper.interrupted_operation`
  detector surfaces it. The user runs `rollback <id> --confirm --yes`
  to restore every changed file from the single snapshot.
- We do NOT auto-rollback successful operations on a downstream
  failure. The user keeps agency: roll back if you want the all-or-none
  semantics; leave it if the partial state is acceptable.

This matches the v0.2 Ruling 9 stance: partial applies surface via the
interrupted-operation detector and route to `rollback <id>`, not to
silent self-recovery. The user already trusts that flow.

The alternative (auto-rollback on any failure) would be more implicit
but would silently undo work the user authorized — and discard the
snapshot before they could inspect the partial state. We prefer
deterministic surface area over implicit recovery.

### 2.6 Output format — batch happy path

```
$ claude-housekeeper clean --batch --confirm --yes \
    --target=plugin.cache_unreferenced \
    --path=/Users/mara/.claude/plugins/cache/foo/1.0.0 \
    --target=plugin.cache_unreferenced \
    --path=/Users/mara/.claude/plugins/cache/bar/2.0.0 \
    --target=registry.local_command_identical \
    --path=/Users/mara/.claude/commands/old-helper.md
HOUSEKEEPER CLEAN (batch)
3 operations planned. Op id: op_20260612091422_d3e1a7b5
Aggregate budget: 142 files, 38.4 MiB (limit: 50 files, 10 MiB)

  REFUSED: aggregate exceeds 10 MiB budget.
  reason: budget-exceeded-batch
  nextStep: Re-run with fewer --target/--path pairs, or run each finding
            individually with `clean --confirm --yes`.

$ echo $?
2
```

The example above intentionally fails the budget check to illustrate
the refusal path. When the batch fits:

```
$ claude-housekeeper clean --batch --confirm --yes \
    --target=plugin.cache_unreferenced \
    --path=/Users/mara/.claude/plugins/cache/foo/1.0.0 \
    --target=registry.local_command_identical \
    --path=/Users/mara/.claude/commands/old-helper.md
HOUSEKEEPER CLEAN (batch)
2 operations planned. Op id: op_20260612091422_d3e1a7b5
Aggregate budget: 17 files, 312 KiB (limit: 50 files, 10 MiB)

  [1/2] dir-rmtree  /Users/mara/.claude/plugins/cache/foo/1.0.0  (312 KiB)
        snapshot taken    → ~/.claude/housekeeper/snapshots/op_.../foo/
        applied           → directory removed
        verified          → no residual files

  [2/2] file-unlink /Users/mara/.claude/commands/old-helper.md     (3.1 KiB)
        snapshot taken    → ~/.claude/housekeeper/snapshots/op_.../old-helper.md
        applied           → file removed
        verified          → file no longer exists

DONE. Operation verified.

RELOAD HINT
  Run /reload-plugins in any active Claude Code session to drop the
  cache reference. The plugins/data/ directory was preserved.

To roll back: claude-housekeeper rollback op_20260612091422_d3e1a7b5
```

Every refusal in `plan.refused[]` is printed inline before the apply
loop starts. If even one refusal is in the batch and the rest fit, the
batch is refused as a whole (atomicity: all or none of the authorized
findings). The product principle: "Do not partially execute a batch."

### 2.7 What `clean --batch` does NOT do in v0.3

- It does NOT mix detectors with `harden` operations. `harden --batch`
  is v0.4.
- It does NOT exceed 10 findings or 50 files or 10 MiB. Period.
- It does NOT skip individual refusals and proceed with the rest. The
  batch is the unit of consent.
- It does NOT prompt interactively to confirm each finding. `--yes`
  applies to the whole batch as a single decision.

## 3. Refusal phrasing — new reasons for v0.3

Per `PLAN-v0.3.md §3`, v0.3 extends the 12-rule taxonomy with
harden-specific reasons. This section proposes the exact structured
keys and human-readable copy for each new refusal class. The copy
follows the same shape as v0.2's `NEXT_STEP_BY_REASON` in
`scripts/lib/clean-plan.mjs`: a single complete sentence under the
refusal, no internal vocabulary, an action the user can take.

### 3.1 `settings-jsonc-detected`

The target settings file contains JSONC comments (`//` or `/* ... */`).
Housekeeper's parser is strict JSON.

**Structured keys:**

```json
{
  "class": "HardenPlanRefusal",
  "reason": "settings-jsonc-detected",
  "targetPath": "/Users/mara/.claude/settings.json",
  "detectorId": "settings.hook_path_dangling",
  "message": "settings.json contains JSONC comments; harden refuses to round-trip JSONC and risk reformatting your file",
  "nextStep": "Strip comments from settings.json by hand, save as plain JSON, and re-run harden. Housekeeper does not auto-strip comments.",
  "exitCode": 2
}
```

**Rendered:**

```
REFUSED
  detector:   settings.hook_path_dangling
  target:     /Users/mara/.claude/settings.json
  reason:     settings-jsonc-detected
  message:    settings.json contains JSONC comments; harden refuses to
              round-trip JSONC and risk reformatting your file
  nextStep:   Strip comments from settings.json by hand, save as plain JSON,
              and re-run harden. Housekeeper does not auto-strip comments.
```

This is the product position on Q2 — see §6.

### 3.2 `settings-shape-unknown`

The settings file parses as JSON, but the top-level shape does not
match the documented Claude Code schema (e.g. the file is `[]` instead
of `{}`, or `"hooks"` is a string instead of an object).

**Structured keys:**

```json
{
  "class": "HardenPlanRefusal",
  "reason": "settings-shape-unknown",
  "targetPath": "/Users/mara/.claude/settings.json",
  "detectorId": "settings.hook_path_dangling",
  "message": "settings.json top-level shape does not match the documented Claude Code schema; harden refuses to write to an unrecognized structure",
  "nextStep": "Compare your settings.json to the documented schema at https://docs.claude.com/claude-code/settings (or your local copy of the docs), restore the expected top-level shape, and re-run harden.",
  "exitCode": 2
}
```

**Rendered:**

```
REFUSED
  detector:   settings.hook_path_dangling
  target:     /Users/mara/.claude/settings.json
  reason:     settings-shape-unknown
  message:    settings.json top-level shape does not match the documented
              Claude Code schema; harden refuses to write to an
              unrecognized structure
  nextStep:   Compare your settings.json to the documented schema (see
              https://docs.claude.com/claude-code/settings), restore the
              expected top-level shape, and re-run harden.
```

This refusal is **load-bearing**. It is the failsafe that catches every
case where Claude Code adds a new top-level key, ships a v2 settings
schema, or where the user has hand-edited their settings into a shape we
do not recognize. Without this refusal, `harden` would silently rewrite
unfamiliar structures.

### 3.3 `patch-not-idempotent`

The proposed patch is computed, then re-applied to its own output. If
the second application changes anything (e.g. an append-instead-of-merge
bug), the patch is non-idempotent and harden refuses.

**Structured keys:**

```json
{
  "class": "HardenPlanRefusal",
  "reason": "patch-not-idempotent",
  "targetPath": "/Users/mara/.claude/settings.json",
  "detectorId": "settings.hook_path_dangling",
  "message": "patch is not idempotent; re-applying it to its own output yields a different file. harden refuses to apply a patch that would change behavior on rerun-after-crash",
  "nextStep": "This is a Housekeeper bug — please file an issue at https://github.com/hemzaz/claude-housekeeper/issues with the contents of your settings.json (redacted as needed). Until a patch lands, remove the broken settings entry by hand.",
  "exitCode": 2
}
```

**Rendered:**

```
REFUSED
  detector:   settings.hook_path_dangling
  target:     /Users/mara/.claude/settings.json
  reason:     patch-not-idempotent
  message:    patch is not idempotent; re-applying it to its own output
              yields a different file. harden refuses to apply a patch
              that would change behavior on rerun-after-crash
  nextStep:   This is a Housekeeper bug — please file an issue with the
              contents of your settings.json (redacted as needed). Until
              a patch lands, remove the broken settings entry by hand.
```

This refusal protects against compose-time bugs in the patch generator.
The architect memo's pre-apply check #4 (apply twice → byte-equal) is
the engine guarantee; this refusal is the user-visible surface when
that guarantee fails. It should be rare; when it fires, it is a bug
report, not a user-actionable state.

### 3.4 `patch-produces-invalid-json`

The proposed patch is computed, applied in-memory, and the result fails
JSON parsing. This catches patch-generator bugs that emit syntactically
broken output before we ever touch disk.

**Structured keys:**

```json
{
  "class": "HardenPlanRefusal",
  "reason": "patch-produces-invalid-json",
  "targetPath": "/Users/mara/.claude/settings.json",
  "detectorId": "settings.hook_path_dangling",
  "message": "patch output does not parse as valid JSON; harden refuses to write a broken settings.json to disk",
  "nextStep": "This is a Housekeeper bug — please file an issue at https://github.com/hemzaz/claude-housekeeper/issues with the contents of your settings.json (redacted as needed). Your settings.json on disk is unchanged.",
  "exitCode": 2
}
```

**Rendered:**

```
REFUSED
  detector:   settings.hook_path_dangling
  target:     /Users/mara/.claude/settings.json
  reason:     patch-produces-invalid-json
  message:    patch output does not parse as valid JSON; harden refuses
              to write a broken settings.json to disk
  nextStep:   This is a Housekeeper bug — please file an issue with the
              contents of your settings.json (redacted as needed). Your
              settings.json on disk is unchanged.
```

Like §3.3, this is a bug-report state. The product principle is that
when Housekeeper's own machinery would produce a broken file, it
refuses loudly rather than silently corrupting the user's home.

### 3.5 Reused refusals

The harden classifier also reuses the 12-rule taxonomy where the
semantics carry over directly:

- `plan-state-error` — interrupted-operation present; run `rollback`
  first.
- `protected-path` — settings.json is under a `doNotTouch` rule.
- `sector-boundary` — settings.json is under `credentials/` (extremely
  unusual; would not normally happen, but the refusal exists for
  defense in depth).
- `no-mutation-mapping-in-v0.3` — equivalent of v0.2's
  `no-mutation-mapping-in-v0.2`; the detector id is not in v0.3's
  hardenable set.

These reuse v0.2's exact `message` and `nextStep` copy. No new strings.

### 3.6 The pattern

Every refusal carries five fields the user reads and four the JSON
envelope exposes. The pattern, frozen here:

| Field | Required | Audience |
|---|---|---|
| `class` | yes | machine (e.g. `HardenPlanRefusal`) |
| `reason` | yes | machine + human (e.g. `settings-jsonc-detected`) |
| `targetPath` | yes | both |
| `detectorId` | yes | both |
| `message` | yes | human (one complete sentence, no internal vocabulary) |
| `nextStep` | yes | human (one complete sentence, an action) |
| `exitCode` | yes | machine (always 2 for refusals) |

The `nextStep` field is **non-empty for every refusal reason** — that
is the G7 invariant. If a contributor adds a new refusal reason
without a `nextStep`, the test `test/clean-plan.test.mjs` fails. v0.3
extends that test to harden refusals.

## 4. End-to-end transcript

verb chain: diagnose → harden plan (dry-run) → consent → execute →
verify → rollback dry-run → rollback. Every line is what the user
literally sees on stdout (or stderr for refusals).

Where the v0.1 and v0.2 design memos use this transcript format
(`docs/design/clean-design.md §9`, `docs/design/clean-product-memo.md`
§3), this section mirrors it for v0.3.

## 6. Q1–Q5 stance

Per `PLAN-v0.3.md §4`, the open design questions need a product
position before Phase 1 starts. This section takes a stance on each.
The architect memo and platform memo may push back; the tie-breaker
arbitrates. Until then, these are the product defaults.

### 6.1 Q1 — `settings.invalid_json` recovery semantics

**Position: option (a). Refuse. Detector graduates to `prepare` stance
but `harden` always refuses with class `settings-shape-unknown` (a
specialization for the unparseable case).**

**Rationale:**

A `settings.json` that does not parse is a file in an unknown state.
Two things could have happened:

1. The user hand-edited it and made a typo. They are likely to want
   to reopen the file in their editor, find the typo, and save. Any
   automated "recovery" by Housekeeper destroys their in-flight work.
2. Claude Code itself wrote a malformed file (extremely rare; would be
   a Claude Code bug). The right response is to file an issue
   upstream, not to silently rewrite the user's settings.

Option (b) — "move aside and write empty `{}`" — has the worst
property of any option: it destroys the user's settings configuration,
which on a real laptop can be hundreds of lines of careful hook
configuration. The "recovery" is more destructive than the failure.

Option (c) — "run JSON repair heuristics" — is exactly the kind of
magic the v0.2 product memo warned against. Heuristic repair can
silently produce settings that parse but mean something different
than the user intended. There is no rollback for "my settings now
load a hook I didn't authorize."

The product position is therefore **refuse, surface the finding, tell
the user to open their editor.** The `nextStep` text for this refusal
class:

> Open settings.json in your editor and resolve the JSON syntax error
> by hand. Housekeeper does not run JSON repair heuristics; an
> incorrectly "recovered" settings.json could silently load hooks you
> did not authorize.

Q1 stays open until the tie-breaker arbitrates. If the architect memo
argues for option (b) with a backup-and-replace path, this memo's
counter is: the user does not want their settings replaced. They want
a clear refusal and a clear next step.

### 6.2 Q2 — Settings JSONC support

**Position: option (a). Refuse JSONC. Strict-JSON parser only in v0.3.**

**Rationale:**

Three reasons:

1. **Round-trip risk.** Claude Code accepts JSONC and writes JSON. If
   Housekeeper reads JSONC, strips comments, applies a patch, and
   writes JSON back, the user's hand-curated comments are lost. That
   is a one-way information destruction event. The user did not
   authorize comment deletion when they typed `--confirm --yes`; they
   authorized one specific patch.
2. **Adopting `jsonc-parser` is option (c).** It buys round-trip
   comment preservation but at the cost of a new dependency, a new
   parser code path, and a new failure mode (what if JSONC parsing
   diverges from Claude Code's parser?). The platform memo (T-D03)
   should explicitly cite Claude Code's JSONC parser implementation
   before we adopt any third-party JSONC library.
3. **Refusing is informative.** A `settings-jsonc-detected` refusal
   tells the user clearly that v0.3 does not support their setup
   style. They can either strip comments to use harden, or wait for
   v0.4 where JSONC handling can land with proper comment-preservation
   tests.

The cost of option (a) is that a slice of users (those who use JSONC
extensively) cannot use `harden` in v0.3 at all. That is acceptable
for a first release of the verb. v0.4 can broaden support once the
platform memo confirms the right parser to adopt.

### 6.3 Q3 — Batch atomicity model

**Position: option (a), but with a product twist: atomic at the
manifest level, not auto-rollback at the runtime level.**

**Rationale:**

The architect memo will probably want option (a) (auto-rollback on
any operation failure) for engine cleanliness. This memo takes a
more user-agency-preserving stance:

- The **manifest** is atomic: status is `verified` only if every
  operation verifies. If any operation fails, status stays at
  `applied` and `housekeeper.interrupted_operation` surfaces it.
- The **runtime** does NOT auto-rollback. The user runs
  `rollback <id> --confirm --yes` if they want the all-or-none
  semantics. Otherwise the partial state is preserved for inspection.

This is the same Q5 / Ruling 9 pattern v0.2 chose. The rationale:
auto-rollback silently undoes work the user explicitly authorized.
If the user authorized 5 deletions and 3 succeeded, they may prefer
to inspect the 2 that failed and decide whether to retry — not have
all 5 silently restored.

The `housekeeper.interrupted_operation` detector is the bridge: it
makes the partial state visible, surfaces the op id, and offers
`rollback <id>` or `rollback --abort <id>` as the next step. The
user keeps agency.

### 6.4 Q4 — Per-detector harden eligibility

**Position: yes, declare `hardenable: true/false` in raw detector
output, but treat it as a **product-side** annotation, not a
guarantee.**

**Rationale:**

The architect memo will want this for engine machinery (the audit
pipeline needs to know which findings to surface as `prepare` vs
`review`). The product memo wants it for a different reason: the
README's "Current Checks" table currently has three columns
(`cleanable`, `planned`, `never`). v0.3 needs a fourth: `hardenable`.
That fourth column is the user-visible expression of the detector
flag.

The product position: yes, add `hardenable: true` to the three Phase
3 detectors. Render the README table accordingly. Surface the
distinction in `diagnose` output so the user sees which findings are
candidates for `harden` versus `clean`.

The non-position: this is not a stance guarantee. A
`hardenable: true` finding can still refuse at compose time (e.g.
JSONC detected, shape unknown). The flag is a *candidacy* signal,
not a *will-act* promise. The `--dry-run` flow is the actual
trial-balloon mechanism.

### 6.5 Q5 — Site/docs version-pinning automation

**Position: option (a). CI check that `docs/index.html` version
matches `package.json`.**

**Rationale:**

Option (b) — "replace the hardcoded version with a build-time
substitution" — is the cleaner engineering answer but adds a build
step to a project that currently has zero build steps. v0.3 is not
the place to add `vite` or `esbuild` to a CLI plugin.

A CI check (option a) is one yaml file, runs in seconds, and fails
loudly when the two values drift. The platform memo can confirm the
exact tool (`grep`, `jq`, a tiny shell script). This is the smallest
intervention that solves the problem.

Specific implementation sketch:

```yaml
# .github/workflows/version-pin.yml
- name: Verify docs/index.html version matches package.json
  run: |
    pkg_version=$(jq -r .version package.json)
    site_version=$(grep -oE 'v[0-9]+\.[0-9]+\.[0-9]+' docs/index.html | head -1 | sed 's/^v//')
    if [ "$pkg_version" != "$site_version" ]; then
      echo "Version mismatch: package.json=$pkg_version, docs/index.html=$site_version"
      exit 1
    fi
```

Six lines. Catches the G4 issue from the v0.2 GA cut. No build step
required.

## 7. The success state — product view

v0.3.0 ships when **a user can complete the round-trip in §4** against
their real `~/.claude/` home. The success state, in user terms:

1. They run `diagnose` and see a `prepare`-stance finding for a
   broken hook in their settings. The `next step` field tells them
   exactly what to type.
2. They copy-paste that next step with `--dry-run` first to see the
   patch as a unified diff. They visually verify the patch removes
   the entry they expected.
3. They re-run with `--confirm --yes`. They see four lines:
   "snapshot taken", "applied", "verified", "DONE". They see an op id
   they can save.
4. They re-run `diagnose`. The finding is gone. The stance summary
   reflects one less `prepare` finding.
5. (Optional) They run `rollback <id> --confirm --yes`. The file is
   restored byte-for-byte. The finding is back. They have proof that
   the round-trip works.

If any of those five steps fails, v0.3 is not shippable. The
acceptance criterion is the round-trip, not "the feature exists."

## 9. Open product questions for the tie-breaker

Three questions this memo cannot resolve alone:

**P1: Should `harden`'s dry-run output show the JSON-pointer patch
representation (e.g. `remove /hooks/SessionStart/0/hooks/2`) in
addition to the unified diff?** The diff is universally readable; the
pointer is precise but unfamiliar to non-JSON-savvy users. This memo
proposes diff-only by default with `--json` revealing the structured
pointer. The architect memo may prefer pointer-first for engine
consistency.

**P2: Does `clean --batch` carry over `--target=`/`--path=`
positional pairing if the user only passes one of the two?** This
memo proposes a hard parse error. The alternative is "treat as the
single-finding form and ignore `--batch`," which is the GNU-style
permissive parse. We argue for strictness.

**P3: Should refusal messages name the v0.4 feature that would
unblock them?** E.g. "JSONC support ships in v0.4 — until then,
strip comments by hand." The memo proposes yes for `settings-jsonc-detected`
specifically, no for `patch-not-idempotent` / `patch-produces-invalid-json`
(which are bug-report states and should not promise a remediation in a
specific version).

These three should land in `docs/design/v0.3-design.md` (T-D04)
alongside Q1–Q5.
