## 0. What this memo is and is not

This is the **platform-interop** lane for v0.3. It does **not** redesign the
`harden` pipeline (architect, T-D01) or the refusal-message copy (product,
T-D02). It pins what Claude Code itself does when Housekeeper rewrites
`<home>/.claude/settings.json`, and what Housekeeper must avoid in order
not to crash, confuse, or corrupt a running Claude session.

The v0.2 platform memo (`docs/design/clean-claude-code-memo.md`) covered
the **deletion** case — what happens to plugin-cache versions when Claude
has them mapped into memory. v0.3 introduces a strictly harder case:
**read-modify-write of a JSON file that Claude itself reads**. The matrix
is different. Atomic rename gives stronger guarantees than deletion, but
Claude's re-read behavior, JSONC tolerance, and MCP-lifecycle semantics
become the load-bearing facts.

The bias of this memo, like its v0.2 predecessor, is conservative: the
operator has chosen `harden` precisely because they want one specific
broken thing fixed without auditing everything else. Housekeeper must
not trade one trust loss (a dangling hook path) for a worse one (a
settings file Claude can no longer parse, or an MCP transport that
silently disconnects mid-session).

The single most consequential platform fact for v0.3:
**Claude Code reads `settings.json` from disk, but the read-frequency and
re-read semantics are NOT fully documented**. The audit trail in
`notes/LOADER-SEMANTICS-AUDIT.md` §5 explicitly records that "merge order
across sources" and "performance impact of many hooks across sources"
remain Unknown after the 2026-05-10 doc fetch. This memo treats that gap
as a core constraint, not a footnote.

## 1. Claude Code Settings Interop

This section answers Question 1 of the task brief: what fields in
`settings.json` are read by Claude itself, and what happens if
Housekeeper replaces the file via atomic rename while Claude is running?

### 1.1 What Housekeeper currently reads from `settings.json`

From `scripts/lib/audit.mjs` (greped 2026-05-15):

| Field | Detector | Purpose |
|---|---|---|
| `hooks.*` (recursive) | `detectHookPathDangling`, `detectHookCommandShellAmbiguous` | Collect command strings, extract absolute paths, check existence |
| `mcpServers.<name>.command` | `detectMcpCommandMissing` | Verify the command binary exists on disk |
| (parse-only) entire file | `detectSettingsInvalidJson` | Surface invalid JSON as a finding |
| (referenced) `hooks` command strings vs plugin-cache dirs | `plugin.cache_referenced_by_hook` | Block cache cleanup that would dangle a hook |

The collector helper `collectHookCommands` walks recursively for any
`.command` strings under `value.hooks` (see `audit.mjs` line ~1332,
`visit(value.hooks)`). No other `settings.json` fields are dereferenced
by v0.2 detectors.

For v0.3 the new `harden` pipeline will additionally **write** to:
- `hooks.*` — to remove dangling-path hook entries (T-300)
- `mcpServers.<name>` — to remove dangling-command MCP entries (T-301)
- (case Q1) the whole file — if `settings.invalid_json` recovery moves
  the file aside (T-302, pending Q1 ruling)

### 1.2 What Claude Code itself reads from `settings.json`

Per `docs/loader-semantics.md` §1 + the configuration docs, Claude Code
reads from up to five settings sources merged by precedence:
Managed → CLI args → Local → Project → User. The User-scope file at
`~/.claude/settings.json` is the one Housekeeper hardens.

Documented top-level keys Claude consumes (configuration docs, current
as of the 2026-05-10 audit):

| Key | Effect | Cited from |
|---|---|---|
| `hooks` | Hook configuration (PreToolUse, PostToolUse, Stop, SessionStart, etc.) | `loader-semantics.md` §5 |
| `mcpServers` | Local-scope MCP servers (project scope lives in `.mcp.json`; user scope lives in `~/.claude.json`) | `loader-semantics.md` §6; configuration docs |
| `permissions` | `/permissions` allow/deny rules | configuration docs; `debug-your-config` `/permissions` probe description |
| `env` | Environment variables exposed to tools | configuration docs |
| `enabledPlugins` | Project-scope plugin enablement | `loader-semantics.md` §2 |
| `skillOverrides` | Per-skill visibility states (`on`/`off`/`name-only`/`user-invocable-only`) | `notes/LOADER-SEMANTICS-AUDIT.md` §4 NEW_RULE_AVAILABLE |
| `disableSkillShellExecution` | Toggles skill shell injection | `loader-semantics.md` §4 |
| `apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport` | Credential helpers | configuration docs |
| `theme`, `model`, etc. | Per-session UX | configuration docs |
| `additionalDirectories`, `--add-dir` equivalents | Extra workspace roots | configuration docs |

The full top-level shape is **not** versioned by a `schemaVersion` field
the way Housekeeper's own manifests are (see `docs/rollback-contracts.md`).
This is the central platform risk for `harden`: Claude can add a new
top-level key in any release, and Housekeeper's read-modify-write must
preserve it.

### 1.3 Does Claude have a file watcher?

**Partial answer, mostly documented; partly inferred.**

From `notes/LOADER-SEMANTICS-AUDIT.md` §4 NEW_RULE_AVAILABLE:

> "Claude Code watches skill directories for file changes. Adding,
> editing, or removing a skill under `~/.claude/skills/`, the project
> `.claude/skills/`, or a `.claude/skills/` inside an `--add-dir`
> directory takes effect within the current session without
> restarting."

So Claude **does** have a file watcher, but the documented surface is
specifically the skills directory tree. The skills doc does **not**
extend this guarantee to `settings.json`, `~/.claude.json`, or
`.mcp.json`. The hooks doc says hooks come from "the menu displays …
configured hooks" (i.e. it's a session-time view), and `notes/
LOADER-SEMANTICS-AUDIT.md` §5 explicitly lists "merge order across
sources" as Unknown.

**Operational summary** for Housekeeper to assume:

| Surface | Re-read on edit? | Source |
|---|---|---|
| `~/.claude/skills/<name>/SKILL.md` | YES, in-session | skills doc, audit §4 |
| `~/.claude/commands/*.md` | YES, in-session (same watcher) | skills doc, audit §4 |
| `~/.claude/settings.json` | UNKNOWN — assume **session-start-only** | gap in audit §5 |
| `.claude/settings.json` (project) | UNKNOWN — assume session-start-only | gap |
| `.claude/settings.local.json` | UNKNOWN — assume session-start-only | gap |
| `~/.claude.json` | UNKNOWN — assume session-start-only | gap |
| `.mcp.json` | UNKNOWN — assume session-start-only | gap |
| Plugin `hooks/hooks.json` | UNKNOWN; plugins reload via `/reload-plugins` | plugins doc, §6 |
| Managed `managed-mcp.json` | UNKNOWN — assume session-start-only | gap |

The hooks doc lists `ConfigChange` as a plugin-supportable event (per
`notes/LOADER-SEMANTICS-AUDIT.md` §5 NEW_RULE_AVAILABLE), which **suggests**
Claude has *some* config-change detection. But the doc does not say
whether `ConfigChange` fires on `settings.json` edits or only on
`~/.claude.json` MCP changes, and it does not say whether the merged
settings tree is re-applied to the live session or only emitted as a
hook event. **The audit's stance applies: do not assume hot-reload.**

### 1.4 What happens on atomic-rename swap mid-session

Assume the worst case: Housekeeper writes `settings.json.tmp.<pid>`,
`fsync`s, then calls `rename(2)` to atomically replace
`~/.claude/settings.json`. A Claude session has the old file already
open (or already parsed into memory). The matrix:

| Case | Filesystem behavior | Claude-side effect |
|---|---|---|
| Claude had the file open with a held fd | macOS APFS and Linux ext4 both preserve the open fd against the old inode after `rename(2)`. Reads continue from the old content. | Claude reads stale data until it next `open()`s the file. Safe — no partial read. |
| Claude had already parsed the file into memory at session start | Memory is unchanged. | Claude continues with the old config until next session start. **Most likely case.** |
| Claude `open()`s the file after the rename | Reads the new content. | Claude gets the new config on its next read. Only material if Claude re-reads. |
| Claude has a watcher (e.g. `fs.watch`/`fsevents`) on the parent dir | macOS will emit `rename` events; Linux inotify emits `IN_MOVED_TO`/`IN_MOVED_FROM`. | If Claude listens, it can detect the change; behavior is undocumented. |
| Claude is mid-read when rename arrives | Atomic rename does NOT interrupt an in-flight `read(2)` system call. The buffer is filled from the old inode. | Safe — no torn read. |

**Worst credible case for v0.3:** Claude has a partial-config watcher
that emits a `ConfigChange` hook on `settings.json` edits but does
**not** re-merge live. Housekeeper removes a dangling hook; the next
session start picks it up; the current session continues running the
old hook entry (which still has a dangling path — same broken state
the user diagnosed). This is **not worse than the pre-harden state**.

**Recommendation:** Treat settings hot-reload as undocumented and
unsafe to assume. Every successful `harden` MUST emit a `RELOAD HINT`
in its output telling the user to restart Claude Code for the change
to take effect in active sessions. This matches the v0.2 platform memo
§3.1 pattern for settings edits.

### 1.5 The `/doctor` cross-check

`debug-your-config` documents `/doctor` as the live introspection
command that reports "invalid keys, schema errors, installation
health" and that "when /doctor reports issues, press `f` to send the
diagnostic report to Claude and have it walk through fixes with you"
(audit §9.1).

Operational implication: after a successful `harden`, the report's
next-step hint should include `/doctor` so the user can confirm the
broken hook entry is no longer surfaced as a config error. This is
not a Housekeeper-side check — it is a probe the user runs.

## 2. JSONC Support Analysis (PLAN Q2)

### 2.1 The question

`notes/PLAN-v0.3.md §4 Q2` asks: Claude Code accepts JSONC (`//`
comments) in `settings.json`. Housekeeper's parser is strict JSON.
Should `harden`:

- **a)** Refuse JSONC files with a clear refusal class
  (`settings-jsonc-detected`), routing the user to manual edit?
- **b)** Strip comments before reading, write them back on save
  (round-trip risk)?
- **c)** Adopt a tolerant JSONC parser (e.g. `jsonc-parser` from npm)?

### 2.2 What the docs actually say

The audit (2026-05-10) did **not** find an explicit statement in the
Claude Code documentation that `settings.json` accepts JSONC. The
phrasing "Claude Code accepts JSONC" in the plan (Q2) is folkloric —
it appears in community guidance, `claude-code` issue threads, and
the operator's own `~/.claude/CLAUDE.md`, but the `configuration` page
on `code.claude.com` (audit §1) describes the file purely as JSON
without mentioning comments.

This memo treats the JSONC claim as **plausible but unconfirmed**.

What is documented:

- The configuration page shows JSON examples throughout, no comments.
- `/doctor` reports "schema errors" — implying a strict parser is
  used at some layer (audit §9.1).
- `notes/LOADER-SEMANTICS-AUDIT.md` did not surface a JSONC mention
  in the 7 audited URLs.

What is inferred (operator-side evidence, not authoritative):

- `~/.claude/settings.json` in real homes commonly contains `//`
  comments inserted by editors or by users following community-driven
  guidance. Claude does not reject these files outright — sessions
  start, hooks fire.
- This implies **some** layer of Claude's parser is tolerant of
  comments — but it could be a documented behavior, an undocumented
  pre-processor, or a tolerant JSON parser (e.g. `JSON5` / `jsonc-parser`)
  used internally.

The honest position is: **Claude probably accepts JSONC, but we don't
have a Pinned source documenting which subset (only `//`? also `/* */`?
also trailing commas? also single-quoted strings?). Housekeeper cannot
mirror Claude's parser exactly without reading its source.**

### 2.3 What the trust-boundary doc forces

`docs/threat-model.md` §2 puts the home in the user's trust domain.
The home owner's existing `settings.json` is **input data**, not a
hostile payload. If it's JSONC, it's because the user (or their
editor, or their plugin installer) put comments there.

`docs/safe-mode.md` Hard Rules say safe mode "may parse JSON
structure" and "may report malformed config" — but doesn't forbid
JSONC tolerance. The safe-mode posture is read-only; it does not
prejudge whether the parser is strict.

For `harden` specifically, the threat-model implication is stronger:
**a refusal that fires on every JSONC home would mean Housekeeper
refuses to harden most real-world `~/.claude/settings.json` files**.
That's not a safety stance — it's a usability tax.

### 2.4 Recommendation for Q2

**Recommend option (a) for v0.3.0, with a v0.3.x escalation path to
option (c) once we have a confirming citation from Claude.**

Concretely:

1. **v0.3.0**: `harden` refuses JSONC files with refusal class
   `settings-jsonc-detected`. The refusal carries `nextStep` text
   pointing the user to manual edit, and the refusal message
   explicitly states: *"Housekeeper's parser is strict JSON. Your
   settings file appears to use comments. The Claude Code parser
   may accept this, but we cannot safely round-trip comments
   through a snapshot + rewrite + verify cycle."* This is honest
   about the tooling gap without overclaiming Claude's parser
   tolerance.
2. **v0.3.x** (post-confirmation): if Claude Code docs add an
   explicit "settings.json accepts JSONC" line, or a Claude
   engineer confirms in a public channel, switch to option (c) —
   adopt `jsonc-parser` (npm) for the read path, write strict JSON
   on save. Document the loss-of-comments semantics in
   `docs/migration-v0.2-to-v0.3.md` so the round-trip is
   non-surprising.
3. **Option (b) is rejected.** Strip-and-restore is the worst
   choice: comment placement is ambiguous (do comments attach to
   the next key, the previous key, or the file?), and a snapshot
   that preserves comment text but rewrites the structural content
   risks producing a "settings.json that looks unchanged but
   actually had a hook removed." That's a debugging nightmare and
   violates the v0.2 invariant that rollback restores the exact
   pre-mutation bytes.

The refusal class `settings-jsonc-detected` must be added to the
refusal taxonomy extension in `composeHardenPlan` (per
`notes/PLAN-v0.3.md §3 Refusal taxonomy extension`).

### 2.5 Detection heuristic

The detector needs a reliable way to distinguish JSONC from JSON
without false-positiving on legitimate `//` characters inside string
values (e.g. URL fields). Recommendation:

1. Attempt strict-JSON parse first.
2. If parse succeeds, proceed as JSON.
3. If parse fails with a SyntaxError, run a comment-detection regex
   on the raw text: `/^[^"]*(\/\/|\/\*)/m` on each line, ignoring
   lines that begin inside a string (use a tiny tokenizer rather
   than a regex if precision matters).
4. If a `//` or `/*` appears outside a string context, classify as
   JSONC and emit `settings-jsonc-detected`.
5. If the parse failed but no comment indicators are found, emit
   `settings.invalid_json` (existing detector); this is Q1's
   territory.

### 2.6 Impact on existing detectors

The current `detectSettingsInvalidJson` (audit.mjs:396) fires when
`context.settings.ok` is false. Today, that includes JSONC files —
they fail strict parse and surface as `settings.invalid_json`. This
is a **false positive**: JSONC homes have Claude running fine but
get flagged. The Q2 ruling above makes the JSONC case a separate
finding (`settings.jsonc_detected`) at `inform` claim level, NOT
`integrity`. The user's home is not broken; Housekeeper is just
not equipped to rewrite it.

This is a small but real classification fix that the tie-breaker
(T-D04) should pin.

## 3. MCP Server Lifecycle

This section answers Question 3 of the task brief: when Housekeeper
removes an MCP entry via `harden`, what happens to the running MCP
server?

### 3.1 Documented MCP startup behavior

Per `docs/loader-semantics.md` §6 + the MCP doc (audit §6):

- Plugin MCP servers: "enabled plugin MCP servers start automatically
  at session startup"
- User/Local/Project MCP servers (from `~/.claude.json` or `.mcp.json`):
  documented to connect at session start; the MCP doc lists scope
  precedence Local > Project > User > Plugin > connectors.
- Mid-session enable/disable: requires `/reload-plugins` for plugin
  MCP servers (audit §6). The doc does **not** describe how
  non-plugin MCP entries in `~/.claude.json` are reloaded mid-session.

The MCP server process model: each MCP server is a child process
spawned by Claude Code (or in claude.ai connector cases, an HTTP
client connection). Claude Code owns the lifecycle — Housekeeper
does not.

### 3.2 What happens when Housekeeper removes an MCP entry

Two scenarios, depending on whether Claude is running:

**Scenario A — Claude not running.**
Housekeeper rewrites `settings.json` (or, more likely, `~/.claude.json`
for User-scope MCP — note this is **not in v0.3 scope** per Q4 / Q5
deferral, see §3.5). Next session start, Claude reads the new file,
does not see the removed MCP entry, does not spawn that server.
Clean state.

**Scenario B — Claude running.**
Housekeeper rewrites the file. Claude's currently-running MCP server
process is **still alive** — Claude spawned it at the prior session
start. Per the threat model (§2 trust boundary), Housekeeper does
**not** signal, kill, or otherwise touch the MCP child process.
Outcomes:

| MCP entry was in… | Effect of file rewrite | When does the running server actually stop? |
|---|---|---|
| Plugin-provided MCP | Removed from settings, but Plugin still references it. Plugin enable/disable + `/reload-plugins` is the controlled path. Housekeeper's settings edit may not even affect plugin MCP definitions (those live in plugin `.mcp.json` or `plugin.json`, not user `settings.json`). | At session end / `/reload-plugins`, depending on Claude's internal logic. |
| User-scope `mcpServers` in `settings.json` | Removed. Server keeps running in current session. | Next session start. |
| User-scope MCP in `~/.claude.json` | NOT a v0.3 target. `~/.claude.json` is out of scope (see §3.5). | n/a |
| Project-scope MCP in `.mcp.json` | NOT a v0.3 target (project files out of scope per audit §1 home-locality). | n/a |
| Managed MCP in `managed-mcp.json` | NEVER a target. Managed is enterprise policy; Housekeeper has no business writing it (audit §6 NEW_RULE_AVAILABLE on `managed-mcp.json`). | n/a |

### 3.3 Does Claude tear it down on next read?

**Unknown for the mid-session case.** The audit explicitly leaves
"mid-session MCP server lifecycle" undocumented for non-plugin
servers. `/reload-plugins` is documented to reload plugin MCPs.
There is no documented `/reload-mcp` or `/reload-config` command in
`debug-your-config` §9.1.

**Operational implication:** Housekeeper cannot promise the MCP
server stops just because the entry was removed. The output of
`harden --target=settings.mcp_command_missing` must include a
RELOAD HINT identical in spirit to §1.4's settings hint:

```
RELOAD HINT
Housekeeper removed the MCP server entry "<name>" because its
command file did not exist. If Claude Code is currently running
with this server connected, restart Claude Code to fully release
the server connection. Run /mcp to confirm the server is no
longer listed.
```

This is honest about the gap and routes the user to the documented
probe (`/mcp`, audit §9.1) that gives ground truth.

### 3.4 The mcp_command_missing case is actually safe

The specific case `settings.mcp_command_missing` (the v0.3 promotion
candidate) is **easier** than the general case. The detector fires
when `mcpServers.<name>.command` points at a file that doesn't
exist. If the binary is missing, Claude **could not have started**
the server at session start — it would have failed with a spawn
error. So there's no running child process to worry about. The
worst case is:

- Claude logged a startup warning, kept going.
- The MCP entry sits dormant.
- Housekeeper removes the dormant entry.
- Next session start: no warning, no dormant entry.

This is a strictly-improving change. The RELOAD HINT in §3.3 is
still valuable as a documentation default, but the specific
finding doesn't carry the "kill a running child" worry that
deleting a working MCP entry would.

### 3.5 What v0.3 should NOT touch (yet)

Per `notes/PLAN-v0.3.md §1 "v0.3 does NOT include"`:

- MCP server repair beyond `settings.mcp_command_missing` — v0.4
- Multi-home / fleet support — not scheduled

Operationally for this memo:

- `harden` writes only `~/.claude/settings.json`.
- `harden` does NOT write `~/.claude.json` (which holds User-scope
  MCP per audit §1) — that file is out of v0.3 scope.
- `harden` does NOT write `.mcp.json` (project scope) — out of v0.3
  scope.
- `harden` does NOT write `managed-mcp.json` — never; managed is
  enterprise policy.

The tie-breaker (T-D04) should explicitly pin this scope reduction.
If the architect memo proposes to harden `~/.claude.json` or
`.mcp.json` in v0.3, push back here.

## 4. Race-Condition Analysis: Atomic Rename Mid-Read

This section answers Question 4 of the task brief.

### 4.1 The protocol

From `docs/snapshot-architecture.md` §4 (write-temp + rename +
fsync-parent), applied to settings:

```
1. read   <home>/.claude/settings.json     → buf_old
2. compute settings_new = transform(buf_old, patch)
3. validate settings_new (parses cleanly, idempotent, etc.)
4. snapshot <home>/.claude/housekeeper/snapshots/<id>/settings.json
            ← buf_old (copied byte-for-byte, fsync)
5. write   <home>/.claude/settings.json.tmp.<pid> ← settings_new
6. fsync   the tmp fd
7. rename  <home>/.claude/settings.json.tmp.<pid>
        → <home>/.claude/settings.json
8. fsync   parent directory <home>/.claude/
9. update  operation manifest status: applied
```

The atomicity guarantee we need: between step 7 and the operation
manifest update, any concurrent `open()`+`read()` from Claude Code
sees either the entirety of `buf_old` or the entirety of `settings_new`,
never a partial mix.

### 4.2 macOS APFS

`rename(2)` on macOS APFS is atomic for files within the same volume.
Apple's File System Programming Guide and the BSD `rename(2)` man
page (`man 2 rename`) describe it as "the rename(2) operation
atomically replaces the destination":

> "If the destination file exists, it will be atomically replaced
> with the source file. If the destination file is open in another
> process, the file descriptor remains valid and refers to the
> original (now-unlinked) file until closed."

Concretely, for Claude Code mid-read on APFS:

| Claude state | Behavior |
|---|---|
| `open(settings.json)` not yet called | Next `open()` gets new inode → new content. |
| `open(settings.json)` already called, fd held | fd continues pointing at the old inode (now unlinked from name). `read()` returns old content. |
| Mid-`read(2)` system call | The buffer is being filled from the old inode's data. Atomicity of `rename(2)` does not interrupt `read(2)`; the read completes with old content. |
| Reading via `mmap` | Same as above; the mapping is to the old inode. macOS `mmap` of a renamed-over file keeps the mapping valid until the fd closes. |

So on macOS APFS, the **read returns the old content cleanly** for
any process that opened the file before our `rename()`. No partial,
no torn, no half-state.

### 4.3 Linux ext4

`rename(2)` on Linux is required by POSIX to be atomic for files
within the same filesystem. The `rename(2)` man page (current Linux
man-pages 6.x):

> "If newpath already exists, it will be atomically replaced, so
> that there is no point at which another process attempting to
> access newpath will find it missing."

ext4 with default journaling (`data=ordered`) provides crash-safe
metadata: after `fsync()` on the parent dir (our step 8), the
rename is durable. For a concurrent reader, the same fd-vs-inode
semantics apply as macOS:

- Already-open fd points at the old inode (now unlinked).
- New `open()`s get the new inode.

ext4 differs from APFS in a few edge cases that **do not affect us**:

- ext4 has `data=writeback` mode where data may lag metadata across
  a crash. We don't run in this mode by default, and our `fsync`
  of the tmp fd before `rename` orders the data write.
- ext4 does **not** preserve `mmap`'d data across `rename` if the
  unlinked inode is the last reference and gets reaped. This is
  edge-case Linux behavior. Claude Code is unlikely to `mmap`
  `settings.json` — it's a small file, and typical config readers
  use `fs.readFile`.

### 4.4 Worst credible partial-read scenario

What if Claude's reader is naive: open, read first N bytes, sleep
for some reason, read next N bytes? Even then, the fd-after-rename
semantics protect us: the second read continues from the **same
inode** as the first read. The reader sees a consistent old file
or a consistent new file, never a mix.

The only way to get a partial read would be:

1. Claude opens `settings.json`, reads to offset X.
2. Claude closes the fd (releases the inode).
3. Housekeeper's rename completes.
4. Claude re-opens `settings.json`, reads from offset X. **(bug — this would be an error in Claude's reader, not ours)**

This is not a realistic Claude bug pattern. Treating it as a hazard
would require Housekeeper to either:

- Hold a file lock — but POSIX advisory locks (`flock`/`fcntl`)
  are not honored by all readers, and Claude's reader is not
  documented to acquire one.
- Use a transactional filesystem — outside our scope.

**Conclusion:** atomic rename satisfies the requirement. The race
window is bounded by the rename syscall itself (microseconds), and
any concurrent reader sees a consistent view of the file.

### 4.5 Confirm: holds on macOS APFS and Linux ext4

| OS / FS | Atomic rename? | Old fd preserved? | Concurrent-read corruption? |
|---|---|---|---|
| macOS APFS | YES (BSD rename(2), per man page) | YES | NO |
| Linux ext4 (data=ordered) | YES (POSIX, Linux man page) | YES | NO |
| Linux ext4 (data=writeback) | YES for metadata; data lag risk on crash, NOT on concurrent read | YES | NO (read-side) |
| macOS HFS+ (legacy) | YES — same BSD rename | YES | NO |
| NFS | Implementation-dependent; some NFS clients return -EBUSY | typically YES | UNKNOWN — flag as out-of-scope |
| SMB / CIFS | Implementation-dependent | UNKNOWN | UNKNOWN |

**Action item:** Housekeeper should detect network-filesystem homes
(via `statfs`/`f_fstypename`) and either refuse to mutate or emit a
`network-filesystem-detected` informational finding. This is a v0.3
enhancement that the architect memo should pin. The base assumption
(atomic rename works) holds for the documented supported platforms
(macOS APFS, Linux ext4) — which matches the v0.2 platform support
in `package.json` and `docs/threat-model.md` §1.

## 5. Schema Drift Across Claude Versions

This section answers Question 5 of the task brief.

### 5.1 The risk

Claude Code is on a ~weekly release cadence (per the operator's
own `~/.claude/CLAUDE.md`, which describes recurring plugin/cache
refresh patterns). The `settings.json` schema is not versioned by
a field Housekeeper can read.

If Claude v1.X adds a top-level key `foo`, Housekeeper v0.3 has
two failure modes:

| Failure mode | Effect |
|---|---|
| Drop the unknown key on rewrite | User's `foo` config silently disappears. Claude reverts to default behavior. Hard-to-debug regression. |
| Refuse to harden because of unknown key | Housekeeper becomes useless against any post-v0.3 Claude version. Operator perception: "Housekeeper is broken." |

The v0.2 release-readiness review (`notes/RELEASE-READINESS-v0.2.0.md`)
and `notes/PLAN-v0.3.md §6 Risks` both flag schema drift as a known
risk with mitigation "pin schema reading to documented shape; refuse
unknown top-level keys" — but neither resolves whether refuse or
preserve is the right default.

### 5.2 Preserve-unknown is the right default

The architecture says: snapshot the byte-exact original, transform
only the targeted subtree, write back the merged result. If
Housekeeper does this **structurally** (read JSON tree → apply
patch to a known sub-path → serialize tree), unknown top-level
keys pass through untouched.

Concretely:

```
buf_old   = readFile(settings.json)
tree_old  = JSON.parse(buf_old)
tree_new  = structuredClone(tree_old)
applyPatch(tree_new, patch)   // patch describes the change to e.g. tree_new.hooks
buf_new   = JSON.stringify(tree_new, null, 2)
write tree_new atomically
```

Under this protocol:

- Unknown top-level keys are read into `tree_old`, copied into
  `tree_new`, and serialized back out. They pass through.
- Unknown nested keys under `hooks.*` or `mcpServers.*` would also
  pass through, **as long as the patch only touches a specific
  subtree**.
- Comment-preservation does NOT pass through (see §2). Hence the
  JSONC refusal posture.

This is the v0.3 plan's "additive only" stance, applied to the
schema. Refusing on unknown top-level keys would be a
maintainability tax; preserving them is the architecture-consistent
choice.

### 5.3 What patch shapes preserve schema, what shapes don't

| Patch shape | Schema-preserving? |
|---|---|
| `remove hooks.PreToolUse[2]` (remove a hook entry by index) | YES — structural delete in a known subtree |
| `remove mcpServers.<name>` (remove an MCP server by name) | YES |
| `add hooks.NewEvent.[...]` | NO — invents a new key shape; not in v0.3 scope |
| `set hooks = {}` (clobber) | NO — destroys unknown hook entries |
| `merge settings.json with template` | NO — template may overwrite unknowns |

**Recommendation:** the `settings-rewrite` mutation kind (T-100)
must constrain its patch grammar to *removal of a specific path-keyed
entry* — never wholesale clobber or template merge. This matches the
v0.3 plan's restricted detector promotion set (hook_path_dangling,
mcp_command_missing) and the idempotency requirement (T-102).

### 5.4 Idempotency under schema drift

`notes/PLAN-v0.3.md §3` requires `settings-rewrite` patches to be
idempotent: applying twice yields the same output. Schema drift
plays nicely with this:

- If a user re-runs `harden` after Claude has added a top-level key
  `foo`, the patch still targets `hooks.PreToolUse[N]` (or wherever
  the broken hook lives). The `foo` key is preserved untouched on
  both the first and second apply.
- If `foo` happens to be a new key that **shadows** the patch path
  (e.g. Claude renamed `hooks` to `triggers`), Housekeeper's patch
  becomes a no-op or worse — it edits the old `hooks` key that
  Claude no longer reads. The detector that originated the finding
  would also be looking at the wrong subtree, so the upstream
  finding wouldn't fire. This is **not a new failure mode**; it's
  the detector going stale, which Housekeeper already handles via
  the `loader-semantics.md` audit pipeline.

### 5.5 Recommendation for Q5 (and beyond)

For the schema-drift specific question:

1. **v0.3.0**: preserve unknown top-level keys structurally. Test
   in `test/harden-plan.test.mjs` with a fixture that has an
   `unknownTopLevelKey: 42` in `settings.json`; after harden, that
   key must still be present and unchanged.
2. **v0.3.0**: refuse patches that target an unknown subtree. If
   the detector fires `settings.hook_path_dangling` but
   `settings.hooks` is missing entirely (e.g. Claude renamed the
   key), refuse with `settings-shape-unknown` rather than
   inventing the key.
3. **v0.3.x**: add a periodic audit task (re-run
   `notes/LOADER-SEMANTICS-AUDIT.md` on every minor release) to
   catch schema drift before it hits users. This is process, not
   code.

Q5 in the plan is specifically about *documentation site version
pin automation* — a release-process concern, not the schema-drift
concern. The platform memo flags schema drift as a code concern
and routes the documentation question to the product memo.

## 7. Batch Mode Considerations (PLAN Q3)

`notes/PLAN-v0.3.md §3` describes `clean --batch` aggregating up to
10 findings into one operation manifest. The platform-side
implications:

### 7.1 Batch and `settings-rewrite`

If a batch includes multiple `settings.hook_path_dangling` findings
against the same `settings.json`, the patches MUST be merged into a
single read-modify-write cycle. Two reasons:

1. Atomic rename of the same file twice in quick succession defeats
   the atomicity (the first rename's content is overwritten before
   any reader could observe it). Better to apply both patches to
   the in-memory tree, then write once.
2. Snapshot economy: snapshotting `settings.json` once per batch
   instead of N times keeps the snapshot tree small.

This affects the architect's mutation pipeline: `settings-rewrite`
needs to accept a list of patches and apply them in a deterministic
order, not just one patch per operation.

### 7.2 Batch failure semantics

The plan's Q3 asks: if 3 of 5 operations succeed and the 4th fails,
do we (a) auto-rollback all 5, (b) leave partial, or (c) resume?

For `settings-rewrite` batches **specifically**, the answer is
forced: there is no partial state. Either all the patches apply
to the in-memory tree and the rewrite succeeds (atomic rename),
or one validation fails and **no patches apply** (we never write
the file). The "partial" case only arises if a batch spans both
`settings-rewrite` operations and other mutation kinds
(`dir-rmtree`, `file-unlink`).

Cross-kind partial-apply matrix:

| Step 1 | Step 2 | Step 3 fails | What state are we in? |
|---|---|---|---|
| settings-rewrite (success) | dir-rmtree (success) | file-unlink (fail) | settings rewritten, dir deleted, file untouched |
| dir-rmtree (success) | settings-rewrite (success) | dir-rmtree (fail) | one dir gone, settings rewritten, target dir untouched |
| (any) | (any) | settings-rewrite (validation fails) | prior steps applied, settings untouched |

In all of these, auto-rollback restores the snapshot of every
successful step. The plan's Q3 option (a) is the right answer
because:

- It matches v0.2's `Q-USER-5` partial-apply ruling.
- It avoids leaving the user with a half-hardened home.
- The cost ("wasted work" — 3 successful operations undone) is
  bounded by the 10-finding batch cap and is recoverable by
  re-running with the failing finding removed.

### 7.3 Lock-and-snapshot economics

The existing `<home>/.claude/housekeeper/lock` (per v0.2 platform
memo §2.2) is per-home, not per-operation. A batch holds the lock
once. Snapshot tree similarly: one snapshot dir per batch, listing
N pre-state files. This is consistent with the plan's "Snapshot is
taken once for the whole batch."

## 14. Summary

The platform-interop bottom line for v0.3:

1. **Atomic rename is the right primitive.** Verified on macOS APFS
   and Linux ext4 (§4). Network filesystems out of scope.
2. **JSONC: refuse for now** (§2). The tooling cost of correct
   JSONC round-tripping exceeds the user value until we have a
   pinned doc citation.
3. **MCP teardown: not Housekeeper's job** (§3). Reload-hint output
   routes the user to `/mcp` and restart.
4. **Schema drift: preserve-unknown structurally** (§5). Patch
   grammar must be path-keyed removal, never clobber.
5. **Mid-session reads: safe** (§1.4, §4). The race window is
   bounded by the rename syscall and any concurrent reader sees
   a consistent view.
6. **Scope: v0.3 writes only `~/.claude/settings.json`** (§3.5).
   Other settings surfaces wait for v0.4.

The plan's central architectural assumption — that
`settings-rewrite` is "just" snapshot + atomic write — holds, but
only because the JSONC and schema-drift hazards are pushed out
of v0.3 by refusing them at the planner. The tie-breaker should
treat that refuse-stance as load-bearing, not as a politeness.
