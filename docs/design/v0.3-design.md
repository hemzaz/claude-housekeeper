## §0 TL;DR

Five load-bearing rulings for v0.3:

1. **Q1 invalid_json — REFUSE.** Don't attempt JSON repair; surface at
   `prepare` stance with `hardenable: true`. Refusal class
   `settings-shape-unknown` if harden is invoked.
2. **Q2 JSONC — REFUSE in v0.3.** Two-phase detection (strict
   `JSON.parse` first; on `SyntaxError` run a lex-aware comment scan).
   Refusal class `settings-jsonc-detected`. Revisit v0.4.
3. **Q3 batch atomicity — manifest-atomic, NO auto-rollback.** Status
   reaches `verified` only when every op verifies; on any failure the
   manifest stays at `applied` with `partialApply: true` and the
   `housekeeper.interrupted_operation` detector surfaces it next session.
   Architect+product majority; platform overruled (incorrect reading of
   v0.2 Q-USER-5).
4. **Q4 hardenable flag — YES, per-detector.** Detectors self-declare
   `hardenable: true/false` on `DetectorOutput`. README "Current Checks"
   gains a 4th column.
5. **Q5 version-pin automation — CI CHECK.** ~6-line workflow step that
   asserts `docs/index.html` matches `package.json` `version`. Lands as
   T-604.

Plus a critical Phase-1 prereq (T-099) surfaced by the architect's §6.3:
the existing `execution-class` refusal rule in `scripts/lib/clean-plan.mjs`
refuses every harden invocation by default unless the classifier is
refactored to accept `allowedExecutionClasses` as input.

## §2 Q1–Q5 final rulings

Each ruling is one row of `notes/PLAN-v0.3.md §5 Decision Log` (added in
this commit).

### §2.1 Q1 — `settings.invalid_json` recovery — REFUSE

**Decision:** Refuse (option a). The detector surfaces the finding at
`prepare` stance with `hardenable: true` so `diagnose` shows a `harden …`
next step. If the user invokes harden against an invalid_json finding,
compose-time refusal fires with class `settings-shape-unknown` (product's
specialization, C2).

**Rationale:** A `settings.json` that doesn't parse is in an unknown
state. The user may be mid-edit; auto-recovery destroys their work. JSON
repair heuristics produce silently-wrong settings — exactly the failure
mode v0.2 ruled out under `no-mutation-mapping-in-v0.2`.

**Linked rows:** C2. **Voice agreement:** all three (a).

### §2.2 Q2 — Settings JSONC support — REFUSE

**Decision:** Refuse JSONC in v0.3 (option a). Refusal class
`settings-jsonc-detected`. Detection: two-phase per C4 — try strict
`JSON.parse` first; on `SyntaxError`, run a lex-aware tokenizer that
scans for `//` or `/*` outside string context. Revisit deferred to
**v0.4** (NOT v0.3.x).

**Rationale:** Comment round-trip is an unsolved problem with current
parsers. `jsonc-parser` parses but doesn't preserve comments on
serialise. `comment-json` has edge cases around comments inside merged
objects. Refusing in v0.3 is conservative-correct. The platform memo's
honest position (Claude probably accepts JSONC but no pinned source)
means even confirming JSONC tolerance doesn't yet tell us which parser
to mirror.

**Linked rows:** C3, C4. **Voice agreement:** all three (a).

### §2.3 Q3 — Batch atomicity — MANIFEST-ATOMIC, NO AUTO-ROLLBACK

**Decision:** The manifest is atomic at the verification level —
`status: verified` only when EVERY operation verifies. The runtime does
NOT auto-rollback successful operations on a downstream failure. On any
failure, the manifest stays at `status: applied` with
`partialApply: true`. The `housekeeper.interrupted_operation` detector
surfaces it on next `diagnose`; `nextStep` routes to `rollback <id>`
which restores ALL files in the manifest (the snapshot tree holds the
pre-state of every operation in the batch).

**Rationale:** This is the major divergence. Architect and product both
argue against auto-rollback: it silently undoes work the user explicitly
authorised, contradicts v0.2 Ruling 9 (`Auto-rollback on partialApply
deferred to v0.2.x`), and discards the partial state before the user
can inspect it. Platform argued FOR auto-rollback, citing "Q-USER-5
partial-apply stance" — but Q-USER-5 in v0.2 (per `clean-design.md §8`)
actually says auto-rollback is **deferred**. Platform's reading was
incorrect.

Crucially, within a SINGLE `settings-rewrite` operation (one file), the
mutation is forced-atomic by construction (read → patch → validate →
atomic rename). Cross-kind partial-applies in `clean --batch` are the
only place this ruling bites — and v0.3 `clean --batch` excludes
`settings-rewrite` operations (C6).

**Linked rows:** C5, C6, C7, C24. **Voice agreement:** architect b /
product manifest-atomic-no-auto-rollback / platform a. Architect+product
majority chosen; platform overruled on C24 (correct reading of v0.2
Ruling 9).

### §2.4 Q4 — Per-detector `hardenable` flag — YES

**Decision:** Yes. Detectors self-declare `hardenable: true/false` on
their `DetectorOutput`. Same pattern for `cleanable: true/false`
(forward-looking; v0.2's `CLEANABLE_DETECTORS_V02` side table stays
as-is, no retrofit). The flag is a *candidacy* signal, not a *will-act*
promise — compose-time refusals can still fire.

**Rationale:** All three memos agree. Detector co-location wins on
ownership (the detector knows whether it has a meaningful patch),
greppability, and composability with future surfaces. The README's
"Current Checks" table gains a 4th column (`hardenable`).

**Linked row:** C8. **Voice agreement:** all three yes.

### §2.5 Q5 — Site/docs version-pinning automation — CI CHECK

**Decision:** CI check (option a). Add a workflow step to
`.github/workflows/ci.yml` (or a new `version-pin.yml`) that asserts
`docs/index.html` contains `v$VERSION` where `$VERSION` is
`jq -r .version package.json`. ~6-line shell snippet; no build pipeline.

**Rationale:** Replacing the hardcoded version with build-time
substitution (option b) requires a build step on a hand-edited static
file. A CI check closes the G4 gap with zero new tooling. All three
memos converge on (a).

Implementation lands as **T-604**.

**Linked row:** C17. **Voice agreement:** all three (a).

## §3 Buildable spec

### §3.1 `settings-rewrite` mutation kind

Add to `MUTATION_REGISTRY` in `scripts/lib/snapshot.mjs`:

```
"settings-rewrite": {
  preApply: async (op, ctx) => {
    // 1. Strict JSON.parse the file at op.targetPath
    // 2. On SyntaxError, run JSONC tokenizer; if comments found,
    //    return refusal { class: "PreApplyRefusal", reason: "settings-jsonc-detected" }
    // 3. Apply op.patch to the parsed object in memory
    // 4. Validate output JSON.parse(JSON.stringify(result)); on failure return
    //    refusal { reason: "patch-produces-invalid-json" }
    // 5. Idempotency: apply patch to result; if !deepEqual(result, twice)
    //    return { reason: "patch-not-idempotent" }
    // 6. Return { ok: true, plannedBytes: stringify(result).length }
  },
  apply: async (op, ctx) => {
    // Read original → parse → apply patch → stringify with stable formatter
    // → atomicWrite (write-temp + rename + fsync-parent) per existing helper
    // Return updated content for sha256After
  },
  rollback: async (op, ctx) => {
    // Identical to file-restore-from-snapshot: copyFile snapshot back to target
  }
}
```

### §3.2 `harden-plan.mjs` shape

New module mirroring `scripts/lib/clean-plan.mjs`:

```
export composeHardenPlan(home, { target, path }): HardenPlan | RefusalSet
export validateHardenPlan(plan, home): ValidatedPlan
export executeHardenPlan(validatedPlan, home): OperationManifest
```

Reuses:
- `loadProtectionPolicy`, `acquireLock`, `releaseLock` from `clean-plan.mjs`
- `takeSnapshot`, `applyOperation`, `verify` from `snapshot.mjs`
- `MUTATION_REGISTRY["settings-rewrite"]` from §3.1

The 12-rule refusal classifier from `clean-plan.mjs` is **shared**, not
forked. Per C9 (architect §6.3), the classifier must be refactored to
take `allowedExecutionClasses` as input — see T-099.

### §3.3 Extended refusal taxonomy

Existing 12 reasons from `clean-plan.mjs` stay. New harden-specific
additions:

| Class | Reason | Trigger |
|---|---|---|
| `PreApplyRefusal` | `settings-shape-unknown` | Top-level JSON shape not in known Claude settings schema |
| `PreApplyRefusal` | `settings-jsonc-detected` | Tokenizer found `//` or `/*` outside string context |
| `PreApplyRefusal` | `patch-not-idempotent` | Apply-twice produces different output |
| `PreApplyRefusal` | `patch-produces-invalid-json` | Output fails JSON.parse round-trip |
| `EnvironmentRefusal` | `settings-network-filesystem` | Target on NFS/SMB (no POSIX atomic-rename guarantee) |
| `BudgetRefusal` | `batch-exceeds-aggregate-budget` | Sum of `--target=` pairs exceeds 50 files / 10 MiB |

Each carries a `nextStep` per G7 (the `NEXT_STEP_BY_REASON` table in
`clean-plan.mjs` is extended).

### §3.4 Detector promotion

Detectors gain `hardenable: boolean` and `cleanable: boolean` on
`DetectorOutput`. The audit pipeline (`assembleReport`) propagates the
candidacy to the rendered finding. README "Current Checks" table grows
a 4th column.

Promotion sequence (per C21):

| T-302 | `settings.invalid_json` | (No patch — refuses with `settings-shape-unknown`; surfaces guidance via `nextStep`) |

### §3.5 Q5 CI check

```
# .github/workflows/ci.yml addendum
- name: docs/index.html version pin matches package.json
  run: |
    VERSION="$(jq -r .version package.json)"
    grep -q "v$VERSION" docs/index.html \
      || (echo "::error::docs/index.html version pin does not match package.json v$VERSION" && exit 1)
```

Lands as T-604. Closes the G4 gap surfaced in the v0.2.0 release-readiness review.

### §3.6 `harden` CLI surface

Mirrors `clean --confirm --yes`:

```
claude-housekeeper harden                                  # dry-run; refuses mutation
claude-housekeeper harden --confirm                        # refuses without --yes
claude-housekeeper harden --confirm --yes \
    --target=settings.hook_path_dangling \
    --path=<absolute path to settings.json> \
    [--timeout=<seconds>] [--json] [--safe]                # mutates one finding
```

Output includes a RELOAD HINT (per C11):

```
DONE: 1 operation verified, op_id=op_20260516_a1b2c3d4
RELOAD HINT: Claude does not document hot-reload of settings.json.
             Restart your Claude session for the change to take effect.
```

### §4.2 Rationale for T-099

Architect §6.3: the existing `composeCleanPlan` classifier hard-codes
the allowed `executionClass` set (currently `inert`-only). Harden
targets `settings.json` which has `executionClass: known-execution-context`
under the v0.1 surface-classification spec — so without the refactor,
**every harden invocation will refuse with `execution-class` and v0.3
ships a no-op.**

T-099 is a small refactor (~30 LOC) that promotes the hardcoded set to a
parameter. `runClean` passes `["inert"]`; `runHarden` passes
`["inert", "known-execution-context"]`. All existing tests stay green
because the default matches.
